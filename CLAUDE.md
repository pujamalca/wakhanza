## Apa itu wakhanza

Gateway notifikasi WhatsApp satu-arah untuk SIMRS Khanza (sistem informasi rumah sakit). Membaca kejadian (booking, antrian, hasil lab/radiologi, obat siap, tagihan) dari database MariaDB Khanza secara **read-only**, lalu mengirim WhatsApp ke pasien lewat whatsapp-web.js. Satu rumah sakit, satu nomor WhatsApp, dipasang on-premise di server RS. Tidak pernah menulis ke database itu — nol perubahan pada SIMRS Khanza adalah sasaran desain nomor satu (PRD §3), dan ini **diverifikasi mesin** lewat grant MariaDB, bukan cuma disiplin kode (lihat `npm run verify:db`).

**Berkas ini menyebut database Khanza sebagai `sik`, dan di mesin ini namanya BUKAN itu.** `SIK_DB_NAME` menunjuk **`alca`** — itulah yang dibaca produksi. `sik` masih ada di server yang sama sebagai salinan berisi riwayat, dan justru lebih berguna untuk MELIHAT bentuk data: beberapa tabel (`referensi_mobilejkn_bpjs_batal`, `bridging_surat_kontrol_bpjs`) masih kosong di `alca` tapi berisi ribuan baris di `sik`. Jadi "`sik`" di sepanjang berkas ini berarti "database Khanza", bukan nama harfiahnya; jangan menaruh nama database mana pun di kode (semuanya lewat `SIK_DB_NAME`), dan jangan menyimpulkan sebuah query salah hanya karena ia mengembalikan nol baris terhadap `alca`.

Aturan proses dari `IMPLEMENTATION_PLAN.md` yang tetap berlaku untuk pekerjaan lanjutan (Fase 5, atau perubahan pada Fase 0–4):

- **Setiap klaim "selesai" harus disertai keluaran perintah yang membuktikannya** — bukan "seharusnya jalan". Semua yang tercatat "selesai" di atas dibuktikan lewat perintah nyata terhadap database `sik`/`wakhanza` sungguhan, bukan diasumsikan.

## Perintah

```bash
npm run dev               # Next.js dev server, port 3100
npm run worker            # proses worker (poller + dispatcher + sesi WhatsApp) -- perlu scan QR pertama kali
npm run migrate           # terapkan migrations/*.sql yang belum jalan (skema wakhanza)
npm run verify:db         # buktikan sik menolak tulisan, dan audit_log append-only tertegak
npm run verify:plans      # EXPLAIN tiap query poller; gagal bila ada type:ALL selain booking_registrasi
npm run poll:dryrun       # cetak pesan yang AKAN terkirim untuk SEMUA pemicu tanpa mengirim/menulis apa pun
npm run dryrun:bpjs -- <database> [tanggal]   # sama, tapi bisa diarahkan ke database Khanza LAIN -- tabel BPJS sering kosong di instalasi baru
npm run dryrun:surat -- [database] [no_surat|no_rawat]   # pratinjau surat sakit/sehat + BUKTIKAN PDF-nya terbentuk (meluncurkan Chromium)
npm run dryrun:hibah -- [database]            # nota hibah; tabelnya kosong di alca, jadi arahkan ke database lain
npm run dryrun:kontrol -- [database] [tanggal]  # pengingat kontrol non-BPJS; TANGGAL acuan bisa diserahkan karena pemicunya harian H-N
npm run scan:contacts -- --dry-run   # hitung nomor pasien yang tidak terpakai, tanpa menulis
npm run scan:contacts     # isi patient_contact untuk SELURUH pasien sekaligus (lihat di bawah)
npm run seed:admin -- <username> "<nama>" <password>   # buat user dashboard pertama (role admin)
npm run users -- list                # daftar akun dashboard + status aktif/terkunci
npm run users -- add <username> "<nama>" <admin|operator> <sandi>   # sama dengan tombol di /pengguna
npm run users -- disable <username>  # juga: enable / unlock / passwd <username> <sandi-baru>
npm run users -- delete <username>   # permanen; pakai disable kalau akunnya mungkin dipakai lagi
npm run harden:permissions  # icacls .env + .wwebjs_auth ke akun saat ini + SYSTEM (jalankan ulang tiap sesi WA baru)
powershell -ExecutionPolicy Bypass -File scripts/install-backup-task.ps1   # daftarkan cadangan harian (lihat di bawah)
npm test                  # semua test unit (fungsi murni, TIDAK butuh database); `npm test -- core/phone` untuk satu suite
npm run test:int          # uji integrasi enqueueMessage() -- BUTUH MariaDB hidup, lihat di bawah
npm run typecheck         # tsc --noEmit
npm run lint
npm run build
npm run audit             # npm audit --omit=dev; lihat "Penyesuaian Implementasi" TECH_STACK.md -- tidak akan pernah 0 tanpa breaking change, dan itu didokumentasikan sengaja
```

`npm run worker:dev` = `npm run worker` + tsx watch. **Jangan dipakai saat sesi WhatsApp hidup** -- tiap penulisan berkas menyalakan ulang proses, dan restart beruntun adalah persis yang merusak state sesi (lihat "Operasi produksi" di bawah).

`verify:db` dan `verify:plans` bukan pemeriksaan opsional — keduanya menegakkan dua batasan paling gampang dilanggar tanpa sadar: menulis ke `sik`, dan query yang diam-diam berubah dari index seek menjadi full table scan. Jalankan keduanya setiap kali koneksi atau query poller disentuh.

**Izin pindai penuh diberikan per TABEL, bukan per query** (`PlanCheck.allowFullScan`, berisi alias sebagaimana muncul di kolom `table` EXPLAIN — `b`/`d`/`p0`, bukan nama tabel aslinya). Bentuk lamanya `boolean`, dan itu terlalu tumpul dalam dua arah sekaligus: satu query menyentuh banyak tabel, jadi mengizinkan pemindaian pada SATU di antaranya berarti berhenti menjaga SEMUANYA — query jadwal dokter menyentuh tiga tabel padahal yang memang kecil cuma `dokter`. `maxRows`-nya pun tidak pernah benar-benar jalan: pemeriksaannya keburu dilewati oleh `continue`, jadi jaring pengaman yang tertulis di komentarnya sebenarnya tidak ada. Sekarang izinnya menggugurkan tepat dua pemeriksaan yang jadi tidak berlaku (`type=ALL` dan `key=NULL`) sementara `maxRows` tetap ditegakkan untuk semua — justru pada tabel yang boleh dipindai penuh itulah asumsi "tabel ini kecil" perlu gagal berisik saat ternyata keliru.

Satu jebakan lagi di skrip yang sama: **baris EXPLAIN dengan `table = NULL` bukan pemindaian penuh, melainkan kebalikannya** ("Impossible WHERE noticed after reading const tables", "Select tables optimized away") — optimizer sudah membuktikan hasilnya tanpa membaca apa pun. Dulu `type ?? 'ALL'` membacanya sebagai full scan, sehingga pemeriksaan GAGAL untuk query yang justru paling murah. Ketahuan lewat query pencarian no. pendaftaran, yang nilai contohnya memang sengaja tidak ada di database mana pun — dan nilai contoh yang tidak cocok dengan data nyata adalah keadaan NORMAL untuk pemeriksaan rencana, bukan kekecualian.

## Operasi produksi: PM2, sesi WhatsApp, cadangan

Seluruh isi seksi ini hanya berlaku saat menjalankan lewat **PM2** atau menyentuh daur hidup sesi WhatsApp. Kalau yang dikerjakan cuma menulis query poller atau halaman dashboard, lompati saja.

Produksi: `ecosystem.config.js` (PM2, dua app: `wakhanza-worker` fork-mode 1 instance, `wakhanza-web`) -- `pm2 start ecosystem.config.js` lalu `pm2 save`. **Enam jebakan Windows di jalur ini, semuanya baru ketahuan saat PM2 benar-benar dipakai** (`npm run worker` tidak pernah menyentuhnya) dan semuanya sudah diperbaiki:

1. **`script` tidak boleh menunjuk `node_modules/.bin/<apa pun>`** -- berkas di `.bin` tanpa ekstensi adalah skrip `/bin/sh` (npm menaruh pembungkus `.cmd`/`.ps1` terpisah untuk Windows), sedangkan PM2 menjalankan `script` dengan node -> `SyntaxError: missing ) after argument list`, berulang tanpa henti karena `autorestart`. Kena pada KEDUA app. Sekarang menunjuk berkas JS/TS sungguhan + `interpreter: 'node'` eksplisit.
2. **Worker memakai `node --import tsx berkas.ts`, bukan CLI `tsx`** -- CLI menjalankan kode di proses ANAK, sehingga PM2 hanya mengawasi pembungkusnya: `max_memory_restart: '800M'` akan mengukur pembungkus yang selalu kecil alih-alih Chromium yang merembes (satu-satunya alasan angka itu ada), dan SIGTERM berhenti di pembungkus tanpa sampai ke handler shutdown yang menutup sesi WhatsApp dan pool database.
3. **`.env`/`.wwebjs_auth` wajib memberi akses ke SYSTEM** -- lihat TECH_STACK.md §"Izin Berkas". Gejalanya menyesatkan: worker mati berulang dengan `SIK_DB_HOST wajib diisi` padahal berkasnya ada.
4. **Handler shutdown TIDAK PERNAH jalan, dan itu merusak sesi WhatsApp.** Windows tidak punya sinyal POSIX; PM2 tidak benar-benar mengirim SIGTERM, jadi `process.on('SIGTERM')` praktis tak pernah menyala. Ditemukan dengan cara paling sederhana: baris pertama `shutdown()` (`"wakhanza-worker berhenti..."`) muncul **0 kali** di seluruh log, di semua restart yang pernah terjadi. Akibatnya Chromium mati mendadak di tengah penulisan state sesi (`.wwebjs_auth`, LevelDB) -- dan kerusakannya baru muncul pada start BERIKUTNYA: `authenticated` menyala, lalu `ready` **tidak pernah datang**. Perbaikannya dua bagian, keduanya perlu: `shutdown_with_message: true` (PM2 mengirim pesan IPC `'shutdown'`, ditangani lewat `process.on('message')`) DAN `kill_timeout: 20000` (bawaannya 1600 ms -- menutup Chromium plus flush LevelDB tidak selesai secepat itu, jadi SIGKILL tetap datang di tengah jalan sekalipun pesannya sampai). **`pm2 restart` tidak membaca ulang `ecosystem.config.js`** -- perubahan di atas baru berlaku setelah `pm2 delete` + `pm2 start ecosystem.config.js`.

5. **Satu perintah `pm2 restart` meluncurkan DUA proses, dan yang bekerja justru jadi tak terlihat.** Terukur dari log: 47 kali start tapi `shutdown()` hanya 5 kali, dan 16 kali `browser is already running`. Jalur IPC shutdown-nya sendiri BENAR -- kelima kalinya menutup Chromium dengan bersih. Masalahnya, keluarnya proses lama itu sendiri dihitung PM2 sebagai exit yang perlu `autorestart`, **di atas** restart yang sedang ia jalankan:

   ```
   06:34:43  proses lama shutdown rapi (exit 0)
   06:34:45  PM2 meluncurkan pengganti #1  -> berhasil, memegang Chromium
   06:34:50  PM2 meluncurkan pengganti #2  -> kalah, "browser is already running"
   ```

   Pengganti #2 mati dengan exit 1 -> autorestart -> kalah lagi -> berputar tiap 5 detik (`restart_delay`) tanpa akhir. Dan karena PM2 selalu menganggap proses TERBARU sebagai miliknya, pengganti #1 yang justru bekerja menjadi **yatim**: `pm2 list` menampilkan pid lain, `pm2 stop` tidak menyentuhnya, dan worker terus mengirim WhatsApp di luar kendali. Dibuktikan langsung -- sesudah `pm2 stop`, prosesnya masih hidup dan `wa_session.heartbeat_at` masih diperbarui.

   Perbaikannya `src/worker/singleInstance.ts`, dipanggil PALING AWAL di `main()` (sebelum database, sebelum Chromium -- yang diperebutkan adalah direktori sesi, jadi yang kalah harus tahu sebelum menyentuhnya). Tiga keputusan yang menempel:

   - **Yang kalah MEMINTA pemegangnya mundur, bukan keluar dan bukan sekadar menunggu.** Keluar adalah persis yang memberi makan loop-nya. Tapi sekadar menunggu juga salah ujungnya: PM2 berakhir melacak si penunggu sementara pemegang sesi tetap yatim, sehingga `pm2 restart` berikutnya hanya mengganti penunggunya dan **kode baru tidak pernah benar-benar dijalankan** -- kegagalan yang lebih senyap daripada loop yang berisik. Dengan meminta mundur, ujungnya benar: proses yang dilacak PM2 adalah proses yang memegang sesi.
   - **Pemegang yang mundur WAJIB lewat `shutdown()`**, bukan `process.exit()` -- kalau tidak ia meninggalkan state sesi setengah tertulis untuk yang mengambil alih, yaitu persis kerusakan di poin 4.
   - **Kuncinya PORT (`WORKER_LOCK_PORT`, default 3101), bukan berkas kunci.** Port dilepas sistem operasi saat proses mati, termasuk SIGKILL dan listrik padam; berkas kunci berisi pid meninggalkan kunci basi sesudah kematian mendadak -- dan kematian mendadak justru mode kegagalan paling sering di sini. Soketnya sekalian jadi jalur permintaan mundur. Ini **bukan** pelanggaran "kedua proses tidak pernah berkomunikasi lewat HTTP": aturan itu tentang koordinasi APLIKASI (antrean pesan, status sesi) yang tetap sepenuhnya lewat tabel; yang lewat sini cuma satu kata kendali daur hidup, antara dua instance worker yang sama, di loopback.

6. **`pm2 start` WAJIB dari PowerShell, bukan git-bash.** Dijalankan dari git-bash, worker mati berulang dengan `Variabel lingkungan SIK_DB_HOST wajib diisi` -- gejala yang IDENTIK dengan jebakan izin berkas di poin 3, sehingga menyesatkan ke arah `harden:permissions` padahal `icacls .env` sudah benar (`SYSTEM:(R)` dan akun saat ini `(R)`), berkasnya ada, dan `process.loadEnvFile()` atas lintasan absolut yang sama berhasil bila diuji langsung dari shell itu juga. Perintah yang sama persis dari PowerShell langsung `online` dengan 0 restart. Terukur, bukan dikira: `pm2 delete` + `pm2 start ecosystem.config.js --only wakhanza-worker` dicoba di kedua shell berturut-turut dengan konfigurasi yang tidak disentuh. Jangan buang waktu pada izin berkas sebelum mencoba PowerShell lebih dulu.

**`ready` TIDAK berarti halamannya bisa mengirim, dan ketiga sinyal kesiapan buta pada bedanya.** whatsapp-web.js menaruh objek pembantunya, `window.WWebJS`, ke dalam halaman lewat `Client.inject()`. Objek itu **dihapus setiap kali frame bernavigasi** dan disuntikkan ulang secara ASINKRON (`pupPage.on('framenavigated', async () => { await this.inject(); })`), tanpa satu pun event yang menandainya. Di sela itu `Client.sendMessage()` -- yang memanggil `window.WWebJS.getChat(chatId, ...)` di dalam halaman -- gagal dengan `Cannot read properties of undefined (reading 'getChat')`. Yang undefined bukan chat-nya, melainkan seluruh objek suntikan kita.

| Sinyal | Yang dibacanya | Melihat celahnya? |
|---|---|---|
| `isWaReady()` | baris `wa_session` yang ditulis saat event READY | tidak — keadaan HISTORIS, bukan sekarang |
| `checkHealth()` → `getState()` | `window.require('WAWebSocketModel')` | tidak — modul milik WhatsApp SENDIRI, selamat dari navigasi |
| `window.WWebJS` | objek suntikan whatsapp-web.js | inilah yang hilang |

Akibatnya bukan satu baris log yang mengganggu: tiap kejadian menghabiskan **satu dari hanya tiga** percobaan (`core/retry.ts`), dan startup justru saat antrean paling menumpuk. Tiga kali seperti itu menandai notifikasi pasien `failed_permanent`, yang sejak itu hanya bergerak kalau ada manusia menekan "Kirim ulang" — gangguan halaman beberapa detik berubah jadi pesan yang tidak pernah sampai. Perbaikannya tiga lapis, dan ketiganya perlu:

- **`core/waError.ts`'s `galatHalamanBelumSiap()`** memisahkan "belum sempat mencoba" dari "sudah dicoba dan gagal". Yang pertama TIDAK menaikkan `attempts` dan TIDAK menulis `send_log` — baris log percobaan yang tidak pernah terjadi hanya membuat riwayatnya berbohong. Dicocokkan lewat TEKS galat karena galatnya lahir di dalam Chromium lalu diseberangkan puppeteer, jadi sudah luruh jadi pesan (alasan yang sama dengan `galatBerkasTerkunci()`). Daftar penandanya sengaja **sempit**: yang terlalu longgar membuat kegagalan sungguhan dicoba ulang tanpa batas tanpa pernah muncul di panel "perlu ditinjau" — persis kelas kegagalan yang sudah dibayar di `core/outboxStatus.ts`.
- **`tungguHalamanSiap()`** menjajaki `window.WWebJS` langsung ke halaman, dipakai gerbang dispatcher (anggaran 2 detik, lewati siklus) DAN `checkHealth()` (anggaran panjang, supaya sela penyuntikan yang normal — biasanya di bawah satu detik — tidak dibaca sebagai gangguan lalu memicu restart; penautan ulang yang terlalu sering justru memperlambat sinkronisasi WhatsApp). **Probe yang tidak bisa dijalankan dianggap SIAP, bukan sebaliknya**: `pupPage` bukan tipe publik, dan gagal-tertutup berarti dispatcher berhenti mengirim selamanya tanpa satu pun galat kalau bentuk pustakanya berubah — jauh lebih buruk daripada bug yang sedang diperbaiki. Jaring pengaman sebenarnya ada di sisi tangkapan.
- **Tidak ada risiko berputar selamanya**, dan itu tidak perlu mekanisme baru: `isStale()` (F5.3) tetap membatalkan pesan yang pemicunya kelewat tua, dan halaman yang tidak pernah tersuntik lagi kini dijaring `checkHealth()` lalu worker dimulai ulang.

**Sesi yang tersangkut `authenticating` tidak pulih sendiri, dan itu pernah membuat sistem mati 14 jam.** Pemeriksaan kesehatan yang lama berhenti lebih dulu (`if (!isWaReady()) return`): ia hanya menjaga sesi yang SUDAH siap dari Chromium yang menggantung, bukan sesi yang tidak pernah sampai siap. Sementara itu poller tetap berputar, PM2 melaporkan `online`, dan tidak satu pun pesan bisa terkirim maupun diterima. Dashboard memang menandainya (`SystemStatus` di `/ringkasan` menampilkan panel peringatan + "Perbaiki sekarang"), tapi itu mengandalkan ada orang yang membukanya -- kejadiannya jam 01:25 dini hari dan baru ketahuan 14 jam kemudian. Sekarang `sessionWatchdog()` (`worker/index.ts`) keluar bila sesi berada di luar `ready` lebih dari **15 menit**, dan PM2 menyalakan ulang. Tiga hal yang menempel padanya:

- **`qr_pending` sengaja dikecualikan**: itu bukan macet melainkan sistem yang benar sedang menunggu manusia memindai QR (bisa berjam-jam saat pemasangan pertama), dan restart di tengahnya justru menerbitkan QR baru sehingga kode yang sedang dipindai petugas jadi kedaluwarsa.
- **15 menit, bukan 5, dan itu bukan kehati-hatian melainkan pengamatan**: penautan ulang yang terlalu sering tampaknya membuat WhatsApp memperlambat sinkronisasi. Satu start setelah jeda panjang mencapai `ready` dalam 5 detik; empat start beruntun sesudahnya semuanya tersangkut. Watchdog yang menyala tiap 5 menit akan menjadi sumber masalahnya sendiri alih-alih pemulihannya.
- **Keluarnya WAJIB lewat `shutdown()`, bukan `process.exit()` langsung.** Ini sempat salah pada versi pertama watchdog-nya: keluar tanpa menutup Chromium meninggalkan state sesi setengah tertulis, sehingga proses penggantinya menggantung di `authenticating` -- pemulihan yang justru menciptakan kegagalan berikutnya. `shutdown()` juga memberi `destroy()` batas waktunya sendiri (15 detik), karena sebagian pemanggilnya keluar JUSTRU karena Chromium menggantung, dan `destroy()` pada Chromium yang menggantung bisa ikut menggantung selamanya.

**DUA `pm2 restart` berdekatan bisa menjatuhkan worker ke crash loop, dan `pm2 stop` TIDAK cukup untuk keluar darinya.** Terjadi sungguhan: worker di-restart dua kali dalam satu jam (perubahan kode, lalu perbaikan atas perubahan itu), dan sesudah yang kedua ia gagal start berulang dengan `{"msg":"worker gagal memulai","message":"Protocol error (Runtime.callFunctionOn): Target closed"}` -- 29 restart beruntun, ditambah baris `ERROR: The process with PID ... could not be terminated`. Bedanya dari ketiga mode kegagalan sesi di atas: bukan sesi yang tersangkut `authenticating`, bukan `window.WWebJS` yang hilang, dan bukan dua instance yang berebut (`singleInstance.ts` bekerja normal) -- melainkan **Chromium yatim yang selamat dari matinya proses induk** dan tetap memegang direktori sesi, sehingga tiap proses baru mati sebelum sempat apa pun.

Yang paling menyesatkan: `wa_session.status` tetap `ready` sepanjang gangguan, karena baris itu ditulis proses yang SUDAH mati dan tidak ada yang membatalkannya. Yang membocorkannya adalah **`heartbeat_at` yang basi** -- 195 detik pada loop yang seharusnya 30 detik. Jadi saat memeriksa kesehatan sesudah restart, `status` saja tidak cukup; yang menjawab "apakah ada proses yang hidup sekarang" hanya umur heartbeat-nya.

Pemulihannya tiga langkah, dan urutannya mengikat:

1. `pm2 stop wakhanza-worker` -- menghentikan loop-nya dulu, kalau tidak proses baru terus lahir di tengah pembersihan.
2. Matikan **hanya** Chromium yang memegang direktori sesi, disaring lewat baris perintahnya: `Get-CimInstance Win32_Process -Filter "Name='chrome.exe'" | Where-Object { $_.CommandLine -like "*wwebjs_auth*" }`. Penyaring itu bukan kerapian -- di mesin ini ada 14 proses `chrome.exe` lain milik pemakai, dan `Stop-Process -Name chrome` akan menutup peramban orang di tengah kerja.
3. `pm2 start wakhanza-worker`, lalu tunggu heartbeat kembali di bawah 40 detik.

Pelajaran yang menempel: **jangan menyalakan ulang worker dua kali berdekatan.** Kalau ada perubahan susulan, kumpulkan dulu lalu restart sekali -- biayanya menunggu beberapa menit, sementara biaya yang satunya adalah sistem notifikasi mati sampai ada yang menyadarinya.

`scripts/backup.ps1` + `scripts/restore-backup.ps1` untuk cadangan terenkripsi AES-256 database + sesi WhatsApp — **sudah diuji langsung** (dekripsi, ekstraksi, dan restore sungguhan ke database uji), dan sejak `scripts/install-backup-task.ps1` ada, **benar-benar terjadwal** alih-alih menunggu seseorang ingat menjalankannya (§ berikutnya).

### Cadangan harian: dijadwalkan sebagai SYSTEM, dan satu jebakan stderr

Skrip cadangannya sudah ada sejak Fase 4 tapi **tidak pernah dijadwalkan** — direktori `backups\` bahkan belum pernah terbentuk. Yang hilang bila disk mati bukan cuma riwayat: `opt_out` adalah catatan permintaan berhenti dari pasien dan tidak bisa direkonstruksi dari mana pun, `audit_log` sengaja append-only, dan `.wwebjs_auth` yang lenyap berarti scan QR ulang dengan akses fisik ke ponsel nomor RS.

`install-backup-task.ps1` mendaftarkannya ke Task Scheduler, harian pukul 01:00 (sesudah lalu lintas pasien reda, dan **sebelum** pembersihan berkala worker jam 02:00 — jadi cadangan hari itu masih memuat baris yang beberapa jam kemudian dipangkas). Berjalan sebagai **SYSTEM**: tidak perlu menyimpan password akun di Task Scheduler, tetap jalan saat tidak ada yang login, dan `.env`/`.wwebjs_auth` memang sudah memberi akses ke SYSTEM lewat `harden:permissions`. `mysqldump` wajib ada di PATH tingkat **MESIN** — SYSTEM tidak membaca PATH milik user — dan skrip pemasangnya memeriksa itu di muka supaya kegagalannya tidak baru muncul jam 01:00.

**Frasa sandinya dibaca dari `.env`.** Task Scheduler tidak punya sesi interaktif, jadi tidak ada tempat mengetiknya; `.env` sudah jadi tempat rahasia lain, gitignored, dan terkunci ke akun saat ini + SYSTEM. Konsekuensi yang harus disadari dan **tidak bisa diselesaikan kode**: menyimpan frasa itu HANYA di `.env` berarti disk mati menghapus cadangan beserta kuncinya sekaligus. Catat di luar mesin.

**Jebakan yang membuat percobaan pertama gagal, dan bentuknya persis seperti `trustHost`:** `mysqldump` MariaDB 10.4 menulis satu peringatan tak berbahaya ke stderr tiap kali jalan (`option 'max_allowed_packet': ... adjusted to ...`). PowerShell 5.1 membungkus tiap baris stderr proses native jadi `ErrorRecord`, dan dengan `$ErrorActionPreference='Stop'` itu MENGHENTIKAN skrip walau kode keluar mysqldump 0 dan dump-nya berhasil. Dijalankan manual dari shell, peringatannya lewat begitu saja dan cadangan terbentuk normal; dijalankan Task Scheduler, skripnya mati di langkah 1 dan **tidak ada berkas cadangan yang terbentuk sama sekali** — setiap hari, jam 01:00, tanpa seorang pun melihat. Sekarang berhasil/gagal ditentukan **kode keluar mysqldump plus ukuran berkas hasilnya**, bukan ada-tidaknya tulisan di stderr. Sekali lagi pelajaran yang sama: verifikasi lewat jalur yang benar-benar dipakai produksi, bukan lewat cara yang paling gampang dijalankan dengan tangan.

Cadangan lama dipangkas sendiri (`-KeepDays`, default 30) **sesudah** cadangan baru berhasil ditulis, tidak pernah sebelumnya — kalau dump gagal, skrip sudah berhenti di atas dan tidak ada cadangan lama yang telanjur hilang. Tanpa pemangkasan, direktori cadangan tumbuh sampai disk penuh, dan disk penuh menghentikan MariaDB — justru bencana yang cadangan ini ada untuk menghadapinya.

## Arsitektur inti

### Dua koneksi database, dua tingkat kepercayaan
`src/db/sik.ts` memakai user MySQL `wakhanza_ro` — `GRANT SELECT` saja, `pool.max: 2` supaya tidak berebut koneksi dengan SIMRS yang sedang dipakai petugas. `src/db/wakhanza.ts` memakai `wakhanza_rw`. Pemisahan ditegakkan hak akses database, bukan disiplin kode: worker **wajib** mencoba `CREATE TEMPORARY TABLE` di `sik` saat mulai dan berhenti jalan bila berhasil (`src/db/guards.ts`, ARCHITECTURE §9.1). `sequelize.sync()` tidak boleh pernah dipanggil — skema `wakhanza` lewat migrasi SQL bernomor (`migrations/NNN_*.sql`) dijalankan `npm run migrate`.

**`wakhanza_rw` BUKAN `GRANT ALL PRIVILEGES`.** Rencana awal ternyata punya bug nyata (ditemukan & diperbaiki saat implementasi, ARCHITECTURE §9.5): MariaDB menyatukan hak akses lintas tingkatan, jadi `REVOKE DELETE, UPDATE ON audit_log` di atas fondasi `GRANT ALL` tidak menegakkan apa pun. Model yang benar: tanpa `UPDATE`/`DELETE` di tingkat database, diberikan satu per satu di tingkat tabel, `audit_log` dikecualikan selamanya. Diverifikasi ulang lewat `npm run verify:db`.

Dua gotcha koneksi:
- Koneksi `sik` wajib `dialectOptions: { dateStrings: true }`. `resep_obat.tgl_penyerahan` memakai `'0000-00-00'` sebagai penanda "belum diserahkan"; tanpa `dateStrings`, mysql2 mengubahnya jadi `Invalid Date`/`null` secara diam-diam (ARCHITECTURE §4.6, `src/khanza/farmasi.ts`).
- MariaDB di sini adalah **10.4, bukan MySQL 8** — tanpa CTE rekursif yang baik, tanpa `JSON_TABLE`, window function terbatas.

### Next.js 16, bukan 14 -- dan `proxy.ts`, bukan `middleware.ts`
TECH_STACK.md awalnya menetapkan Next.js 14/NextAuth v4; keduanya dinaikkan ke Next 16/NextAuth v5 (beta) saat implementasi karena Next 14 punya kerentanan tinggi tanpa patch lanjutan (detail di TECH_STACK.md "Penyesuaian Implementasi"). Konsekuensi konkret bagi siapa pun yang menyentuh `src/app/`: `params`/`searchParams`/`cookies()`/`headers()` bersifat `Promise` (async), dan gerbang autentikasi tingkat-request bernama **`src/proxy.ts`** (Next 16 mengganti nama dari `middleware.ts` -- fungsinya sama). Auth.js v5 dipecah dua berkas: `src/auth.config.ts` (tanpa provider, aman untuk Edge Runtime tempat `proxy.ts` berjalan) dan `src/auth.ts` (provider Credentials penuh + Sequelize/bcrypt, HANYA dipakai route handler/Server Component/Server Action). Jangan import `@/auth` dari `proxy.ts` -- Edge Runtime tidak mendukung Sequelize.

**`trustHost: true` di `auth.config.ts` WAJIB, dan sempat luput.** Auth.js v5 hanya memercayai Host header secara otomatis saat `next dev`. Pada build produksi -- persis yang dijalankan PM2 lewat `ecosystem.config.js` -- tanpa baris itu SETIAP permintaan ke `/api/auth/*` ditolak `UntrustedHost` dan dijawab HTTP 500, sehingga tidak seorang pun bisa masuk. Perbedaan dev/produksi ini tidak pernah muncul selama pengujian memakai `npm run dev`; ia baru ketahuan saat dashboard diuji lewat `npm start`. **Verifikasi HTTP apa pun yang menyangkut login harus lewat `npm run build && npm start`, bukan `npm run dev`** -- dev server memaafkan justru kelas kesalahan yang mematikan di produksi. Aman di sini karena topologinya tetap: satu server RS, prosesnya diikat ke 127.0.0.1 (`next start -H 127.0.0.1`), tidak melayani banyak host.

Otorisasi API ditegakkan DUA lapis dan keduanya perlu diperiksa saat menambah route baru: `proxy.ts` hanya menjaga HALAMAN (redirect ke `/login`); setiap route di `src/app/api/**/route.ts` memanggil `requireSession()`/`requireRole('admin')` dari `src/lib/authz.ts` sendiri dan mengembalikan 401/403 JSON. `/api/*` sengaja dikecualikan dari matcher `proxy.ts` -- kalau tidak, pemanggil API menerima redirect HTML alih-alih JSON.

### Topologi dua proses, koordinasi lewat tabel
`wakhanza-worker` (PM2, **wajib** `instances: 1, exec_mode: 'fork'`, tidak boleh `cluster` -- lihat `ecosystem.config.js`) memegang sesi whatsapp-web.js dan menjalankan poller + dispatcher + scheduler. `wakhanza-web` (Next.js) tidak memegang state sesi. Kedua proses **tidak pernah** berkomunikasi lewat HTTP — semua lewat tabel `wakhanza` (`wa_session` untuk QR/status/perintah lewat `src/worker/sessionCommand.ts`, `outbox` untuk status pesan), dengan konsekuensi tindakan petugas di dashboard tertunda hingga satu siklus (§1).

### Pipeline bersama: `src/worker/pipeline.ts` dan `src/worker/sisipCycle.ts`
`POLL → COALESCE → RESOLVE nomor → NORMALIZE → GATE (opt-out/invalid/nonaktif) → PRIVACY → RENDER → ENQUEUE` (langkah [3]-[8] ada di `pipeline.ts`'s `enqueueMessage()`, dipakai SEMUA pemicu -- jangan duplikasi logika ini saat menambah pemicu baru). Pemicu kelas sisip (QUEUE_REG, RESULT_READY, PHARMACY_READY, BILLING_READY) berbagi `runSisipCycle()` generik di `sisipCycle.ts`, dibedakan lewat parameter fetch/mapping per pemicu di `src/worker/poller*.ts`. `DISPATCH → SEND → LOG` (`dispatcher.ts`) mengambil dari `outbox` dengan `FOR UPDATE SKIP LOCKED`, terpisah total dari langkah enqueue -- kegagalan kirim tidak pernah menghapus jejak bahwa pemicunya terdeteksi.

**Kode unik per pesan disisipkan di langkah RENDER, bukan SEND.** `core/uniqueCode.ts` menambahkan satu baris pendek (`Kode Pengiriman : 2026-08-02 20:18:41 5QVC9G`, default `dispatch.unique_code_template` = `Kode Pengiriman : {waktu} {kode}`) ke SETIAP pesan keluar, termasuk BROADCAST -- karena laju rendah (jeda acak 3-8 detik + kuota per jam, PRD F5.2) hanya menangani separuh pemicu deteksi spam WhatsApp; separuh lainnya adalah banyak pesan berteks IDENTIK, dan template tetap membuat puluhan pesan sehari nyaris sama. Dua keputusan yang menempel di sini dan gampang dirusak tanpa sadar:

- **Diturunkan dari `idempotency_key`, bukan acak.** Dispatcher mencoba ulang sampai beberapa kali (`core/retry.ts`); kode acak akan membuat percobaan kedua tampak sebagai pesan BARU bagi pasien maupun bagi WhatsApp -- persis kebalikan dari tujuannya.
- **`{waktu}` saja TIDAK cukup, dan `{kode}` bukan hiasan di sampingnya.** Satu broadcast meng-enqueue seluruh penerimanya dalam perulangan rapat, jadi ratusan pesan mendapat detik yang SAMA; digabung dengan isi broadcast yang memang identik, seluruh kiriman jadi identik karakter per karakter -- persis pola yang fitur ini ada untuk mencegahnya. Karena itu `{kode}` tetap ditempelkan walau admin menghapusnya dari template; `{waktu}` tidak diperlakukan begitu karena ia tidak menjamin apa pun.
- **`{waktu}` diisi `scheduled_at`, bukan waktu enqueue.** Pesan yang muncul pukul 22.00 lalu ditahan jam tenang sampai 07.00 harus menyebut 07.00 -- kalau tidak, pasien membaca stempel sembilan jam sebelum pesannya tiba. Karena itu `computeScheduledAt()` dipanggil SEBELUM body dirender di `enqueueMessage()`.
- **Disisipkan saat ENQUEUE (`pipeline.ts`), bukan saat SEND (`dispatcher.ts`).** Menyisipkannya di dispatcher akan membuat `outbox.body` berbeda dari yang benar-benar terkirim -- halaman Log berhenti menunjukkan teks sungguhan, dan kode yang disebut pasien lewat telepon tidak bisa lagi dicari (`outbox.body LIKE '%KODE%'`, satu-satunya cara -- kodenya sengaja TIDAK disimpan di kolom terpisah).

Substitusi footer-nya SENGAJA terpisah dari `renderTemplate()`: menggabungkan footer ke body lalu merender ulang sekali lagi akan melanggar aturan satu-lintasan (§ substitusi template di bawah). Alfabetnya Crockford Base32 -- tepat 32 karakter (tanpa bias modulo) dan tanpa I/L/O/U supaya tidak tertukar saat dibacakan lewat telepon. Kalau admin menghapus `{kode}` dari templatenya, kodenya TETAP ditempelkan di akhir (`buildUniqueCodeFooter`) -- tanpa itu seluruh pesan berakhiran teks identik dan fitur ini mati diam-diam tanpa satu pun pesan error.

Pratinjau `/broadcast`, `/broadcast-terjadwal`, dan `npm run poll:dryrun` semuanya membaca pengaturannya lewat `loadUniqueCodeTemplate()`/`previewUniqueCodeFooter()` yang SAMA dipakai `enqueueMessage()` -- pratinjau tidak boleh menampilkan bentuk pesan yang berbeda dari yang benar-benar terkirim.

**Uji integrasi pipeline (`worker/pipeline.int.test.ts`, `npm run test:int`).** Sampai berkas ini ada, seluruh suite uji proyek ini menguji `src/core/` saja -- fungsi murni yang tidak menyentuh database. Bagian yang MENGGABUNGKAN semuanya, dan satu-satunya jalur yang dilewati keempat kelas pemicu, hanya pernah divalidasi manual satu per satu setiap kali ada yang berubah. Tiga hal yang menempel padanya:

- **Config terpisah** (`jest.integration.config.js`, berkas `*.int.test.ts`, dikecualikan dari `jest.config.js`). `npx jest` harus tetap bisa dijalankan di mana saja tanpa database dan selesai dalam hitungan detik -- begitu ia butuh MariaDB hidup, ia berhenti dipakai sebagai pemeriksaan cepat. `maxWorkers: 1` karena beberapa uji sengaja mengubah pengaturan bersama.
- **Menulis ke database `wakhanza` SUNGGUHAN**, bukan database uji hasil `sync()`. Yang perlu dibuktikan justru perilaku terhadap skema, grant, dan UNIQUE KEY yang benar-benar berlaku -- dan `sequelize.sync()` memang tidak pernah dipanggil di proyek ini. Baris ujinya ditandai pada `idempotency_key` dan dibersihkan di `afterAll`.
- **`.env` harus dimuat lewat `setupFiles`, dan sebabnya halus.** `process.loadEnvFile()` adalah fungsi native yang menulis ke `process.env` milik proses SUNGGUHAN, sementara berkas uji berjalan di sandbox VM yang memegang salinannya sendiri: pemuatannya "berhasil" tanpa galat, lalu `WA_DB_HOST` tetap undefined. Karena itu setup-nya membaca `.env` dan menulis nilainya satu per satu.

**Dan uji ini langsung menemukan satu perangkap**: `PipelineContext.identity` ada tapi `enqueueMessage()` tidak pernah membacanya -- kelima pemanggil kebetulan menyisipkan `identityVars()` sendiri ke `vars`, jadi kebenarannya bergantung pada kelimanya mengingat itu. Yang membuatnya berbahaya bukan pemicunya melainkan **template generik**: isinya ditulis admin di halaman Pengaturan dan memang memuat `{nama_rs}`/`{kontak_rs}`, sementara ia menggantikan pesan untuk jalur privasi mana pun -- termasuk pemicu baru yang penulisnya tidak tahu kewajiban itu. Pesannya akan berbunyi "ada informasi dari ." tanpa satu pun galat. Sekarang `enqueueMessage()` menyisipkannya sendiri sebagai dasar dan `input.vars` tetap menimpa, jadi pemanggil lama menghasilkan pesan yang sama persis.

RESULT_READY punya DUA watermark terpisah (`RESULT_READY_LAB`, `RESULT_READY_RADIOLOGI` di `poll_cursor`) walau satu `trigger_code` -- mencampur watermark dua sumber independen bisa membuat salah satunya melompati baris yang belum diproses.

### Status `outbox`: terminal vs aktif, dan tiga kebocoran yang lahir dari selisih tafsir

`core/outboxStatus.ts` memegang daftar status sekaligus pembagiannya. Ia dibuat karena tiga tempat yang berjauhan -- dispatcher (memilih yang dikerjakan), cleanup (memangkas yang selesai), Ringkasan (menampilkan yang menunggu orang) -- masing-masing menafsirkan sendiri "baris ini masih akan bergerak atau tidak", dan ketiganya ternyata tidak sepakat. Akibatnya persis kelas kegagalan termahal di proyek ini: baris yang tidak dikerjakan siapa pun, tidak ditampilkan di mana pun, dan tidak pernah dihapus. **Aktif hanya `pending` dan `sending`**; sisanya terminal. Tidak ada status "gagal tapi nanti dicoba lagi" -- percobaan ulang bekerja dengan mengembalikan baris ke `pending` berikut `scheduled_at` mundur, bukan lewat status tersendiri. Uji `outboxStatus.test.ts` menjaga kedua golongan itu MEMBAGI HABIS ENUM-nya, supaya status baru memaksa keputusannya diambil sadar-sadar alih-alih diam di celah.

Tiga hal yang diperbaiki bersamaan, dan ketiganya bergejala sama: tidak ada pesan error di mana pun.

- **Pemangkasan dulu hanya `status='sent' AND sent_at < cutoff`.** Setiap baris yang TIDAK pernah terkirim punya `sent_at` NULL, jadi `skipped_no_contact`/`skipped_opt_out`/`failed`/`failed_permanent`/`expired` menetap selamanya di tabel yang paling cepat tumbuh -- dan justru itu yang paling banyak: satu broadcast ke 500 pasien di RS yang ~40% nomornya tidak terpakai meninggalkan ~200 baris abadi sekali kirim. Sekarang memangkas seluruh status terminal menurut `created_at`. **Akibat lanjutannya**: baris `skipped_*` ikut menyimpan `media_path`, sementara `cleanupOrphanMedia()` hanya menghapus berkas yang tak ditunjuk baris mana pun -- selama baris abadi itu ada, lampiran broadcast **tidak pernah bisa dihapus dari disk**. Memperbaiki pemangkasan barisnya sekaligus memperbaiki yang ini; keduanya tidak bisa dipisah.
- **Percobaan-habis dulu ditulis `failed`, bukan `failed_permanent`.** `NEEDS_REVIEW` di `ringkasan/queries.ts` cuma memuat `failed_permanent` dan `expired`, dan label `failed` berbunyi "masih akan dicoba ulang otomatis" padahal dispatcher hanya mengambil `pending`. Jadi notifikasi pasien yang gagal tiga kali berturut-turut berhenti diam-diam: tidak dicoba ulang, tidak tampil di panel mana pun, tidak ada yang tahu. `failed` tetap ada di ENUM demi baris peninggalan dan **ikut dimasukkan ke `NEEDS_REVIEW`** -- baris lama yang selama ini tak terlihat harus muncul ke permukaan, bukan ikut terkubur oleh perbaikannya.
- **Baris tersangkut `sending` tidak pernah pulih.** `sending` ditulis di dalam transaksi tepat sebelum kirim; kalau worker mati di antaranya (SIGKILL setelah `kill_timeout`, listrik padam), barisnya tinggal di sana selamanya. `recoverInterruptedSends()` dijalankan di startup SEBELUM dispatcher menyala. **Sengaja TIDAK dikembalikan ke `pending`**: kegagalannya terjadi di satu-satunya titik yang hasilnya tidak bisa kita ketahui -- pesannya mungkin sudah sampai ke WhatsApp sebelum prosesnya mati -- jadi kirim ulang otomatis berarti sebagian pasien menerima pesan sama dua kali tanpa ada yang memutuskan. Ditandai `failed_permanent` supaya muncul berikut tombol Kirim ulang. Aman di startup karena worker dijamin instance tunggal (`instances: 1, exec_mode: 'fork'`).

### Kendala indeks yang membentuk setiap query poller
Kolom tanggal Khanza yang tampak wajar (`tgl_registrasi`, `tgl_periksa`, dst.) **tidak terindeks**. Solusinya: tanggal sudah ter-enkode di primary key, jadi tiap query poller wajib dua penyaring sekaligus:
```sql
WHERE no_rawat >= :lookback_prefix              -- pemangkas lewat indeks (PK)
  AND TIMESTAMP(tgl_periksa, jam) >= :cursor_ts  -- ketepatan
```
Setiap query poller wajib menunjukkan `range`/`eq_ref`/`index`, tidak pernah `type: ALL` pada tabel dasar — ditegakkan `npm run verify:plans`. Pengecualian satu-satunya yang disengaja: `booking_registrasi` (kelas pindai, interval 5 menit bukan 60 detik). `scripts/verify-plans.ts` juga mengecualikan hasil scan terhadap **tabel turunan/subquery** (`<derived2>` dsb.) dari pemeriksaan full-scan -- itu hasil yang sudah tersaring, bukan tabel dasar. Baca ARCHITECTURE §4.4 sebelum menyentuh query poller mana pun.

### Dua kelas pemicu: sisip vs pindai
`QUEUE_REG`, `RESULT_READY`, `PHARMACY_READY`, `BILLING_READY`, `BOOK_CONFIRM` = kelas **sisip** (watermark). `BOOK_CANCEL`, `BOOK_REMIND` = kelas **pindai** (`src/worker/pollerBooking.ts`, `scheduler.ts` -- scan ulang jendela terbatas; dedup murni lewat kunci idempoten yang menyertakan `status`). `BOOK_CONFIRM` dan `BOOK_CANCEL` berbagi SATU query (`khanza/booking.ts`'s `pollUpcomingBookings()`) dan SATU siklus (`pollerBooking.ts`), dibedakan lewat status baris dan idempotency key masing-masing -- bukan dua query terpisah. `event_at` untuk keduanya memakai waktu DETEKSI (sekarang), bukan `tanggal_booking` -- lihat komentar di `pollerBooking.ts` untuk kenapa memakai timestamp booking asli akan salah membuat konfirmasi jangka panjang tampak basi.

### Kelas ketiga: BROADCAST (dipicu staf, bukan sik)

`/broadcast` menambah kelas pemicu ketiga di luar sisip/pindai: **staf-inisiasi**. Tidak ada polling `sik` sama sekali -- staf memfilter `khanza/pasienSegment.ts`'s `fetchPatientSegment()` (join `reg_periksa`+`pasien`+`penjab`+`kabupaten`/`kecamatan`/`kelurahan`, satu baris per pasien lewat `MAX(no_rawat)`, dipangkas prefix `no_rawat` yang sama seperti pemicu lain) lalu mengetik pesan bebas. Keputusan desain kunci: **enqueue-nya memakai `enqueueMessage()` yang SAMA PERSIS** dengan ketujuh pemicu lain (`loadBroadcastContext()` cuma sumber `template.body`-nya beda -- teks staf, bukan `Template.findByPk()`), jadi privasi (`checkPrivacy`, fallback ke `privacy.generic_template`), opt-out, jam tenang, dan idempotency (`buildIdempotencyKey('BROADCAST', campaignId, no_rkm_medis)`) otomatis identik tanpa logika baru. Dashboard HANYA menulis baris `outbox` -- pengiriman tetap tugas dispatcher worker, konsisten dengan "kedua proses tidak pernah lewat HTTP".

**Lampiran gambar/dokumen HANYA di `/broadcast` manual** (`core/media.ts` + `lib/mediaStorage.ts`, `migrations/014`). Broadcast terjadwal, ketujuh pemicu, dan balasan otomatis tetap teks — ketiganya mengirim tanpa ada manusia yang meninjau tiap kali. Lima hal yang menempel:

- **Berkasnya di luar `public/`.** Apa pun di bawah `public/` dilayani Next.js tanpa autentikasi, jadi setiap surat edaran RS akan bisa diunduh siapa saja yang menebak namanya. Disimpan di `uploads/broadcast/` (gitignored).
- **Yang disimpan di `outbox` cuma LINTASANNYA, bukan isinya.** Satu broadcast ke 500 pasien menghasilkan 500 baris yang menunjuk SATU berkas — blob per baris akan menggandakan poster 5 MB sebanyak 500 kali di tabel yang paling cepat tumbuh.
- **Nama berkas simpanan tidak pernah diturunkan dari nama unggahan** (`namaBerkasSimpanan`): ekstensinya dari MIME yang sudah lolos daftar-izin, sisanya acak. `resolveMediaPath()` menolak apa pun yang keluar dari direktori media — nilainya pulang-pergi lewat database, dan itulah yang memastikan satu baris yang disunting lewat SQL tidak bisa membuat worker mengirim `.env` ke pasien.
- **Batas keterangan 1024 karakter, dan hanya berlaku saat ADA lampiran.** Pesan teks biasa boleh panjang; begitu ada lampiran, isi pesan menjadi *caption* dan tunduk pada batas yang jauh lebih pendek. Diperiksa saat menyusun (berikut panjang baris kode pengiriman, yang ikut memakan jatah), bukan saat kirim.
- **Pembersihan berkas per-BERKAS, bukan per-baris** (`cleanup.ts`): dihapus hanya setelah tidak ada baris `outbox` yang menunjuknya. Menghapus saat baris pertama terpangkas membuat kiriman ke pasien ke-2 sampai ke-500 gagal karena berkasnya lenyap di tengah jalan. `broadcast_campaign` sengaja tidak jadi acuan — ia insert-only dan tidak pernah dipangkas, jadi catatan nama berkasnya tetap utuh sebagai jejak akuntabilitas walau berkasnya sudah tidak ada.

**Rentang tanggal OPSIONAL, dan mengosongkannya mengubah BENTUK query-nya** (`core/segmentScope.ts`). Rentang yang selalu terisi benar untuk pemakaian aslinya ("kirim ke pasien yang berkunjung belakangan ini") tapi salah untuk mencari SATU pasien lewat nama/no. RM: pasien yang terakhir datang delapan bulan lalu tidak muncul, dan yang terlihat cuma "tidak ada pasien yang cocok" -- persis seperti kalau namanya salah ketik. Lima hal yang menempel:

- **Menghapus kondisi tanggalnya saja SALAH, dan ini bagian terpentingnya.** Prefix `no_rawat` itulah satu-satunya yang membuat query segmen tidak memindai seluruh `reg_periksa` (§4.4). Karena itu ada DUA bentuk query, bukan satu bentuk dengan kondisi opsional: `buildWindowedSql()` berangkat dari `reg_periksa`, `buildAllTimeSql()` berangkat dari `pasien` lalu masuk ke `reg_periksa` lewat indeks `no_rkm_medis`. Keduanya di-EXPLAIN terpisah (`BROADCAST_SEGMENT`, `BROADCAST_SEGMENT_SEMUA`, `BROADCAST_SEGMENT_SEMUA_PJ`).
- **Tidak semua filter setara, dan pembedaannya mengikuti bentuk query -- bukan selera.** Bentuk semua-waktu berangkat dari `pasien`, jadi yang bisa mempersempitnya hanya filter yang melekat pada PASIEN: pencarian nama/no. RM/no. pendaftaran, dan wilayah. Cara bayar melekat pada KUNJUNGAN; tanpa tanggal, "semua pasien BPJS sejak kapan pun" praktis seluruh tabel -- dengan cara bayar sebagai satu-satunya filter, optimizer membalik arah join dan membaca separuh `reg_periksa`. Karena itu cara bayar (dan batas ATAS tanggal) tidak cukup untuk membuka mode semua-waktu; keduanya tetap boleh MENDAMPINGI penyaring pasien.
- **Tanpa tanggal DAN tanpa penyaring pasien = ditolak sebelum satu baris pun dibaca.** `broadcast.max_recipients` sudah menolak segmen kelewat besar, tapi SESUDAH staf menyusun pesan dan menekan Kirim. Yang lebih buruk dari besarnya: hasilnya dipotong `LIMIT`, jadi yang terpilih adalah sekian ratus pasien yang kebetulan terurut paling akhir -- angka yang terlihat pasti padahal isinya kebetulan.
- **No. pendaftaran diterjemahkan dulu jadi no. RM** (`resolveNoRawatKeRm`, satu lookup primary key) alih-alih ikut jadi `OR lv.no_rawat = ...` seperti di bentuk berjendela. OR yang merentang dua tabel membatalkan join lewat indeks dan mengembalikan query ke pemindaian penuh. Ketiga cara cari tetap bekerja di kedua mode; salah satunya diam-diam mati tergantung terisi-tidaknya tanggal justru inkonsistensi yang paling membingungkan.
- **`pasien` boleh dipindai penuh di bentuk ini, dan alasannya BERBEDA dari dua izin lain.** `booking_registrasi` boleh karena kelas pemicunya memang pindai; `dokter` boleh karena tabel konfigurasi yang tidak tumbuh seiring jumlah pasien. `pasien` jelas tumbuh -- tapi satu baris per PASIEN, bukan per kunjungan, dan query ini jalan sekali tiap staf menekan Terapkan, bukan berulang di latar. Dengan pencarian nama saja MariaDB memakai `nm_pasien` sebagai covering index; ia jatuh ke pemindaian penuh begitu wilayah ikut dipilih, karena kesetaraan `kd_kab` dan `LIKE '%..%'` tidak bisa dilayani satu indeks yang sama.

Rentang tanggal yang mati juga harus TERLIHAT mati: kotak tanggal kosong gampang terbaca sebagai "belum diisi" alih-alih "sengaja tanpa batas". Halaman menampilkan keterangan cakupan, dan **angka "Cocok" yang menyentuh `SEGMENT_LIMIT` diberi peringatan terpotong** -- tepat pada angka itu ia berubah arti dari "jumlah yang cocok" menjadi "jumlah yang sempat terbaca", dan diam di situ membuat segmen terpotong terlihat persis seperti segmen utuh. `broadcast_campaign.filter_json` menyimpan `null` (bukan tanggal karangan) supaya jejak auditnya bisa membedakan keduanya. **Broadcast TERJADWAL sengaja tidak ikut** -- jendelanya relatif dan dihitung ulang tiap kali jalan (`resolveScheduleWindow`), dan "semua waktu" yang berulang otomatis adalah persis pola yang §"Yang masih perlu keputusan rumah sakit" memperingatkan.

Dua pagar yang tidak dipunyai pemicu lain: `broadcast.max_recipients` (app_setting, default 500) menolak kirim sebelum enqueue bila segmen kelewat besar (filter yang salah tidak boleh langsung jadi ribuan pesan), dan `broadcast_campaign` (insert-only, `outbox.campaign_id` menautkan balik) adalah jejak akuntabilitas siapa mengirim apa ke berapa orang kapan -- jumlah terkirim/gagal DIHITUNG LANGSUNG dari `outbox WHERE campaign_id=x` saat dibaca, tidak pernah disimpan sebagai penghitung yang bisa basi. Variabel template dibatasi `BROADCAST_TEMPLATE_VARIABLES` (`core/template.ts`) ke `nama_pasien`/`no_rm`/`nama_rs`/`alamat_rs`/`kontak_rs` saja -- `{nama_poli}`/`{jam}`/dst tidak well-defined untuk segmen yang bisa merentang banyak kunjungan.

### Kelas ketiga, varian: BROADCAST TERJADWAL (worker-inisiasi, bukan staf-inisiasi)

`/broadcast-terjadwal` (`src/app/(dashboard)/broadcast-terjadwal/`) membangun DI ATAS BROADCAST, bukan menggantikannya -- staf menyimpan DEFINISI (segmen + pesan + pola pengulangan) ke tabel `broadcast_schedule`, lalu **worker** (`worker/broadcastScheduleRunner.ts`'s `runDueBroadcastSchedules()`, dipanggil tiap `polling.scan_interval_ms` dari `worker/index.ts`, siklus terpisah bernama `broadcast-schedule`) yang benar-benar mengeksekusi saat `next_run_at` jatuh tempo -- bukan staf mengklik kirim. Sekali eksekusi memakai rantai fungsi produksi yang SAMA PERSIS dengan kirim manual (`fetchPatientSegment` → `loadBroadcastContext` → `enqueueMessage`), plus membuat SATU baris `broadcast_campaign` baru per kali jalan (jejak akuntabilitas per-jalan, `created_by` diisi `system:broadcast_schedule:<id jadwal>` supaya beda dari username staf sungguhan).

**Rentang tanggal RELATIF, bukan tetap.** `broadcast_schedule.filter_json` menyimpan `lookbackDays`/`offsetDays` (mis. "30 hari terakhir"), BUKAN `dateFrom`/`dateTo` absolut seperti `broadcast_campaign.filter_json` -- `khanza/broadcastSchedule.ts`'s `scheduleFiltersToSegment()` menghitung ulang jendela tanggal dari SEKARANG setiap kali dipanggil (matematikanya di `core/schedule.ts`'s `resolveScheduleWindow()`, diuji unit). Jadwal mingguan yang dibuat hari ini harus tetap masuk akal empat minggu lagi; tanggal beku akan membuatnya makin tidak relevan tiap kali jalan.

**DUA mode jendela, dan bedanya menentukan berapa kali satu pasien dikirimi** (`core/schedule.ts`'s `ScheduleWindowMode`):

- **`rolling`** -- jendela berjalan `lookbackDays` terakhir sampai hari ini. Pasien yang sama tetap masuk kriteria selama masih di dalam jendela, jadi jadwal HARIAN dengan lookback 30 hari mengirim ke orang yang sama **30 kali**. Ini perilaku asli (dan satu-satunya) sebelum mode kedua ada, jadi baris `broadcast_schedule` lama yang `filter_json`-nya tidak punya `windowMode` dibaca sebagai `rolling` -- perilakunya tidak berubah. Masuk akal untuk pengumuman berkala, berbahaya untuk yang lain; `ScheduleForm` menampilkan peringatan kuning saat mode ini dipasangkan dengan pengulangan.
- **`followup`** -- TEPAT satu hari kalender, `offsetDays` hari yang lalu (`dateFrom == dateTo`; `fetchPatientSegment` memangkas lewat prefix `no_rawat` `[hari, hari+1)`, jadi itu satu hari penuh, bukan jendela kosong). Dipasangkan dengan pengulangan harian, tiap pasien melewatinya persis SEKALI -- inilah bentuk "pasien yang daftar hari ini, dikirimi 3 hari lagi".

**Kunci idempoten berbeda per mode, dan itu yang menegakkan "sekali kirim".** `rolling` memakai `buildIdempotencyKey('BROADCAST', campaign.id, no_rkm_medis)` -- `campaign.id` BARU tiap kali jalan, jadi memang mengirim ulang (itu yang diminta pola pengumuman berkala). `followup` memakai `buildIdempotencyKey('BROADCAST_FOLLOWUP', schedule.id, no_rawat)` -- **tanpa `campaign.id`**, jadi satu kunjungan hanya pernah memicu satu pesan selamanya, ditolak `UNIQUE KEY uq_idem` di mesin database bila jadwalnya tidak sengaja jalan dua kali (worker restart, jam server mundur, staf menekan aktifkan berulang). `no_rawat` ada di `PatientSegmentRow` khusus untuk ini -- kuncinya per KUNJUNGAN, bukan per pasien, supaya kunjungan berikutnya pasien yang sama tetap dapat tindak lanjutnya sendiri.

`runOneSchedule()` juga menyaring lebih dulu kunjungan yang kunci idempotennya sudah ada (`filterAlreadySent()`) sebelum membuat `broadcast_campaign`. UNIQUE KEY tetap penjaga terakhirnya; penyaringan ini murni supaya `broadcast_campaign` jujur -- tanpa itu jadwal harian menumpuk baris kampanye yang mengaku punya penerima padahal nol pesan baru masuk `outbox`, dan `broadcast_campaign` insert-only sehingga angka yang terlanjur salah tidak bisa dikoreksi belakangan.

Dua tempat yang sengaja MELONGGARKAN pemeriksaan untuk mode `followup`: `createScheduleAction` tidak menolak simpan saat segmen 0 hasil, dan tombol Simpan tidak dinonaktifkan -- jendelanya cuma satu hari kalender, jadi nol hasil hari ini sering wajar belaka (hari libur, atau H+N jatuh di hari sepi) dan sama sekali bukan tanda filternya keliru.

**Matematika tanggal `core/schedule.ts`'s `computeNextRunAt()`** (diuji unit `schedule.test.ts`, 15 kasus termasuk pergantian tahun dan batas waktu persis): dipakai baik saat jadwal dibuat (dashboard, hitung `next_run_at` pertama) maupun setelah tiap kali worker selesai jalan (hitung kejadian berikutnya) -- satu fungsi murni, bukan dua implementasi yang bisa berbeda tafsir. Memakai getter/setter `Date` lokal biasa (bukan util UTC+7 eksplisit), konsisten dengan asumsi seluruh proyek bahwa server RS berzona WIB (`quietHours.ts`, `khanza/common.ts`). `dayOfMonth` sengaja dibatasi 1-28 (bukan sampai 31) supaya valid di semua bulan termasuk Februari tanpa logika kasus-khusus.

**Dua pagar tambahan yang tidak dipunyai BROADCAST manual**, karena ini berjalan TANPA staf meninjau tiap kali kirim: (1) `stop_after_date` opsional -- kalau lewat, worker menonaktifkan jadwal sendiri (`is_active=0`) supaya tidak ada "atur lalu lupa" tanpa batas waktu; direkomendasikan diisi lewat UI, tapi tidak wajib. (2) Segmen yang melebihi `broadcast.max_recipients` pada suatu siklus **dilewati seluruhnya** (bukan dipotong sebagian) dan dicatat ke `audit_log` sebagai `broadcast_schedule_skip_too_large` -- jadwal TETAP aktif untuk siklus berikutnya, staf perlu meninjau manual. Baik `toggleScheduleAction` (jeda/aktifkan) maupun `deleteScheduleAction` di dashboard admin-only dan tercatat `audit_log`.

**Grant database untuk tabel baru TIDAK otomatis.** `wakhanza_rw` diberi `UPDATE`/`DELETE` per-tabel (ARCHITECTURE §9.5), bukan skema-lebar -- ditemukan LANGSUNG lewat percobaan `UPDATE`/`DELETE` empiris saat implementasi (`ERROR 1142: command denied`) sebelum sempat jadi bug produksi: tabel baru wajib grant eksplisit satu per satu, tidak mewarisi apa pun dari tabel lain. `broadcast_schedule` butuh `UPDATE`/`DELETE` (beda dari `broadcast_campaign`/`audit_log` yang insert-only) untuk `next_run_at`/`is_active`/`last_run_at` dan aksi jeda/hapus staf -- grant-nya ada di daftar `TECH_STACK.md` §"Dua Koneksi Database yang Sengaja Dipisah", diterapkan manual lewat akun MariaDB berhak grant (root), bukan lewat `npm run migrate` (`wakhanza_rw` sendiri tidak punya `GRANT OPTION`).

**Gotcha uji manual, dicatat supaya tidak terulang**: baris `broadcast_schedule` yang `next_run_at`-nya di-INSERT lewat `mysql` mentah (mis. `NOW() - INTERVAL 10 SECOND`) TIDAK cocok dengan query `Op.lte` Sequelize milik worker, walau `SELECT next_run_at <= NOW()` lewat SQL biasa menunjukkan `1` (benar). Sequelize/mysql2 menerjemahkan `Date` JS dan nilai `DATETIME` MySQL secara konsisten satu sama lain (tulis-lewat-Sequelize lalu baca-lewat-Sequelize cocok), tapi TIDAK konsisten dengan nilai yang ditulis langsung lewat klien `mysql` di luar Sequelize. Saat menguji fitur berbasis tanggal/jam secara manual, buat baris ujinya lewat kode aplikasi (`Model.create()` atau server action/skrip yang memanggilnya), jangan lewat `INSERT` SQL mentah untuk kolom yang nanti dibandingkan lewat Sequelize.

**SEBABNYA, ditemukan belakangan: kolom `DATETIME` di `wakhanza` menyimpan UTC, bukan WIB.** Sequelize memakai `timezone: '+00:00'` (bawaannya), jadi `Date` JS pukul 20:16 WIB tersimpan sebagai `'13:16:27'` dan dibaca balik menjadi 20:16 WIB lagi — konsisten, dan **tidak ada yang perlu diperbaiki di kode**. Yang perlu diketahui adalah konsekuensi bacanya: **nilai yang terlihat di CLI `mysql` bukan jam dinding WIB**, jadi menghitung selisih waktu dari angka mentah itu meleset 7 jam. Pakai `CONVERT_TZ(kolom,'+00:00','+07:00')` saat memeriksa lewat `mysql`, atau baca lewat Sequelize. Semua model menulis `created_at` sendiri (`defaultValue: DataTypes.NOW`) alih-alih membiarkan `DEFAULT current_timestamp()` milik MariaDB mengisinya — itulah yang menjaga tulis/baca tetap sepasang. Baris yang di-INSERT lewat SQL mentah melewati pasangan itu, dan di situlah gotcha di atas lahir.

### Kelas keempat: BALASAN OTOMATIS (dipicu PASIEN, arah berlawanan)

Tiga kelas sebelumnya berangkat dari kejadian di `sik` (sisip/pindai) atau dari staf/jadwal (broadcast). Yang ini berangkat dari **pesan masuk pasien** -- satu-satunya kelas yang lajunya tidak dikendalikan rumah sakit sama sekali, dan itu yang membentuk hampir seluruh pagarnya.

`worker/wa-client.ts`'s pendengar `client.on('message')` -> `worker/autoReply.ts`'s `handleInboundMessageSafely()`. **Permintaan berhenti diperiksa lebih dulu dan langsung `return`** -- aturan balasan yang keliru ditulis staf tidak boleh bisa menyandera permintaan berhenti berlangganan.

**Enqueue lewat `enqueueMessage()` yang sama persis**, bukan `message.reply()`. Membalas langsung dari pendengar event akan melewati jeda acak 3-8 detik, kuota per jam, kode unik, dan `send_log` sekaligus -- dan halaman Log berhenti menunjukkan apa yang benar-benar dikirim. Satu-satunya yang BERBEDA dari pemicu lain: AUTO_REPLY tidak tunduk pada opt-out (§ berikutnya).

**Jam tenang DILEWATI** (`core/quietHours.ts`'s `BYPASS_QUIET_HOURS`, bersama `BOOK_CANCEL`). Ini balasan atas pesan yang pasiennya sendiri kirim barusan; menahannya sampai jam 07.00 membuat jawaban datang sembilan jam setelah pertanyaannya. Jam tenang melindungi dari pesan yang TIDAK diminta -- balasan atas pertanyaan sendiri bukan itu.

**Pencocokan: kata kunci, bukan AI.** `core/autoReply.ts` seluruhnya fungsi murni (tanpa database/WhatsApp) supaya kotak "Uji coba" di dashboard memakai fungsi yang SAMA -- pratinjau yang berbeda dari kenyataan lebih buruk daripada tanpa pratinjau. Tiga hal yang menempel di sana:

- **Cocok sebagai KATA UTUH**, lewat penyelubungan spasi (`` ` ${teks} ` ``.includes(`` ` ${kunci} ` ``)), bukan `includes` mentah dan bukan RegExp per kata kunci. Tanpa itu "obat" ikut cocok pada "obatan" dan kata kunci pendek seperti "rm" meletus di tengah kata mana pun. RegExp ditolak karena kata kuncinya input staf -- tanda baca yang tak sengaja terketik jadi galat sintaks atau pola lambat.
- **Aturan pertama yang cocok menang**, diurutkan `priority` lalu `id`. Bukan "kecocokan terpanjang" atau peringkat terhitung: "kenapa aturan ini yang membalas" harus terjawab dengan melihat daftar terurut di layar. Satu pesan = maksimal satu balasan.
- **`detectPoli()` mengembalikan null saat AMBIGU**, bukan menebak yang pertama -- pemanggilnya menafsirkan null sebagai "tampilkan seluruh jadwal", jawaban yang lebih panjang tapi tak pernah salah. Menebak dan meleset menghasilkan jawaban percaya-diri-dan-keliru: pasien datang di hari yang salah.

**`khanza/jadwalDokter.ts` -- satu-satunya modul `khanza/` yang tidak membaca kejadian satu pasien.** Ia membaca tabel konfigurasi layanan (`jadwal`+`dokter`+`poliklinik`), informasi yang memang diumumkan RS. Dua hal yang ditemukan langsung dari `sik` sungguhan saat implementasi:

- **`d.status='1'` DAN `p.status='1'` keduanya wajib.** Baris `jadwal` tidak ikut terhapus saat poli ditutup -- Poliklinik Mata di database ini sudah `status='0'` tapi masih menyimpan dua baris jadwal. Tanpa penyaring poli, balasan otomatis menyuruh pasien datang ke poli yang sudah tidak dilayani.
- `verify:plans` mendaftarkannya dengan izin pindai penuh untuk alias `d` (= `dokter`, 9 baris), dan alasannya BERBEDA dari `booking_registrasi`: `jadwal` adalah tabel konfigurasi yang barisnya sebanyak (dokter × hari praktik) dan tidak tumbuh seiring jumlah pasien. `jadwal` sendiri (alias `j`) TIDAK diberi izin itu dan memang tidak membutuhkannya -- ia masuk lewat indeks.

**Poli sensitif diperlakukan asimetris, dan itu disengaja** (`buildJadwalSql()`): dilewati pada daftar UMUM ("jadwal dokter"), tapi TETAP ditampilkan bila pasien menyebut poli itu dengan nama. `privacy.sensitive_poli_codes` (F4.3) ada untuk mencegah pesan membocorkan bahwa SEORANG PASIEN berurusan dengan layanan itu -- bukan untuk merahasiakan bahwa layanannya ada. Menyembunyikannya dari orang yang menanyakannya hanya membuat pasien yang paling butuh tidak terlayani, tanpa menambah kerahasiaan apa pun.

**`{jadwal_dokter}`/`{jadwal_hari_ini}`/`{daftar_poli}` dikecualikan dari `sanitizeValue()`** (`MULTILINE_VARIABLES` di `core/template.ts`) -- sanitizer itu justru bertugas membuang baris baru dan memotong di 60 karakter. Pengecualiannya aman HANYA karena `formatJadwal()` memanggil `sanitizeValue()` sendiri untuk tiap `nm_dokter`/`nm_poli` sebelum merangkainya: semua baris baru pada hasil akhir dipasang kode kita, bukan datang dari isi kolom. **Jangan pernah menambahkan variabel ke daftar itu yang isinya langsung dari satu kolom `sik`** -- itu persis lubang §9.2. Aturan satu lintasan tetap utuh (`String.replace` dengan callback tidak memeriksa ulang hasil substitusi), diuji unit.

**Empat pagar, dan tiga di antaranya ada karena pasien yang mengatur lajunya:**

1. `autoreply.enabled` default `'0'`. Menyalakannya lewat `toggleAutoReplyAction` di halamannya sendiri, SENGAJA tidak lewat `/api/settings` -- supaya tercatat di `audit_log` sebagai peristiwanya sendiri (`auto_reply_toggle`), bukan tenggelam sebagai satu nama kunci di dalam `settings_update`.
2. `autoreply.max_per_number_per_hour` (default 5), dihitung dari `auto_reply_log` **bukan** `outbox` -- pesan lain ke nomor yang sama (antrian, hasil lab) tidak boleh ikut memakan jatahnya.
3. **Pemeriksaan duplikat di DEPAN, bukan cuma mengandalkan `uq_idem`.** Kunci idempotennya `buildIdempotencyKey('AUTO_REPLY', waMessageId)` dan UNIQUE KEY memang menolak baris kedua -- tapi penolakan itu terjadi terlambat untuk dua hal yang sudah terjadi sebelum insert: satu baris `auto_reply_log` bertanda `matched` yang tidak pernah jadi pesan, dan satu jatah kuota pasien yang termakan. whatsapp-web.js menyerahkan ulang pesan lama setiap sesi dipulihkan, jadi tanpa pemeriksaan depan ini satu restart worker bisa menghabiskan kuota nomor yang tidak mengirim apa pun hari itu. **Ditemukan saat pengujian, bukan diperkirakan.**
4. Pesan cadangan (`autoreply.fallback_body`) default KOSONG = **diam**. Pesan tak dikenali sering pertanyaan medis sungguhan; menjawabnya "maaf tidak mengerti" berulang kali lebih buruk daripada tidak menjawab. Kalau diisi, ia punya jeda sendiri (`fallback_cooldown_minutes`, default 180) supaya orang yang mengetik beberapa kalimat berturut-turut tidak menerimanya per kalimat.

**`auto_reply_log.inbound_preview` default TIDAK diisi** (`autoreply.log_inbound_text` = `'0'`). Pesan masuk pasien bisa berisi keluhan medis dan tabel ini bukan rekam medis; yang dibutuhkan untuk menyetel kata kunci cuma tahu BERAPA BANYAK yang tak terjawab, dan itu sudah dijawab kolom `outcome` tanpa menyimpan satu kata pun milik pasien. Halaman ringkasan `/balasan-otomatis` memakai `outcome`, bukan menghitung `outbox` -- pertanyaan yang TIDAK dibalas justru tidak meninggalkan jejak di `outbox` sama sekali.

Grant: `auto_reply_rule` dapat `UPDATE`+`DELETE`; `auto_reply_log` dapat `DELETE` saja (dipangkas `worker/cleanup.ts`, masa simpan sama 90 hari) tapi **tidak** `UPDATE` -- baris log tidak pernah ditulis ulang. Sekali lagi terbukti tidak diwarisi: `ERROR 1142` untuk keduanya sebelum grant eksplisit diterapkan lewat root.

**Bagian yang dulu ditulis "BELUM terbukti end-to-end, tapi pembungkusnya cuma enam baris" — dan enam baris itu ternyata memang salah.** Klaim lamanya berbunyi: event `client.on('message')` belum pernah diuji dengan ponsel kedua, tapi jalurnya sama dengan penanganan `STOP` sejak Fase 4 jadi aman diasumsikan. Begitu pesan masuk sungguhan akhirnya dikirim, **tidak satu pun dibalas**. Lihat § berikutnya. Pelajarannya bukan soal LID: bagian yang "terlalu kecil untuk salah" adalah persis bagian yang tidak diuji, dan di sinilah satu-satunya batas sistem yang bentuk datanya ditentukan pihak luar.

### Kelas kelima: NOTIFIKASI FARMASI (tujuannya STAF, bukan pasien)

`/farmasi` (admin-only) mengirim pemberitahuan ke **grup WhatsApp apotek atau nomor petugasnya** setiap resep divalidasi dan setiap obat diserahkan. Empat kelas sebelumnya semuanya berujung ke nomor seorang pasien; yang ini tidak, dan perbedaan itu menjalar ke hampir seluruh pagarnya.

**Kolom mana yang berarti "validasi" dibuktikan dari data, bukan ditebak dari namanya.** `resep_obat` tidak punya kolom bernama validasi sama sekali, dan `tgl_perawatan` sama sekali tidak mengisyaratkan apa pun tentang apotek. Urutan sebenarnya di database ini:

| Langkah | Kolom | Jeda rata-rata |
|---|---|---|
| Dokter menulis resep | `tgl_peresepan` + `jam_peresepan` | — |
| **Validasi apotek** | `tgl_perawatan` + `jam` | +5,3 menit |
| **Penyerahan** | `tgl_penyerahan` + `jam_penyerahan` | +12,4 menit |

Yang memastikan `jam` benar-benar langkah tersendiri dan bukan salinan waktu penyerahan: **3.214 resep yang BELUM diserahkan sudah punya `jam` terisi**, dan dari ~28 ribu baris yang sudah diserahkan hanya 1 yang urutannya terbalik. `tgl_perawatan` NULLABLE dan berisi `'0000-00-00'` pada 13 baris lama -- keduanya wajib disaring eksplisit, kalau tidak `TIMESTAMP()` menghasilkan NULL dan barisnya lolos jadi Invalid Date.

**`outbox.chat_id`, kolom BARU dan bukan menumpang `phone_e164`** (`migrations/016`). Tiga hal akan jadi bug diam kalau ditumpangkan: JID grup 24 karakter tidak muat di `VARCHAR(20)`; dispatcher memakai `phone_e164` untuk mencari `opt_out` dan memanggil `getNumberId()`, keduanya tidak berlaku untuk grup; dan `maskPhone()` mengasumsikan isinya nomor. `chat_id` NULL = perilaku sembilan pemicu lain persis seperti sebelumnya. `sendWhatsAppMessage()` sekarang menerima ALAMAT LENGKAP, bukan nomor -- perakitan `@c.us` pindah ke dispatcher, satu-satunya tempat yang tahu jenis tujuannya.

**Pemeriksaan pendaftaran diturunkan dari ALAMATNYA, bukan dari ada-tidaknya `phone_e164`.** `getNumberId()` atas JID grup menjawab "tidak terdaftar", dan tanpa cabang ini setiap notifikasi grup ditandai gagal permanen dengan alasan yang tidak ada hubungannya dengan sebab sebenarnya. Diturunkan dari akhiran `@c.us` supaya tujuan personal farmasi (yang `phone_e164`-nya sengaja NULL) tetap ikut terjaga.

**Kode grup yang salah TETAP berstatus `sent`** -- dibuktikan langsung: kiriman ke `120363999999999999@g.us` yang tidak ada diterima WhatsApp tanpa galat apa pun. Itulah kenapa tombol **"Kirim uji"** per tujuan bukan kenyamanan melainkan satu-satunya cara membuktikan sebuah kode grup benar: harus ada manusia yang melihat pesannya muncul di grup. Pelajaran yang sama sudah dibayar di tombol uji webhook peringatan. Kunci idempotennya menyertakan stempel waktu supaya bisa ditekan berulang -- staf yang sedang membetulkan kode harus bisa mencoba lagi.

**Daftar grup dibaca worker, dan `client.getChats()` SENGAJA tidak dipakai.** JID grup tidak bisa dilihat dari aplikasi WhatsApp; yang bisa disalin staf hanyalah tautan undangan (`chat.whatsapp.com/...`), yang sama sekali bukan JID dan tidak bisa dikonversi -- karena itu `core/farmasiTarget.ts` menolaknya dengan menyebut jalan keluarnya, bukan sekadar "format tidak valid". `sync_groups` (`wa_session.command`, jalur tabel yang sama seperti QR) mengisi `wa_group` supaya staf MEMILIH alih-alih mengetik. `getChats()` gagal pada percobaan pertama dengan galat `"r"` -- nama variabel dari kode WhatsApp terminifikasi -- karena ia memetakan SETIAP chat lewat `getChatModel()` di dalam satu `Promise.all`: satu chat rusak menjatuhkan seluruh daftar, dan ribuan percakapan pasien diserialisasi padahal yang dibutuhkan cuma grup. Penggantinya membaca koleksi yang SAMA (`WAWebCollections.Chat`, persis yang dipakai `getChats()` di baliknya -- jadi bukan ketergantungan baru, melainkan yang lama dikurangi satu lapis), menyaring `@g.us` lebih dulu, dan membungkus tiap chat dalam try/catch sendiri. Hasilnya 6 grup dalam ~16 ms.

**Ambang rekap (`farmasi.max_per_cycle`, default 20) adalah syarat hidup, bukan penghematan.** Pagi sibuk menghasilkan puluhan resep dalam satu siklus 60 detik; mengirimnya satu per satu adalah persis pola beruntun yang memicu deteksi spam WhatsApp (F5.2) -- dan yang diblokir adalah SATU-SATUNYA nomor rumah sakit, sehingga notifikasi pasien ikut mati bersamanya. Di atas ambang, satu pesan rekap per tujuan menggantikan seluruhnya. Kunci idempotennya memakai watermark baru + jumlah baris, bukan nomor resep (di sini ada banyak).

**`chat_id` WAJIB masuk kunci idempoten** (`buildIdempotencyKey(triggerCode, no_resep, chatId)`). Tanpa itu tujuan KEDUA dan seterusnya ditolak `uq_idem` sebagai duplikat dan hanya satu grup yang pernah menerima apa pun -- kegagalan yang tidak meninggalkan galat sama sekali karena INSERT-nya memang sengaja `ignoreDuplicates`.

**Poli sensitif TETAP dikirimi, dengan pesan generiknya sendiri.** `farmasi.template_generic` bukan `privacy.generic_template` -- yang terakhir ditulis untuk pasien ("ada informasi dari rumah sakit") dan tidak berguna bagi apotek. Padanan di sini tetap menyebut nomor resep tapi tidak menyebut pasien maupun poli: apotek tetap tahu ada pekerjaan masuk, sementara keterkaitan seseorang dengan poli sensitif tidak terbaca sekian orang di dalam grup. Mendiamkannya sepenuhnya justru membuat resep pasien poli sensitif diam-diam terlewat -- merugikan pasien yang perlindungannya paling dijaga.

**Jam tenang dilewati, opt-out tidak berlaku.** Jam tenang melindungi orang yang tidur di rumah, bukan shift malam yang menunggu pesan ini; menahannya sampai 07.00 juga membuat seluruh resep semalam menumpuk lalu terkirim serentak sebagai puluhan pesan basi. Opt-out tidak berlaku karena tidak ada nomor pasien untuk dicocokkan, dan seorang pasien tidak bisa memberhentikan koordinasi kerja internal RS -- kasus paling jelas dari tiga pengecualian di `OPT_OUT_TRIGGERS`, dan justru karena itu paling gampang lolos tanpa dipikirkan.

**Yang sengaja TIDAK diambil dari `sik`**: nama obat, jumlah, aturan pakai, diagnosis, dan `no_tlp`. `FARMASI_TEMPLATE_VARIABLES` tidak punya variabelnya, dan `khanza/farmasiStaf.ts` tidak pernah men-`SELECT` kolomnya -- menambahkan variabelnya akan jadi alasan pertama untuk mulai mengambilnya. Daftar obat seseorang adalah justru bagian yang paling tidak boleh berpindah ke grup WhatsApp.

Kunci `farmasi.*` sengaja TIDAK didaftarkan ke `EDITABLE_KEYS` (`api/settings/route.ts`): form Pengaturan mengirim ULANG semua kunci tiap kali Simpan ditekan, jadi membiarkannya di sana membuka jalan agar isi pesan tertimpa oleh halaman yang bahkan tidak menampilkannya. Grant `UPDATE`/`DELETE` untuk `farmasi_target` dan `wa_group` diterapkan manual lewat root, dan sekali lagi terbukti tidak diwarisi (`ERROR 1142` sebelum, berhasil sesudah).

### Balasan stok & harga obat (`/farmasi`, migrations/019) -- arah MASUK, dan katalog BUKAN rekam medis

Bagian kedua di `/farmasi`, arahnya berlawanan dari notifikasi farmasi di atasnya: menjawab pertanyaan MASUK ("stok paracetamol?", "berapa harga paramex") dari `databarang` (harga) + `gudangbarang` (stok per batch) + `kodesatuan`.

**Ini TIDAK melanggar "nama obat tidak pernah diambil dari `sik`", dan bedanya harus jelas sebelum menyentuh kodenya.** Larangan itu tentang `resep_obat` -- obat APA yang diterima SIAPA, yang memang rekam medis. Yang dibaca di sini katalog barang milik apotek: tidak ada satu pun kolom yang menghubungkan sebuah obat dengan seorang pasien, dan nomor yang bertanya tidak pernah dipakai untuk mencari pasien. Setara daftar harga yang ditempel di loket. `khanza/stokObat.ts` memuat peringatan agar modul ini tidak pernah digabung dengan `resep_obat`/`detail_pemberian_obat` -- penggabungan itulah yang mengubahnya jadi data pasien. `STOK_TEMPLATE_VARIABLES` sengaja **tidak** punya `{nama_pasien}`/`{no_rm}`/`{no_resep}`, justru supaya tidak ada alasan pertama untuk mulai mengambilnya.

**`farmasi.stok_mode` punya TIGA nilai** (`mati` bawaan, `petugas`, `semua`), karena "boleh dijawab otomatis" dan "boleh dijawab kepada siapa" dua keputusan berbeda. Yang menentukan **angka** sisa stok muncul BUKAN modenya melainkan siapa yang bertanya: penanya terdaftar mendapat angka berikut tanda `(menipis)`/`(habis)`, penanya umum yang lolos lewat mode `semua` hanya mendapat "tersedia"/"kosong" + harga. Mengikatnya ke mode akan membuat apotek kehilangan angka persediaannya sendiri begitu RS membuka layanan untuk umum.

**Daftar putihnya `farmasi_target.boleh_tanya`** (migrations/020) -- kolom TERSENDIRI, bukan `is_active` dan bukan tabel kedua. Satu tabel, karena dua tempat yang harus diingat saat petugas berganti nomor akan gagal DIAM: petugasnya sekadar tidak pernah dijawab. Tapi kolom terpisah, karena `is_active` menjawab "ke mana notifikasi resep dikirim" sementara `boleh_tanya` menjawab "siapa yang boleh membuat nomor RS menjawab" -- sebuah grup sangat wajar cuma menerima pemberitahuan tanpa nomor RS ikut bicara di dalamnya. Bawaannya `0` untuk baris yang sudah ada: memperketat dengan sengaja.

**GRUP bisa bertanya, dan itu pengecualian atas aturan "nomor RS tidak pernah membalas di grup" -- bukan pelonggarannya.** Aturan itu masih berlaku untuk semua yang lain, dan sebabnya tidak berubah: menjawab pertanyaan satu orang berarti seluruh anggota menerima pesannya, dan satu percakapan ramai berubah jadi rentetan balasan dari satu-satunya nomor RS (PRD F5.2). Tiga syarat yang membuat pengecualian ini bisa dipertanggungjawabkan, dan ketiganya harus tetap ada: (1) grupnya didaftarkan admin satu per satu -- **wajib terdaftar bahkan pada mode `semua`**, karena mode itu berarti "siapa pun boleh bertanya lewat japri", bukan "nomor RS boleh menjawab di grup mana pun yang kebetulan mengundangnya"; (2) hanya kata kunci stok yang dijawab -- aturan `/balasan-otomatis` SENGAJA tidak ikut, kata kuncinya jauh lebih longgar; (3) ada kuota per jam per grup (`farmasi.stok_max_per_grup_per_jam`, default 10).

**Kuota grup dihitung dari `outbox`, bukan `auto_reply_log`** -- dan sebab pertamanya akan jadi bug diam kalau diabaikan: `auto_reply_log.phone_e164` VARCHAR(20) sementara JID grup 24 karakter, jadi MariaDB non-strict memotongnya diam-diam tepat di ekor yang membedakan satu grup dari grup lain. Kelas kesalahan yang sama dengan kunci idempoten pada `template_target`. Sebab kedua: yang perlu dihitung cuma balasan stok, dan notifikasi resep ke grup yang sama tidak boleh ikut memakan jatahnya -- pagi sibuk penuh resep akan mendiamkan pertanyaan stok kalau ikut terhitung. Kombinasi `trigger_code='AUTO_REPLY'` + `chat_id` terisi hanya dihasilkan jalur ini.

Jalur grup dipisah (`cobaBalasStokDariGrup()`), bukan menumpang `handleInboundMessage()`, karena tiga hal di sana tidak berlaku di grup: permintaan berhenti (berkunci pada nomor, sementara yang mengetik cuma salah satu peserta), pencatatan `auto_reply_log`, dan aturan kata kunci. Yang TETAP dikerjakan: pesan tanpa huruf/angka dilewati, dan penyerahan ulang ditolak -- whatsapp-web.js menyerahkan ulang pesan lama tiap sesi dipulihkan, jadi tanpa itu satu restart worker bisa membanjiri grup dengan jawaban atas pertanyaan kemarin.

**Sakelarnya berdiri sendiri dari `autoreply.enabled`**, dan `handleInboundMessage` berjalan bila SALAH SATU menyala. Yang TIDAK dipisah: pemeriksaan pesan kosong, penyerahan ulang, dan kuota per nomor -- memisahkannya berarti satu nomor bisa menghabiskan kuota lewat satu jalur lalu tetap dilayani lewat jalur lain, dan kuota itu ada justru karena laju pesan masuk tidak dikendalikan rumah sakit.

**Cabang stok didahulukan atas aturan `/balasan-otomatis`**: kata kunci stok spesifik ("stok", "harga") sementara aturan buatan staf cenderung umum, dan urutan sebaliknya membuat satu aturan bertema luas menelan seluruh pertanyaan stok tanpa ada yang menyadarinya. Aman untuk yang tidak memakainya -- `cobaBalasStok()` mengembalikan `ditangani: false` untuk pesan tanpa kata kunci, untuk nomor tak berhak pada mode `petugas`, dan tentu saat modenya `mati`. **Pemeriksaan izin dikerjakan SEBELUM kata kunci dibaca**, supaya nomor tak berhak jatuh ke aturan biasa seolah fitur ini tidak ada; membalikkannya membuat pertanyaannya "tertangani" lalu didiamkan.

**`trigger_code`-nya tetap AUTO_REPLY, bukan kode baru.** Ini balasan atas pesan yang penanya kirim sendiri, jadi seluruh perlakuannya harus sama: melewati jam tenang, dan tidak tunduk pada daftar tolak. Kode baru berarti kedua keputusan itu harus didaftarkan ulang di `core/optOut.ts` dan `core/quietHours.ts` -- dan yang lupa mendaftarkannya tidak mendapat satu pun galat.

Empat hal lagi yang menempel:

- **Nama obat TIDAK ditebak saat penanya tidak menyebutnya.** "berapa harga obat?" menyisakan string kosong dan dijawab dengan permintaan menyebutkan namanya -- bukan barang pertama di katalog. Kesalahan yang sama yang membuat `detectPoli()` mengembalikan null saat ambigu. Potongan di bawah 3 karakter diperlakukan sama, karena `LIKE '%a%'` cocok dengan hampir seluruh katalog dan hasilnya tampak seperti pencarian sungguhan.
- **`{stok_obat}` masuk `MULTILINE_VARIABLES`, `{cari_obat}` TIDAK.** Yang pertama dirakit `formatStokObat()` yang memanggil `sanitizeValue()` sendiri per nama obat dan satuan, jadi setiap baris baru pada hasil akhir berasal dari kode kita. Yang kedua adalah teks yang diketik penanya -- masukan dari luar, wajib lewat sanitasi. Dipatok unit test tersendiri.
- **`b.status='1'` wajib**, pelajaran yang sama seperti `p.status='1'` pada jadwal dokter: barang yang sudah tidak dijual tetap punya barisnya, dan menjawabnya lengkap dengan harga lama membuat orang datang menanyakan barang yang tidak ada. `LEFT JOIN` pada `gudangbarang` juga wajib -- INNER akan membuat obat yang belum pernah punya baris stok hilang dari hasil, sehingga dijawab "tidak ditemukan" padahal ada di katalog.
- **Nol dibedakan dari menipis.** Ada obat berstok 0 sementara `stokminimal`-nya di atas nol; tanpa pembedaan itu keduanya jatuh ke cabang yang sama dan terbaca "sisa 0 (menipis)" -- seolah masih ada yang bisa diserahkan hari ini.

**Dua bug yang membuat pertanyaan grup SUNGGUHAN tidak pernah dibalas** -- 22 pemeriksaan lolos, `boleh_tanya` dicentang, sesi `ready`, pengiriman KE grup terbukti jalan, dan tetap nol balasan / nol baris `outbox` / nol galat. Keduanya hanya bisa ditemukan lewat pesan yang datang dari luar:

- **`message.id._serialized` HILANG pada pesan grup**, dan jalur grup satu-satunya yang memperlakukannya sebagai fatal lalu diam. Sekarang lewat `kunciPesanMasuk()` -- lihat § tersendiri di bawah.
- **Sebutan `@<id>` terbaca sebagai nama obat.** `normalizeInbound()` mengubah tiap karakter non-alfanumerik jadi spasi, sehingga `@115634008510549` menjadi kata 15 digit yang lolos `KATA_PENGAPIT` lalu dipakai sebagai pencarian katalog -- sesudah normalisasi, informasi yang menandainya sebagai sebutan sudah musnah. Karena itu **`buangMention()` wajib berjalan LEBIH DULU, bukan sesudah**. Hanya `@` diikuti ANGKA yang dibuang; sebutan WhatsApp selalu id numerik, sementara `@` diikuti huruf bisa saja bagian nama dagang. Di dalam grup, me-mention nomor RS justru cara paling wajar memanggilnya -- ini bentuk pertanyaan yang UMUM, bukan kekecualian.

Pelajarannya sama dengan bug `@lid`, dan diulangi di titik yang sama: **uji yang membangun sendiri objek pesannya tidak pernah bisa membuktikan batas sistem yang bentuk datanya ditentukan pihak luar.** Kedua puluh dua pemeriksaan itu menyusun `{ id: { _serialized: '...' }, from, body }` dengan tangan -- lengkap, rapi, dan tidak pernah seperti yang benar-benar datang dari Chromium.

`verify:plans` mendaftarkannya sebagai `FARMASI_STOK` dengan izin pindai penuh untuk alias `b` (= `databarang`): pencariannya `LIKE '%potongan%'` dan tidak ada indeks B-tree yang bisa melayani pola berawalan wildcard. Alasan diterimanya sama seperti `dokter` pada AUTOREPLY_JADWAL -- `databarang` KATALOG, tumbuh seiring jenis barang (ratusan), bukan seiring jumlah pasien. `gudangbarang` yang justru bertambah per batch pembelian TIDAK diberi izin itu dan masuk lewat `PRIMARY`/`kode_brng`.

### Kelas keenam: DARURAT STOK (`/farmasi`, migrations/021) -- dipicu WAKTU, bukan kejadian

Bagian ketiga di `/farmasi`, dan pemicunya satu-satunya yang tidak berasal dari kejadian apa pun:

| Kelas | Yang memicu |
|---|---|
| sisip / pindai | kejadian di `sik` |
| broadcast | staf menekan kirim |
| broadcast terjadwal | jadwal + segmen pasien |
| balasan otomatis | pesan masuk pasien |
| notifikasi farmasi | resep divalidasi/diserahkan |
| **darurat stok** | **jadwal jatuh tempo, dan keadaan gudang saat itu** |

Bedanya bukan akademis: sebuah pemicu resep berhenti sendiri saat resepnya habis, sementara daftar barang di bawah ambang minimal tidak pernah "habis" -- ia cenderung tetap panjang sampai apoteknya memesan ulang.

**Satu query `GROUP BY ... HAVING`, dan JANGAN ditiru dari Khanza.** Layar persediaan Khanza membaca seluruh katalog lalu menjalankan satu query jumlah stok tersendiri untuk SETIAP baris (N+1). Wajar untuk aplikasi desktop yang dijalankan sesekali; sama sekali tidak wajar untuk proses latar yang berbagi database dengan SIMRS yang sedang melayani pasien (`pool.max: 2`).

**`stokminimal > 0` WAJIB disaring, dan Khanza TIDAK menyaringnya.** Aturan mentah Khanza ikut mencocokkan barang ber-`stokminimal = 0` -- barang yang apoteknya memang tidak pernah menetapkan ambang untuknya. "Stok 0, minimum 0" bukan keadaan darurat, itu entri katalog yang belum pernah distok. Bedanya menentukan apakah fiturnya dipakai atau diabaikan: daftar yang sebagian besar isinya kebisingan berhenti dibaca dalam seminggu, dan peringatan yang tidak dibaca sama saja dengan tidak ada -- pelajaran yang sama sudah dibayar pada pemisahan level log `debug`/`warn` di `wa-client.ts`.

**`khanza/stokGudang.ts` -- satu penurunan stok, dipakai BERSAMA dengan balasan stok.** Query balasan stok yang lama tidak menyaring `bangsal.status='1'` maupun cabang batch, padahal Khanza melakukan keduanya; di database ini hasilnya kebetulan sama, tapi "kebetulan sama hari ini" bukan alasan membiarkan dua penurunan hidup berdampingan. Yang muncul kalau keduanya menyimpang bukan galat, melainkan **dua angka stok berbeda dari satu sistem**: pasien diberi tahu "tersedia" pada menit yang sama apotek menerima peringatan "habis". Bentuk kegagalan yang sama persis dengan `respectsOptOut()`, `core/outboxStatus.ts`, dan `kunciPesanMasuk()`.

Tiga hal yang menempel pada penurunan bersamanya:

- **Cabang batch jadi pengaturan (`farmasi.stok_pakai_batch`), dibaca PEMANGGIL bukan modul `khanza/`.** Batas itu yang membuat `npm run verify:db` bisa membuktikan `sik` hanya dibaca. Bawaannya `0` karena seluruh baris `gudangbarang` di mesin ini ber-`no_batch = ''`. Instalasi yang memakai batch WAJIB menyalakannya -- salah menyetel tidak menghasilkan galat, melainkan seluruh katalog terbaca berstok nol.
- **Penyaring bangsal ada di dalam `SUM(CASE ...)`, bukan di WHERE.** Penyaring di WHERE menggugurkan seluruh barangnya begitu ia cuma punya stok di gudang nonaktif, sehingga barang yang stok efektifnya NOL malah hilang dari daftar darurat -- kebalikan persis dari yang dibutuhkan.
- **Kondisi batch ada di ON, bukan WHERE.** Dengan `LEFT JOIN`, kondisi di WHERE menggugurkan barang yang belum punya satu pun baris stok -- barang yang justru paling perlu muncul.

**TANPA izin pindai penuh, dan jangan ditambahkan.** `b.stokminimal > 0` dilayani indeks yang sudah ada (`range` + `Using index`) -- penyaring yang ada karena alasan kebenaran itu kebetulan sekaligus membuat query-nya lebih murah daripada balasan stok yang `LIKE '%..%'`. Izinnya sengaja tidak ditulis walau "aman kalau ada": izin pindai penuh yang menganggur adalah izin yang diam-diam menutupi kemunduran berikutnya.

**`every_n_days` ditambahkan ke `computeNextRunAt()`, tapi TIDAK ke `RepeatKind`.** `broadcast_schedule.repeat_kind` adalah ENUM MariaDB yang tidak memuatnya; melebarkan tipenya akan membuat TypeScript meloloskan nilai yang baru gagal di tingkat database sebagai galat ENUM yang tidak menyebut sebab sebenarnya. Karena itu ada `RepeatKindPeriodik` terpisah -- tipe sempit tetap boleh masuk ke fungsi bertipe lebar, jadi kedua pemanggil tetap berbagi SATU fungsi. Melompat N hari PENUH (bukan 1 lalu N-1): jadwal "tiap 3 hari pukul 18:00" yang dibuat pukul 20:00 pertama kali jalan tiga hari lagi, bukan besok -- jarak tak seragam membuat "kenapa peringatannya datang hari ini" tidak bisa dijawab dari pengaturannya. Dijepit 2-90; 1 sudah punya namanya sendiri (`daily`), dan dua jalan menuju perilaku yang sama berarti dua tempat yang harus diperiksa saat menelusuri.

**`next_run_at` dimajukan BAHKAN saat pesannya tidak jadi dikirim.** Kalau tidak, jadwal yang gudangnya sedang aman tetap jatuh tempo pada siklus berikutnya, membaca katalog lagi, dan begitu seterusnya sepanjang hari -- persis beban yang alasan "jalan sekali sehari" ada untuk mencegahnya. **Satu pengecualian**: saat belum ada tujuan yang mencentang, `next_run_at` sengaja TIDAK maju. Itu keadaan salah setel yang bisa diperbaiki dalam hitungan detik lewat satu centang, dan memajukannya berarti peringatan hari itu hilang begitu saja; biayanya satu query ringan tiap siklus, dan katalognya belum dibaca karena pemeriksaan tujuan ada di depan.

**`farmasi_target.terima_darurat_stok` -- kolom KETIGA, dan sekali lagi terpisah.** Tabel itu kini menjawab tiga pertanyaan berbeda: `is_active` = ke mana notifikasi resep dikirim, `boleh_tanya` = siapa yang boleh membuat nomor RS menjawab, `terima_darurat_stok` = siapa yang menerima rekap persediaan. Menggabungkannya salah ke dua arah sekaligus, dan keduanya pemakaian wajar: grup shift apotek yang perlu tahu tiap resep tanpa perlu rekap tiap pagi, dan nomor kepala instalasi yang justru HANYA perlu rekap. Alasannya sama dengan yang membuat 020 memisahkan `boleh_tanya` -- dan alasan itu terbukti bukan teori: pilihan yang digabung adalah pilihan yang hilang.

**Kunci idempoten memuat waktu JATUH TEMPO (`next_run_at`), bukan `sekarang`.** `sekarang` berbeda tiap siklus, jadi jadwal yang gagal memajukan `next_run_at` akan mengirim ulang tiap menit dengan kunci yang selalu dianggap baru. `chat_id` ikut masuk, dengan alasan yang sudah dibayar di notifikasi farmasi.

Sakelarnya (`farmasi.darurat_enabled`) **default MATI**, berdiri sendiri dari `farmasi.enabled`: notifikasi resep memuat data PASIEN dan itu yang membuat sakelarnya berat, sementara peringatan persediaan tidak menyebut seorang pasien pun. RS yang memutuskan belum mau data pasien mengalir ke grup tetap boleh memakai yang ini. `farmasi.template_darurat_kosong` default KOSONG = **diam** saat gudang aman -- peringatan harian yang isinya "tidak ada apa-apa" berhenti dibaca dalam seminggu, dan sejak itu yang sungguhan ikut tidak terbaca. Jam tenang dilewati karena jamnya dipilih staf sendiri lewat `time_of_day`; menundukkannya pada jam tenang berarti diam-diam mengabaikan setelan yang baru saja mereka buat.

`{daftar_stok}` masuk `MULTILINE_VARIABLES` -- aman HANYA karena `core/stokDarurat.ts` memanggil `sanitizeValue()` sendiri untuk tiap nama barang dan satuan. `DARURAT_TEMPLATE_VARIABLES` sengaja tanpa `{nama_pasien}`/`{no_rm}`/`{no_resep}`: ketiadaannya yang menutup alasan pertama untuk mulai menggabungkan katalog dengan `resep_obat`. Grant `UPDATE`/`DELETE` untuk `stok_alert_schedule` diterapkan manual lewat root, dan sekali lagi terbukti tidak diwarisi (`ERROR 1142` sebelum, berhasil sesudah).

**Tiga jebakan verifikasi**, ketiganya kegagalan UJI bukan kegagalan produk -- yang justru penting, karena uji yang gagal karena dirinya sendiri gampang dibaca sebagai bug produk lalu "diperbaiki" ke arah yang salah:

- **Menunggu kurang dari satu interval penuh terbaca sebagai "worker tidak pernah mengambilnya".** Siklus `stok-darurat` memakai `polling.scan_interval_ms` (300 detik), dan tick pertama sesudah worker menyala bisa terjadi saat sakelarnya masih mati.
- **Pencarian tombol lewat teks mengenai tombol di dalam `<dialog>` TERTUTUP.** Halaman ini memuat tiga `<dialog>` yang selalu ada di DOM, dan `ConfirmDialog` memberi tombol konfirmasinya label bawaan "Hapus" -- sama persis dengan tombol Hapus di baris tabel, dan Puppeteer melempar `Node is either not clickable`. Penyaring visibilitas wajib, kalau tidak yang diuji adalah tombol yang tidak pernah dilihat siapa pun.
- **Asersi `!body.includes(nama)` GAGAL walau penghapusannya berhasil** -- pesan suksesnya sendiri berbunyi `Jadwal "..." dihapus.` dan memuat nama yang sedang dicari. Periksa pada baris TABELNYA, bukan seluruh halaman.

### Darurat stok: batas dicabut, dan arahnya jadi dua (migrations/022, 023)

Dua perubahan atas fitur di atas, keduanya berangkat dari pemakaian SUNGGUHAN alih-alih dari perancangan ulang.

**`max_baris` bawaannya 30 dan isiannya berhenti di 200 -- dan katalog di mesin ini punya 208 barang di bawah ambang.** Kapnya bukan teoretis; ia menggigit pada hari pertama. Bukti langsungnya ada di baris jadwal nyata: `max_baris=200` dengan `last_jumlah=201`. Angka 201 itu hasil pembacaan `max_baris + 1` yang memang ada supaya "terpotong" bisa dibedakan dari "kebetulan pas", jadi ia bukti bahwa daftarnya tergunting dan pesannya ditutup catatan "...dan 1 barang lain".

Alasan asli batas itu ("pesan 10 KB tak seorang pun membacanya sampai bawah; yang paling kritis toh sudah di atas") keliru terhadap pekerjaan yang sebenarnya: **daftar ini bukan bacaan, melainkan daftar pesanan.** Barang ke-31 tetap harus dibeli hari itu juga, dan yang tergunting justru yang paling tidak mendesak -- sehingga ketiadaannya paling sulit disadari. Nol berarti seluruhnya, dan itu kini bawaannya.

**Yang menggantikan batas itu PEMECAHAN, bukan pemotongan, dan pembedaan itu inti perubahannya.** Ada dua batas yang gampang tertukar: berapa banyak yang ingin dilihat apotek (kebijakan -- `max_baris`), dan berapa panjang sebuah pesan WhatsApp boleh (protokol -- `BATAS_KARAKTER_BAGIAN`). Menyamakan keduanya adalah kesalahan versi pertama; akibatnya kebutuhan apotek dipangkas demi batas milik WhatsApp. `pecahDaftarDarurat()` sekarang mengirim seluruh daftar sebagai beberapa pesan berturut-turut bila perlu. Empat hal yang menempel:

- **12.000 itu DIUKUR, bukan dibaca dari dokumentasi.** Pesan 13.035 karakter -- seluruh amplop yang mungkin dihasilkan angka itu, yaitu daftarnya plus pembuka/penutup template plus baris kode pengiriman -- dikirim lewat sesi sungguhan dan terbukti `sent` dalam 274 ms. Batas WhatsApp yang sebenarnya jauh di atasnya, tapi batas yang cuma dibaca adalah batas yang belum pernah gagal di hadapan kita, dan kegagalannya datang sebagai pesan yang dipotong DIAM oleh pihak yang jauh -- bukan sebagai galat yang bisa ditangkap. Daftar 208 barang berukuran 9.277 karakter, jadi dalam keadaan normal tetap SATU pesan; pemecahan adalah jaring pengaman.
- **Satu penurunan, bukan dua.** `formatDaruratStok()` kini cuma `pecahDaftarDarurat(r, Infinity)[0]`. Dua fungsi yang sama-sama merangkai daftar ini pasti menyimpang, dan yang muncul saat menyimpang bukan galat melainkan dua bentuk pesan berbeda dari satu sistem.
- **Judul kelompok diulang di tiap bagian, ditandai "lanjutan".** Bagian kedua yang dibuka deretan butir tanpa keterangan tidak bisa dibaca -- pembacanya tidak tahu apakah yang dilihatnya barang habis atau menipis, padahal justru itu yang menentukan mana yang dikerjakan lebih dulu.
- **BAGIAN di luar, TUJUAN di dalam** pada perulangan enqueue. Terbalik, seluruh bagian ke grup pertama terkirim sebelum grup kedua menerima apa pun. `turunkanKunciBagian()` memberi tiap bagian kuncinya sendiri, dan **bagian pertama memakai kunci dasarnya apa adanya** -- kalau tidak, pemeriksaan penyerahan-ulang di `handleInboundMessage` (yang mencari kunci dasar) selalu meleset dan satu restart worker membanjiri penerimanya dengan jawaban lama.

**Migrasi 023 ada karena 022 melewatkan kasus yang paling jelas.** 022 membebaskan `max_baris = 30` -- bawaan kolom, yang tidak pernah dipilih siapa pun. Yang terlewat justru 200: itu bukan penilaian bahwa dua ratus baris cukup, melainkan satu-satunya cara meminta "sebanyak yang sistem izinkan". Hanya 200 yang dibebaskan, bukan "semua yang di atas 100" -- jadwal yang disetel 10 atau 50 memang meminta rekap pendek, dan mengubahnya membuang keputusan yang sungguh diambil.

**Arah MASUK: rekapnya kini bisa DITANYAKAN** (`cobaBalasDarurat` di `worker/stokReply.ts`). Keadaan yang paling sering menimbulkan pertanyaan adalah di antara dua jadwal -- "yang tadi pagi sudah dibeli, sekarang tinggal apa lagi". Balasan stok (019) menjawab satu barang; yang belum ada adalah rekapnya. Lima hal yang menempel:

- **TIDAK ada mode `semua`, dan itu bukan kelalaian.** Balasan stok boleh dibuka untuk umum karena setara daftar harga di loket -- pasien memang perlu tahu apakah obatnya ada. Rekap ini kebalikannya: daftar kekurangan gudang, informasi kerja internal yang tidak menjawab satu pun pertanyaan yang wajar diajukan pasien. Penanya WAJIB terdaftar `boleh_tanya`, perorangan maupun grup, apa pun `farmasi.stok_mode`.
- **Frasa, bukan kata tunggal.** Kata "stok" sendirian sudah milik pencarian satu obat. Frasa diperiksa dari yang TERPANJANG lebih dulu -- kalau tidak, frasa pendek yang jadi bagian frasa panjang menang dan sisa katanya ikut memuat kata dari frasa yang sebenarnya cocok.
- **Sisa kata yang berarti MEMBATALKAN kecocokan.** "stok habis paracetamol" bukan permintaan rekap; menjawabnya dengan 208 barang adalah jawaban percaya-diri-dan-keliru yang sama jenisnya dengan `detectPoli()` yang menebak saat ambigu. Dibatalkan, pertanyaannya jatuh ke balasan stok yang memang tahu cara mencari nama obat. Konsekuensinya `KATA_PENGAPIT` diperluas dengan partikel percakapan ("dong", "deh", "daftar", "habis", ...) -- tanpa itu "rekap stok dong" berhenti dibaca sebagai permintaan rekap hanya karena satu kata.
- **Gudang aman TIDAK boleh dijawab dengan diam.** Jalur terjadwal memperlakukan "Pesan saat aman" yang kosong sebagai sengaja diam, dan itu benar di sana. Di sini ada orang yang baru saja bertanya; `JAWABAN_GUDANG_AMAN` menggantikannya -- alasan yang sama persis dengan AUTO_REPLY yang melewati jam tenang.
- **Urutan ditetapkan di SATU tempat, `cobaBalasPersediaan()`.** Rekap lebih dulu (frasanya lebih spesifik; "stok menipis" memuat kata "stok"), lalu pencarian satu obat. Dua pemanggil memakainya -- perorangan dan grup -- dan masing-masing menentukan urutannya sendiri adalah persis bentuk kegagalan yang sudah dibayar di `respectsOptOut()` dan `kunciPesanMasuk()`.

`farmasi.darurat_tanya` **default MENYALA**, berbeda dari sakelar-sakelar lain, dan itu bukan kelalaian: yang menahan seluruhnya tetap `farmasi.darurat_enabled` yang mati. Kunci ini ada untuk MEMATIKAN arah masuk, bukan menambah satu langkah lagi sebelum fiturnya bisa dipakai. Menyalakan tanya tanpa satu pun frasa ditolak saat disimpan -- kalau tidak ia mati DIAM: tidak ada yang pernah cocok, dan yang terlihat cuma sakelar bercentang.

**Jebakan verifikasi keempat, dan ia bentuk baru dari yang sudah tercatat:** percobaan pertama uji HTTP gagal pada pagar anti-build-lama. Sebabnya BUKAN `npm run build` yang belum jalan, melainkan **proses `next start` sisa dari sesi berjam-jam sebelumnya** yang masih memegang `127.0.0.1:3199`. Proses baru tetap menyala tanpa `EADDRINUSE` karena ia mengikat `0.0.0.0:3199` -- dua listener hidup berdampingan, dan koneksi ke `127.0.0.1` dimenangkan yang lebih spesifik, yaitu yang LAMA. `netstat -ano | Select-String ":3199"` menampilkan dua baris LISTENING dengan PID berbeda; `Get-Process -Id <pid> | Select StartTime` yang membuktikannya (14:19 vs 18:19). Pelajarannya: memakai port sendiri saja tidak cukup, port itu harus dipastikan KOSONG lebih dulu -- dan pagar "kalau penanda fitur baru tidak ada, `exit 2`" adalah satu-satunya alasan ini ketahuan alih-alih jadi belasan "kegagalan" atas kode yang benar.

### `/farmasi` dipecah jadi TAB -- dan rujukan spasial yang ikut jadi salah

Halaman ini tumbuh jadi empat bagian yang berdiri sendiri (satu daftar tujuan bersama + tiga fitur bersakelar sendiri), ditumpuk vertikal. Terukur di peramban: **5.808 px** sekali gulung, dan yang paling jarang disentuh (isi pesan) mendorong yang paling sering dilihat (jadwal darurat stok) ke dasar halaman. Sekarang `?tab=tujuan|resep|stok|darurat`; tab terpanjang **1.774 px**.

**Lewat URL, bukan state klien**, dan itu bukan selera: bagian yang tidak dibuka tidak di-query sama sekali -- termasuk `daftarJenisBarang()` yang menyentuh `sik`, kolam yang sengaja dibatasi `pool.max: 2` supaya tidak berebut dengan SIMRS yang sedang melayani pasien. Dibuktikan lewat HTML: dropdown "Semua jenis" TIDAK ada di ketiga tab lain. Gratis pula: bisa dibagikan sebagai tautan, dan tombol maju/mundur peramban bekerja.

Lima hal yang menempel:

- **`components/ui/Tabs.tsx` sengaja BUKAN `role="tablist"`.** Kontrak ARIA untuk tab menjanjikan panel bertukar DI DALAM dokumen yang sama tanpa navigasi, plus panah kiri/kanan berpindah tab. Ini tautan -- ia benar-benar bernavigasi dan panah tidak melakukan apa pun. Menandainya `tablist` berarti menjanjikan perilaku yang tidak ada kepada orang yang paling bergantung pada janji itu. Yang benar untuk bentuk ini adalah `<nav>` + `aria-current="page"`.
- **Titik status di tab menggantikan gulungan.** Tiga keadaan, bukan dua: mati, menyala, dan **menyala tapi setengah jadi** -- yang ketiga itulah yang mahal, karena bergejala sama persis dengan yang benar (halaman tampak wajar, nol pesan keluar). Sebelumnya keadaan itu hanya terbaca sesudah menggulir ke bagiannya; kini terlihat tanpa membuka tabnya dan tanpa memakan satu baris pun ruang vertikal. Warna saja tidak pernah cukup (WCAG 1.4.1), jadi tiap titik membawa `title` + `sr-only`.
- **Rujukan spasial wajib ikut diperbaiki, dan ini bagian yang paling gampang terlewat.** "Tambahkan tujuan **di bawah**" benar selama halaman satu gulungan; sesudah ditab ia menunjuk ke tempat yang tidak ada di layar, dan staf mencarinya dengan menggulir alih-alih pindah tab. Enam kalimat di `MasterSwitch`/`StokForm`/`DaruratForm` diubah jadi nama tab, tiga di antaranya jadi tautan sungguhan. Kegagalannya tidak menghasilkan satu pun galat -- cuma instruksi yang salah.
- **`components/ui/Callout.tsx` melipat prosa panjang lewat `<details>` asli** (nol JS, bisa keyboard, dibuka sendiri saat kena Ctrl+F). Syarat yang mengikat: **judulnya harus utuh sendirian**, karena cuma judul yang selalu terlihat -- judul memuat KESIMPULAN, isinya memuat ALASAN. Peringatan "pesan ini berisi data pasien" sengaja **tidak** dilipat: ia harus dibaca sebelum sakelarnya dinyalakan, dan melipatnya menukar halaman yang lebih pendek dengan keputusan yang diambil tanpa keterangan.
- **Urutan di tab Darurat dibalik jadi jadwal → alat → isi pesan.** Urutan lama adalah urutan MENULIS fiturnya, bukan urutan MEMAKAINYA. Dibalik lewat urutan DOM, bukan `order-*` CSS -- urutan visual yang beda dari urutan DOM membuat Tab keyboard dan pembaca layar melompat-lompat.

**Satu bug ikut terperbaiki, dan ia bug yang sama yang komentar di sebelahnya sudah menjelaskan.** `adaTargetAktif` dulu dihitung `barisTarget.some((t) => t.isActive)` -- dari SATU halaman paginasi 25 baris. Tujuan aktif di halaman kedua tidak terhitung, `MasterSwitch` lalu memperingatkan "belum ada tujuan yang aktif" padahal ada, dan staf mengaktifkan tujuan KEDUA untuk membungkamnya sehingga grup menerima dua pesan per resep. `jumlahTujuanDarurat` sudah memakai `count()` penuh justru karena ini -- perbaikannya tidak pernah menyeberang ke tetangganya. Kini keempat angka penyalaan peringatan dihitung dari seluruh tabel.

**Jebakan verifikasi kelima, dan ia jenis yang paling menyesatkan: uji yang GAGAL karena dirinya sendiri.** Dua asersi browser melaporkan Server Action rusak selama beberapa putaran. Sebabnya `waitForFunction` menunggu atas `document.body.innerText` -- dan teks yang ditunggu (`barang di bawah ambang`, `balasan stok`) sudah ada di teks STATIS halaman (label "Pesan saat tidak ada barang di bawah ambang"). Syaratnya terpenuhi seketika, tunggu 120 detik berubah jadi nol detik, dan asersinya membaca form yang tombolnya masih bertuliskan "Membaca...". Tiga hipotesis lebih dulu dibuang lewat percobaan terkendali (waktu tunggu, hidrasi React, kolam `sik`) -- fungsinya sendiri ternyata membalas dalam **520 ms**. Pelajarannya: **kondisi tunggu dan asersi wajib dibatasi ke elemen yang sedang diuji, bukan ke `<body>`**; di halaman yang memang menjelaskan dirinya panjang lebar, teks statis nyaris selalu memuat kata yang sedang ditunggu. Dan `.catch(() => {})` pada `waitForFunction` menelan bukti -- ia harus mencetak sebabnya.

### Kelas ketujuh dan kedelapan: BPJS (`/bpjs`, migrations/024) -- satu kanal, dua arah berlawanan

`/bpjs` (admin-only) membaca kanal BPJS, bukan alur kerja internal Khanza. Dua pemicu di satu halaman karena sumber datanya satu, tapi keduanya **tidak berbagi apa pun selain daftar tujuan**:

| Pemicu | Sumber | Penerima | Kelas |
|---|---|---|---|
| `BPJS_BATAL` | `referensi_mobilejkn_bpjs_batal` | grup/petugas LOKET | pindai, tiap siklus rapat |
| `BPJS_KONTROL` | `bridging_surat_kontrol_bpjs` | **PASIEN** | waktu, sekali sehari H-N |

**Prefix `nobooking` ADA dan tetap tidak boleh dipakai sebagai pemangkas** -- ini bagian yang paling menggoda untuk "diperbaiki". Ia berformat `YYYYMMDD` + 6 digit (`20260107000014`), persis sekelas `no_rawat`/`no_resep`, jadi §4.4 tampak berlaku apa adanya. Tapi yang disandikannya tanggal **JANJI**, bukan tanggal **PEMBATALAN**. Diukur atas 1.808 baris: 506 dibatalkan sebelum hari janji, 1.158 pada harinya, dan **144 SESUDAHNYA -- sampai 105 hari**. Baris terakhir itulah yang mematikannya: pembatalan yang tercatat hari ini bisa menunjuk booking 105 hari lalu, sehingga `nobooking >= prefix(hari ini - 30)` membuangnya. Yang terjadi bukan galat melainkan pemberitahuan yang tidak pernah dikirim, tanpa satu baris `outbox` pun yang menandainya. Karena itu **pemindaian penuh yang disengaja**, dan yang membuatnya bisa diterima adalah LAJU TUMBUHNYA (~2,8 baris/hari -- tabel ini bertambah hanya saat ada yang membatalkan), bukan ukurannya hari ini.

**`bridging_surat_kontrol_bpjs` juga dipindai penuh, dan di sini memang tidak ada jalan keluar.** PK-nya `no_surat` (`0055S0010126K000204`) memuat tanggal sebagai `0126` = MMYY di tengah string -- tidak terurut leksikal antar tahun, jadi tidak bisa jadi pemangkas rentang sama sekali. Masuk lewat `bridging_sep` lebih buruk (27.484 baris berbanding 18.843, dan jarak `tgl_surat`→`tgl_rencana` mencapai dua bulan). Diterima karena jalannya **sekali sehari**: diukur ~35 ms untuk join penuh. SATU query untuk seluruh selisih hari lewat `IN (:tanggalTarget)` -- bentuk per-selisih berarti dua pemindaian penuh saat staf menyetel "7,1", dan biayanya bertambah tiap pengingat ditambahkan.

**`maping_poli_bpjs` WAJIB dilewati, dan melewatkannya gagal DIAM.** Kode poli BPJS dan kode poli Khanza hidup di ruang nama berbeda yang kebetulan bertabrakan: BPJS `INT` memetakan ke Khanza `U0003`, sementara `poliklinik` punya barisnya sendiri ber-`kd_poli = 'INT'`. Join langsung `poliklinik.kd_poli = kodepoli` karena itu **cocok, tapi ke poli yang salah** -- dan `checkPrivacy()` lalu memeriksa daftar poli sensitif terhadap kode yang bukan miliknya. Tidak ada galat; yang muncul cuma perlindungan yang diam-diam tidak berlaku.

**Tabel surat kontrol adalah kasus privasi paling tajam di proyek ini.** Ia punya ~45 kolom dan sebagian besar rekam medis telanjang: `status_prb` berisi diagnosis kronis apa adanya (`01. Diabetes Melitus`, `06. Skizofrenia`, `09. SLE`), plus HBA1C, GDP, eGFR, LDL, tekanan darah, `JantungKoroner`, `HamilMenyusui`; `bridging_sep` yang di-join menyimpan `diagawal`/`nmdiagnosaawal`. Query-nya mengambil **sembilan kolom, tidak satu pun klinis**. Ditegakkan dua lapis dengan alasan berbeda: `BPJS_KONTROL_TEMPLATE_VARIABLES` tidak punya variabelnya (itu yang dilihat orang saat menyusun template), dan query-nya tidak pernah men-`SELECT` kolomnya (itu yang menentukan datanya sampai ke proses ini atau tidak). Dibuktikan pada **objek barisnya**, bukan dengan membaca SQL -- `npm run dryrun:bpjs` mencetak `Object.keys()` baris sungguhan.

**Nomor pasien untuk pengingat kontrol punya CADANGAN, dan cadangan itu sengaja tidak ditulis ke `patient_contact`.** Urutannya: koreksi manual → `pasien.no_tlp` → `bridging_sep.notelep`. Tingkat ketiga hanya berlaku untuk pesan itu saja. Menulisnya ke `patient_contact` akan membuat baris pasien yang sama berbolak-balik antara "terpakai" dan "bermasalah" tergantung pemicu mana yang terakhir menyentuhnya -- dan `/nomor-bermasalah`, yang justru ada untuk menunjukkan apa yang perlu dibetulkan petugas, berhenti bisa dipercaya. Bukan optimasi spekulatif: **618 dari 18.843 surat** milik pasien ber-`no_tlp` tak terpakai, dan **602 di antaranya (97%)** punya nomor sah di SEP.

**Jam tenang dan opt-out BERBEDA antar keduanya, dan itu seluruh inti pemisahannya.** `BPJS_BATAL` melewati jam tenang (penerimanya staf, dan slot yang batal sering untuk besok pagi -- pembatalan 21.30 yang baru sampai 07.00 tiba bersamaan pasiennya) dan tidak terikat daftar tolak (tidak ada nomor pasien untuk dicocokkan). `BPJS_KONTROL` **tunduk pada keduanya** -- ia satu-satunya pesan di halaman ini yang dibaca pasien. Konsekuensi yang wajib ikut: `OPT_OUT_CONFIRMATION` di `wa-client.ts` sekarang menyebut "pengingat kontrol BPJS", dan `bpjs.template_kontrol` berakhiran frasa berhentinya seperti ketujuh template pasien. Janji yang dibaca pasien tidak boleh lebih sempit dari yang dijalankan mesin -- di sini arahnya kebalikan dari biasanya, dan sama-sama salah.

**Jadwal hariannya TIDAK memakai node-cron, dan itu perbaikan yang disengaja atas pola BOOK_REMIND.** `startScheduler()` membaca `schedule.book_remind_hour` **sekali** saat worker mulai, jadi mengubah jamnya lewat dashboard tidak berlaku sampai ada yang menyalakan ulang worker -- tanpa satu pun tanda bahwa setelan barunya belum aktif. `runBpjsKontrolIfDue()` memeriksa kejatuhtempoannya tiap siklus pindai dan membaca `bpjs.kontrol_jam` ulang tiap kali. Penanda hariannya (`bpjs.kontrol_last_run`) **cuma penghemat query, bukan penentu kebenaran**: yang mencegah kirim ganda adalah kunci idempoten, ditegakkan `uq_idem` di mesin database.

**Penanda itu dimajukan SESUDAH pekerjaannya berhasil, dan hanya kalau berhasil -- versi pertama salah di sini.** Menulisnya lebih dulu tampak lebih aman (ia menjamin pembacaan 18 ribu baris tidak terulang), dan alasan itu ditulis di komentar sebelum sempat dihitung. Begitu dihitung, biaya yang dihindarinya ternyata tidak ada: siklusnya tiap `polling.scan_interval_ms` (**5 menit**, bukan 1 menit seperti yang saya kira saat menulisnya) dan satu pembacaan terukur ~35 ms, jadi mengulanginya sepanjang hari berjumlah sekitar **sepuluh detik** waktu database. Yang dibayar sebagai gantinya jauh lebih mahal: satu kegagalan sesaat -- MariaDB sedang terkunci SIMRS, jaringan berkedip -- menghapus pengingat SEHARIAN bagi semua pasien yang kontrol besok, tanpa percobaan kedua. Karena itu `pollBpjsKontrol` yang gagal **melempar ulang** alih-alih menelan galatnya: penelanan itulah yang membuat pemanggil tidak bisa membedakan "tidak ada yang jatuh tempo" dari "tidak sempat dibaca". Mencoba ulang aman justru karena kunci idempotennya -- pesan yang telanjur masuk `outbox` ditolak `uq_idem` pada percobaan berikutnya.

**Kunci idempoten kontrol memuat TIGA bagian**: `no_surat` (satuan yang benar), `tgl_rencana` (tanggalnya bisa direvisi -- tanpa ini surat yang dijadwalkan ulang tidak pernah diingatkan lagi), dan **selisih harinya** (setelan "7,1" harus menghasilkan dua pengingat; tanpa ini yang kedua ditolak sebagai duplikat, diam-diam, dan yang terlihat cuma "pengingat H-1 tidak jalan").

`bpjs_target` adalah **tabel sendiri, bukan kolom keempat di `farmasi_target`**. Bentuk barisnya identik dan validasinya memang dipakai bersama (`core/farmasiTarget.ts`), tapi halaman `/farmasi` menampilkan SELURUH baris tabel itu sebagai "tujuan apotek": grup pendaftaran akan muncul di sana berikut tiga centang yang tidak berlaku baginya, dan menghapusnya dari halaman itu diam-diam mematikan notifikasi BPJS yang tidak ditampilkan di sana. Alamat yang sama boleh ada di kedua tabel -- itu dua keputusan berbeda yang kebetulan menuju alamat yang sama. Dua centangnya (`terima_batal`, `terima_kontrol`) terpisah dengan alasan yang sudah dibayar di 020/021: grup pendaftaran sangat wajar perlu tahu pembatalan tanpa ikut menerima salinan tiap pengingat.

**`npm run dryrun:bpjs -- <database> [tanggal]` ada karena kedua tabel ini sering KOSONG** di instalasi yang baru menyalakan bridging Mobile JKN (termasuk `alca` di mesin ini), sementara arsip berisi riwayatnya ada di database lain. Tanpa cara mengarahkan ke sana, satu-satunya "bukti" adalah nol baris -- yang tidak membedakan "query benar, data memang belum ada" dari "query salah". Nama databasenya di-override **sesudah** `lib/env` memuat `.env` (yang menimpa `process.env`), lalu modulnya diimpor **dinamis**; mengubahnya jadi `import` biasa di puncak berkas membuat override-nya tidak berpengaruh sama sekali, dan gejalanya bukan galat melainkan hasil dari database yang salah. `varsBatal`/`varsKontrol` diekspor dari `bpjsRunner.ts` dan dipakai bersama `poll:dryrun` -- pelajaran `worker/triggerVars.ts`, diterapkan sejak awal alih-alih menunggu penyimpangannya terjadi.

Sakelarnya bertingkat: `bpjs.enabled` (utama, default MATI) menahan keduanya, lalu `bpjs.batal_enabled` dan `bpjs.kontrol_enabled` sendiri-sendiri. `bpjs.kontrol_ke_pasien` boleh dimatikan supaya pengingat hanya masuk ke tujuan yang dicentang -- padanan `template.tujuan_mode = 'tujuan'` -- tapi **ditolak saat disimpan** selama belum ada tujuan seperti itu, karena pesannya lalu tidak pergi ke mana pun tanpa meninggalkan satu baris `outbox` pun. Grant `UPDATE`/`DELETE` untuk `bpjs_target` diterapkan manual lewat root, dan untuk kelima kalinya terbukti tidak diwarisi (`ERROR 1142` sebelum, berhasil sesudah).

### PERMINTAAN lab & radiologi (`migrations/025`) -- pasangan RESULT_READY dari ujung yang lain

Dua pemicu pasien baru, dan bentuknya paling gampang dipahami sebagai pasangan yang sudah ada:

| | Kapan | Yang dikatakan ke pasien |
|---|---|---|
| `LAB_REQUEST` / `RAD_REQUEST` | dokter MEMESAN pemeriksaan | "ada yang harus Anda jalani" |
| `RESULT_READY` | hasilnya selesai | "hasilnya sudah bisa diambil" |

Sampai `migrations/025` hanya ujung yang kedua ada, dan ketiadaan yang pertama punya akibat konkret: pasien rawat jalan yang pulang tanpa menyadari ada permintaan lab akan datang lagi hanya untuk itu, dan bagian penunjang tidak pernah tahu ada pekerjaan masuk sampai pasiennya muncul di loket.

**DUA kode pemicu, bukan satu -- dan ini KEBALIKAN dari keputusan RESULT_READY.** Di sana lab dan radiologi berbagi satu `trigger_code` (dibedakan hanya oleh dua watermark di `poll_cursor`), karena pesannya memang sama dan `{jenis_layanan}` cukup membedakannya. Yang menuntut pemisahan di sini bukan isi pesannya melainkan **tujuannya**: sejak `template_target` (018), tujuan tambahan dipasang per `trigger_code`, jadi satu kode bersama berarti grup Laboratorium dan grup Radiologi tidak bisa dipisahkan -- keduanya menerima setiap permintaan, termasuk yang bukan pekerjaannya. Akibat sampingan yang kebetulan menguntungkan: karena kodenya berbeda, watermarknya berbeda dengan sendirinya, jadi tidak ada `cursorKey` terpisah yang bisa salah dipasangkan.

**Kunci idempoten per `noorder`, BUKAN per (no_rawat, tanggal) seperti RESULT_READY**, dan bedanya lahir dari bentuk tabelnya. `periksa_lab` berisi satu baris per ITEM pemeriksaan, sehingga panel darah lengkap menghasilkan belasan baris untuk satu kunjungan dan wajib digabung supaya pasien tidak menerima belasan WhatsApp. `permintaan_lab` sudah satu baris per PERMINTAAN (`noorder` PK), jadi penggabungan yang sama justru salah: dua permintaan terpisah pada hari yang sama -- yang memang terjadi saat dokter menambah pemeriksaan susulan -- akan menyusut jadi satu pesan, dan yang kedua tidak pernah diberitahukan.

**Pemangkasnya `no_rawat` BERIKUT MARGIN 90 hari, dan margin itu bukan kehati-hatian melainkan pengukuran.** `no_rawat` menyandikan tanggal KUNJUNGAN sementara kejadiannya `tgl_permintaan`, dan keduanya tidak selalu sehari: diukur atas 4.636 baris, **4.631 pada hari yang sama dan 5 sampai 61 hari SESUDAHNYA**. Arahnya selalu maju (tidak ada permintaan yang mendahului kunjungannya), jadi yang perlu dilebarkan hanya batas bawahnya. Tanpa margin, permintaan yang dibuat hari ini atas kunjungan dua bulan lalu jatuh di luar prefix dan hilang tanpa satu pun galat -- kelas kegagalan yang sama persis dengan prefix `nobooking` pada pembatalan BPJS, hanya jauh lebih jarang.

**`noorder` sebenarnya pemangkas yang EKSAK, dan sengaja tidak dipakai.** Formatnya `PK202612310001` dan ia cocok sempurna dengan `tgl_permintaan` -- 0 dari 4.636 meleset. Yang menghalangi: awalan hurufnya tidak bisa dipastikan untuk radiologi, karena `permintaan_radiologi` **kosong di kedua database di mesin ini**, jadi "PR" cuma tebakan. Memakai pemangkas berbeda untuk dua pemicu kembar adalah bentuk penyimpangan yang sudah berkali-kali dibayar di proyek ini; kalau suatu saat awalan radiologi terbukti, keduanya boleh pindah BERSAMA.

**Izin pindai penuh yang alasannya BERBEDA dari tiga izin lain, dan karena itu jangan ditiru begitu saja.** `booking_registrasi` boleh dipindai karena kelas pemicunya memang pindai; `dokter` dan `databarang` karena tabel konfigurasi/katalog. `permintaan_lab` jelas tumbuh seiring pasien. Yang terjadi di sini: query-nya BENAR dan memakai indeks pada volume nyata, tapi optimizer memilih pindai penuh selagi tabelnya kecil -- dan di database produksi (`alca`) ia baru berisi 74 baris. Dibuktikan dengan menjalankan query yang SAMA terhadap dua database: `alca` 74 baris → `type=ALL`; `sik` 4.636 baris → `type=range, key=no_rawat`. Jadi pindai penuhnya keputusan optimizer yang benar dan akan berhenti sendiri. **`maxRows` yang jadi penjaga sebenarnya**, bukan izin itu.

**Privasi: dua kolom yang wajib tidak pernah disentuh, dan keduanya ada di tabel yang sama.** `diagnosa_klinis` (dugaan diagnosis dokter yang meminta -- di database ini terisi, mis. "kontrol gula") dan `informasi_tambahan`. Query-nya tidak men-`SELECT` keduanya sama sekali, jadi merendernya bukan terlarang melainkan MUSTAHIL (§5.2) -- prinsip yang sama dengan `status_prb` pada surat kontrol BPJS. `kd_jenis_prw` diambil sebagai KODE dan hanya untuk `checkPrivacy()`; nama pemeriksaannya tidak pernah ikut, dan `jumlah_item` juga tidak (§4.3: banyaknya pemeriksaan pun petunjuk medis).

**`{nama_dokter}` ADA di sini dan TIDAK ada di RESULT_READY**, dan itu bukan kelalaian di salah satunya: pada hasil, dokter pemeriksanya tidak menambah apa-apa bagi pasien; pada permintaan, "dokter siapa yang menyuruh" adalah yang membuat pesannya masuk akal alih-alih tampak seperti salah kirim. Diambil dari `dokter_perujuk`. `{tanggal}`/`{jam}` adalah waktu PERMINTAANNYA dibuat, bukan jadwal pemeriksaan -- Khanza tidak menyimpan jadwal untuk ini.

Keduanya terikat daftar tolak (`OPT_OUT_TRIGGERS`) dan tunduk jam tenang, seperti pemicu pasien lain -- pasangan yang satu terikat sementara satunya tidak akan jadi janji yang mustahil dijelaskan. `OPT_OUT_CONFIRMATION` ikut berubah menyebut "permintaan & hasil pemeriksaan". Bawaannya `is_active = 0`: worker berjalan begitu barisnya aktif, dan baris aktif yang termigrasi diam-diam akan mengirim SELURUH permintaan sebulan terakhir sekaligus (`polling.lookback_days`).

**`permintaan_radiologi` kosong di kedua database, jadi RAD_REQUEST TIDAK pernah terbukti terhadap satu baris data pun.** Query-nya benar secara struktur (EXPLAIN `range no_rawat`, bentuk SQL-nya identik dengan lab yang terbukti atas 4.636 baris), tapi itu bukan hal yang sama dengan terbukti. Kemungkinan besar rumah sakit ini memang belum memakai modul radiologi Khanza; kalau nanti dipakai, **periksa lebih dulu bahwa barisnya benar-benar terbaca** sebelum menyalakan templatenya -- dan awalan `noorder`-nya bisa dipastikan pada saat yang sama.

### PENGINGAT KONTROL non-BPJS (`migrations/032`) -- padanan BPJS_KONTROL dari sisi Khanza sendiri

Pemicu pasien ke-11, dan satu-satunya yang lahir dari **menu Khanza yang namanya nyaris sama dengan menu lain**. Khanza punya DUA:

| Menu | Kelas Java | Tabel | Ditangani |
|---|---|---|---|
| **Surat Kontrol** | `surat/SuratKontrol.java` | `skdp_bpjs` | `KONTROL_ULANG` (ini) |
| Surat Kontrol VClaim | `bridging/BPJSSuratKontrol.java` | `bridging_surat_kontrol_bpjs` | `BPJS_KONTROL` (024) |

Akhiran `_bpjs` pada tabel yang pertama peninggalan sejarah (SKDP = Surat Keterangan Dalam Perawatan) dan **menyesatkan** -- isinya dipakai untuk pasien mana pun, dan justru pasien non-BPJS yang tidak punya jalur pengingat lain. Terukur di arsip: 252 BPJS, 1 UMUM -- karena pada awal 2024 RS ini masih memasukkan pasien BPJS lewat menu itu, sebelum bridging VClaim dipakai.

**Baris `template` biasa, BUKAN halaman sendiri seperti `/bpjs`** -- dan itu yang membuat seluruh kebijakannya gratis. Ia dikelola di `/template` (bagian "Template pemicu otomatis"), sehingga sakelarnya `is_active`, dan tujuan tambahan per pemicu (`template_target`), daftar tolak, jam tenang, serta penggantian poli sensitif berlaku tanpa satu baris kode tambahan. Jadwalnya di `app_setting` (`schedule.kontrol_ulang_*`), padanan `schedule.book_remind_hour` milik BOOK_REMIND.

**Seluruh matematika penjadwalannya DIPAKAI BERSAMA dengan BPJS_KONTROL** (`core/bpjs.ts`: `bacaHariSebelum`, `sasaranKontrol`, `labelSisaHari`, `jatuhTempoHarian`), bukan disalin. Dua penurunan untuk "kapan H-N jatuh tempo" pasti menyimpang, dan yang muncul saat menyimpang bukan galat melainkan dua pengingat berbeda hari dari satu sistem. `tahunDariTanggal()` ikut tinggal di sana walau hanya pemicu ini yang memakainya -- ia matematika tanggal murni, dan modul `khanza/` menarik koneksi database sehingga tidak bisa diuji unit.

**Pemangkasnya `tahun`, dan ia EKSAK -- kasus paling bersih di proyek ini.** PRIMARY KEY-nya `(tahun, no_antrian)`, dan `tahun` diisi Khanza dari tahun kotak Tanggal Periksa yang SAMA yang mengisi `tanggal_datang` (`SuratKontrol.java`) -- satu sumber, dua kolom, jadi tidak bisa menyimpang. Diukur atas 275 baris di tiga database: **0 meleset, 0 NULL**. Bandingkan prefiks `no_faktur` pengadaan (9 dari 910 menyimpang) dan prefiks `nobooking` pembatalan BPJS (144 dari 1.808, sampai 105 hari -- yang justru membuatnya tidak boleh dipakai). Tidak ada margin yang perlu ditambahkan. Diserahkan sebagai **larik**: setelan "7,1" pada 28 Desember menyasar dua tahun sekaligus, dan satu tahun saja membuang yang seberang tanpa galat.

**TANPA izin pindai penuh, dan yang paling layak dicatat: `booking_registrasi` pun tidak.** Tabel itu satu-satunya yang punya izin pindai penuh yang disengaja (§4.4), tapi izin itu ada karena BOOK_CONFIRM memangkasnya lewat `tanggal_periksa >= today` yang tidak terindeks; di sini ia dimasuki lewat PRIMARY KEY-nya sendiri dan keduanya terisi. EXPLAIN: `s` = `ref PRIMARY`, keempat join = `eq_ref` -- **termasuk terhadap `alca` yang tabelnya nol baris**, justru keadaan yang membuat `sks` dan `permintaan_lab` jatuh ke pindai penuh dan perlu izin sementara.

**Privasi: ENAM kolom yang tidak pernah disentuh, dan keenamnya tercetak di surat kertasnya.** `diagnosa`, `terapi`, `alasan1`, `alasan2`, `rtl1`, `rtl2` -- `report/rptSuratSKDPBPJS.jrxml` memakai `$F{temp4}`..`$F{temp9}` untuk mencetak semuanya. Surat kertas diserahkan ke satu orang di loket; pesan WhatsApp diteruskan tanpa batas. Query-nya tidak men-`SELECT` satu pun, jadi merendernya bukan terlarang melainkan MUSTAHIL (§5.2). Dibuktikan pada `Object.keys()` baris hasilnya lewat `npm run dryrun:kontrol`, bukan dengan membaca SQL.

**`status = 'Menunggu'` WAJIB.** Enum tiga nilai ('Menunggu', 'Sudah Periksa', 'Batal Periksa'); terukur 151 berbanding 102 di arsip. Mengingatkan pasien yang sudah datang bukan sekadar mubazir -- ia membuat orang datang untuk kedua kalinya. Pelajaran `p.status='1'` pada jadwal dokter.

**TABRAKAN DENGAN BOOK_REMIND -- ini yang paling penting sebelum menyalakannya.** Khanza punya setelan `JADIKANBOOKINGSURATKONTROL` di **`setting/database.xml`, bukan tabel**, jadi tak terlihat dari wakhanza sama sekali. Bila `yes`, setiap surat kontrol JUGA menulis satu baris `booking_registrasi`. Di mesin ini nilainya `yes` dan terukur **253 dari 253** surat punya bookingnya -- artinya BOOK_CONFIRM dan BOOK_REMIND sudah menyentuh pasien yang sama, dan menyalakan keduanya berarti dua pesan untuk satu kunjungan. Bentuk kegagalan yang sama yang membuat SURAT PEMESANAN sengaja tidak memberitakan kedatangan barang.

Sengaja **TIDAK dipagari mesin**: keduanya sah dipakai sendiri-sendiri, dan di instalasi yang setelannya `no` justru pemicu inilah satu-satunya yang memberi tahu pasien -- itu lubang yang sesungguhnya ditutupnya. Yang ada adalah peringatan di `/template`, dan bentuknya berubah menurut keadaan: **terbentang dan kuning saat KONTROL_ULANG dan BOOK_REMIND sama-sama aktif**, terlipat dan netral di luar itu. Melipatnya pada keadaan yang merugikan pasien akan menukar halaman yang lebih pendek dengan pasien yang menerima dua pesan tanpa seorang pun tahu kenapa.

**`{nama_poli}` sengaja TIDAK ada di template bawaannya**, walau variabelnya tersedia. Poli tidak disimpan di `skdp_bpjs`; satu-satunya jalan adalah `booking_registrasi` yang cuma ada bila setelan Khanza di atas menyala. Di instalasi yang mati, baris "Poli : {nama_poli}" jadi "Poli : " pada SETIAP pesan -- label menggantung yang terbaca sebagai sistem rusak, pelajaran yang sama persis dengan sakelar nilai hibah (031). **Akibat lanjutan yang wajib disadari**: tanpa poli, `checkPrivacy()` memperlakukan barisnya sebagai aman (`if (input.kdPoli && ...)`), jadi penggantian pesan generik untuk poli sensitif diam-diam tidak berlaku. Runner-nya menghitung dan mencatat `warn` berapa baris yang kehilangan poli justru supaya keadaan itu punya suara.

**`{no_surat_kontrol}` TERPISAH dari `{no_antrian}` yang sudah ada**, walau kolom Khanza-nya sama-sama bernama `no_antrian`: yang lama nomor antrian pendaftaran pada QUEUE_REG. Kolomnya kebetulan bernama sama, artinya bagi pasien sama sekali tidak. Kunci idempotennya memuat `tahun`-`no_antrian`, tanggal kontrol, dan selisih harinya -- `tahun` wajib ikut karena `no_antrian` cuma urut PER TAHUN, dan tanpanya surat 000001 tahun ini ditolak `uq_idem` sebagai duplikat surat 000001 tahun lalu, diam-diam.

**Sakelarnya diperiksa SEBELUM kejatuhtempoan** (`runKontrolUlangIfDue`). Terbalik, pemicu yang masih nonaktif pukul 09:00 tetap memajukan penanda hariannya, dan staf yang menyalakannya pukul 10:00 menunggu pengingat yang baru datang BESOK tanpa satu pun keterangan.

**Yang WAJIB diketahui sebelum mengaktifkannya: `skdp_bpjs` KOSONG di `alca`.** Arsip `sik` berisi 253 baris bertanggal Des 2023 - Feb 2024, lalu berhenti -- menunya dipakai sebentar di awal 2024 lalu ditinggalkan. Query-nya terbukti atas 253 baris sungguhan itu (16 kandidat pada satu tanggal sasaran, nol kolom klinis terbaca), tapi belum pernah berjalan atas satu baris pun yang dibuat RS ini belakangan. `npm run dryrun:kontrol -- [database] [tanggal]` ada persis untuk ini, dan menerima **tanggal acuan** selain nama database -- tanpa itu, arsip berisi tanggal lampau juga menjawab nol baris, benar dan sama sekali tidak informatif. Ia mencetak DUA bagian (seluruh isi tabel dan yang benar-benar jatuh tempo) supaya "belum ada yang jatuh tempo" bisa dibedakan dari "tabelnya memang belum pernah berisi".

### Kelas kesembilan: ADMINISTRASI (`/administrasi`, migrations/026) -- mengirim BERKAS, bukan kabar

Sepuluh pemicu sebelumnya mengirim KABAR ("antrian Anda sekian", "hasil sudah siap"). `/administrasi` (admin-only) mengirim **barangnya**: surat keterangan sakit dan sehat sebagai PDF, dirender mengikuti `rptSuratSakit5.jasper` dan `rptSuratSehat.jasper` milik Khanza. Bedanya bukan teknis belaka -- surat sakit adalah dokumen yang diserahkan pasien ke tempat kerjanya, jadi yang beredar bukan lagi kabar tentang kunjungan melainkan surat resmi RS yang bisa diteruskan ke siapa pun. **`administrasi.enabled` default MATI.**

**Kedua surat BERBEDA BENTUK, dan itu menentukan seluruh halamannya.** Dibuktikan dari sumber Khanza (`src/surat/SuratSakit.java`, `src/simrskhanza/DlgReg.java`), bukan disimpulkan dari nama tabel:

| | Sumber | Ada catatan surat? | Artinya mengirim |
|---|---|---|---|
| Surat sakit | `suratsakit` (18 baris di `alca`) | YA -- `no_surat`, tanggal, lama | MENGANTARKAN ULANG keputusan dokter yang sudah tercatat |
| Surat sehat | `reg_periksa` + `pasien` + `dokter` | **TIDAK** | **MENERBITKAN** surat atas sebuah kunjungan |

`rptSuratSehat` dicetak langsung dari layar registrasi dan tidak pernah menyentuh `surat_keterangan_sehat` -- itulah sebabnya tabel itu **kosong di kedua database** (0 baris) sementara `suratsakit` berisi. Tabel itu milik formulir LAIN. Kesimpulannya diambil dari sana bila barisnya kebetulan ada; halaman tab Surat sehat memuat peringatan yang menyebut perbedaan ini di depan staf, bukan cuma di sini.

**PDF lewat Chromium yang SUDAH ada, nol paket baru.** Puppeteer sudah jadi dependensi lewat whatsapp-web.js. Dua hal yang WAJIB tetap begini, keduanya dibayar insiden nyata: **`userDataDir` sendiri di direktori sementara** (perebutan `.wwebjs_auth` itulah yang pernah menjatuhkan worker ke crash loop 29 kali), dan **selalu ditutup di `finally` berikut `SIGKILL` cadangan** (9 Chromium yatim pernah tertinggal sekaligus). Terukur ~480 ms peluncuran, ~600-700 ms per surat, jadi peramban TIDAK disimpan hidup antar permintaan -- yang menganggur berjam-jam persis bentuk yang berakhir jadi proses yatim.

**Dirender di proses WEB, bukan worker**, dan itu bukan pelanggaran topologi: staf harus bisa MELIHAT suratnya sebelum mengirim, dan pratinjau yang menunggu satu siklus worker bukan pratinjau. Worker tidak berubah sama sekali -- ia mengirim berkas dari `outbox` seperti lampiran broadcast mana pun.

**Penanda kosong Khanza merusak alamat 89% pasien, dan Khanza sendiri tidak menanganinya.** Kolom wilayah memakai NAMA TABELNYA sebagai isian bawaan: `kelurahan.nm_kel = 'KELURAHAN'` pada **4.332 dari 4.873 pasien**. Query cetak Khanza menggabungkan keempatnya apa adanya, jadi suratnya beralamat "KOTO ALAM, KELURAHAN, KECAMATAN, KABUPATEN". `core/suratDoc.ts`'s `isianSurat()` membuangnya, dan baris yang jadi kosong DIHILANGKAN dari surat alih-alih dicetak "Pekerjaan : ". Pelajaran `namaPenjamin()` yang sama, hanya lebih luas: `pekerjaan` 78% berpenanda `-`, `nama_perusahaan` **100%**. Khanza juga memakai INNER JOIN ke `kelurahan`/`kecamatan`/`kabupaten`/`perusahaan_pasien` sekaligus -- pasien yang salah satunya kosong tidak bisa dicetak sama sekali; di sini semuanya LEFT JOIN.

**Diagnosa: sakelar TERSENDIRI, default MATI.** `rptSuratSakit5` (varian yang dirujuk) mencetak kode ICD + nama penyakit dari `diagnosa_pasien`+`penyakit`; `rptSuratSakit.jasper` (varian dasar Khanza) tidak. Penerimanya pasien sendiri, yang berhak atas diagnosanya -- jadi larangan §5.2 tidak otomatis berlaku, tapi keputusannya juga bukan milik kode: nomor tujuan berasal dari `pasien.no_tlp` yang 40%-nya tidak terpakai, dan PDF bisa diteruskan ke mana pun. Saat mati, kolomnya **tidak di-SELECT sama sekali** -- pola `farmasi.stok_pakai_batch`: pengaturannya dibaca `lib/surat.ts` lalu diserahkan sebagai parameter, karena modul `khanza/` tidak boleh menyentuh pengaturan.

**Poli sensitif MENOLAK, tidak diganti template generik** -- satu-satunya kelas yang begini. Sepuluh pemicu lain cukup mengganti kalimatnya karena yang bocor cuma beberapa kata; di sini yang menyertai pesan adalah BERKAS berisi identitas lengkap, jadi mengganti pengantarnya tidak menyembunyikan apa pun selama lampirannya ikut. Pasien tetap bisa mengambilnya di loket, tempat kendali aksesnya memang ada.

**Kunci idempoten memuat STEMPEL WAKTU -- sengaja bisa kirim ulang.** Kebalikan dari sepuluh pemicu lain yang ada justru untuk memastikan satu kejadian = satu pesan. Di sini pengirimnya manusia yang menekan tombol untuk satu pasien, dan kirim ulang adalah keadaan NORMAL (berkas terhapus dari ponsel, pasien ganti nomor). Menolaknya sebagai duplikat berarti staf menekan tombol, halaman menjawab berhasil, dan tidak ada apa pun yang terkirim. Perlindungan tekan-ganda tempatnya di layar, bukan di database.

**Jam tenang DILEWATI** (`BYPASS_QUIET_HOURS`), dan ini satu-satunya di daftar itu yang penerimanya PASIEN. Yang membenarkannya: ia sinkron dengan tindakan seseorang -- staf menekan kirim karena pasiennya sedang di loket atau baru menelepon, alasan yang sama persis dengan AUTO_REPLY. **Daftar tolak tidak berlaku**, sama seperti BROADCAST/AUTO_REPLY: yang dihentikan pasien adalah kiriman OTOMATIS, dan ini bukan itu.

**Pemangkas `no_surat` adalah satu-satunya yang EKSAK di proyek ini**: `SKS` + `YYYYMMDD` + 3 digit, terurut leksikal, dan ia PRIMARY KEY -- rentang tanggal jatuh langsung jadi `range` pada PRIMARY. Yang disandikannya tanggal surat DIBUAT, dan itu memang yang dicari staf; `tanggalawal` (mulai istirahat) berbeda pada **5 dari 18 baris** dan tidak terindeks. Rentang tanggal WAJIB terisi dan selalu terlihat, berbeda dari `/broadcast`: di sana ada bentuk query kedua yang berangkat dari `pasien`, di sini tidak ada padanannya karena yang dicari SURAT dan KUNJUNGAN.

**Izin pindai penuh untuk `sks` bersifat SEMENTARA**, dan sebabnya sama dengan `permintaan_lab` di `alca`: tabelnya kosong, dan MariaDB memindai tabel kosong. Dibuktikan terhadap salinan berstruktur sama berisi 3.000 baris -- `type=ref, key=no_rawat, rows~1`. Izinnya akan berhenti terpakai sendiri begitu RS memakai formulir itu; `maxRows` yang jadi penjaga sebenarnya.

**Berkasnya disimpan di `uploads/broadcast/` yang SAMA**, bukan direktori baru: `cleanupOrphanMedia()` memangkas dengan memindai direktori itu, jadi direktori kedua berarti setiap surat yang pernah dikirim menetap di disk selamanya berikut nama dan alamat pasiennya.

**Pratinjaunya HTML di dalam modal, bukan tautan yang membuka PDF -- dan `Content-Disposition: inline` ternyata cuma PERMINTAAN.** Bentuk pertamanya `<a target="_blank">` menuju PDF ber-header `inline`, dengan anggapan peramban menampilkannya. Header itu benar dan tetap dikirim, tapi yang memutuskan render-atau-unduh adalah **peramban**: Chrome punya setelan "Download PDF files instead of automatically opening them" (`plugins.always_open_pdf_externally`), dan begitu ia menyala di komputer loket mana pun -- tanpa terlihat sedikit pun dari sisi kita -- tombol "Lihat" berubah jadi mengunduh berkas. Akibatnya bertentangan dengan alasan pratinjau ini ada: surat berisi nama, umur, dan alamat pasien menumpuk di folder Unduhan komputer yang dipakai bergantian banyak petugas. Tidak ada header yang bisa memaksanya. Enam hal yang menempel:

- **Yang dipratinjau HTML-nya, dan itu LEBIH DEKAT ke sumber, bukan lebih jauh.** HTML bukan penurunan kedua di samping PDF melainkan bahannya (`suratKeHtml` → `htmlKePdf`), jadi aturan "pratinjau tidak boleh berbeda dari yang terkirim" justru lebih terjaga daripada sebelumnya. Peramban mana pun merendernya tanpa syarat. Terukur **27 ms** berbanding **1.030 ms** jalur PDF -- 38× lebih cepat, dan nol peluncuran Chromium per klik berikut risiko proses yatimnya (`lib/pdf.ts`).
- **PDF tetap dilayani lewat `?format=pdf`**, dibuka dari dalam modal. Yang kadang perlu dibuktikan memang berkas yang akan diterima pasien; di tombol yang bernama "Buka berkas PDF", peramban yang memilih mengunduh sudah sesuai harapan orang yang menekannya.
- **Galat dijawab HTML, bukan JSON.** Route ini tidak pernah dipanggil dari JavaScript -- selalu dibuka peramban sebagai `src` iframe atau tab baru. `{"error":"..."}` mentah di tengah kotak pratinjau terbaca sebagai halaman rusak, bukan sebagai keterangan bahwa datanya memang tidak ada.
- **SATU modal untuk seluruh tabel, `src` hanya terpasang saat terbuka.** Satu `<iframe>` per baris berarti route ini ditembak sebanyak baris yang tampil, dan tiap tembakan satu query ke `sik` -- kolam yang sengaja dibatasi `pool.max: 2`. `key={kunci}` pada iframe-nya wajib: tanpa itu React memakai ulang elemen yang sama dan penanda "sudah dimuat" sempat bernilai benar sementara isinya masih surat pasien SEBELUMNYA.
- **Lebarnya dipaku 794 px (A4 pada 96 dpi), digulir menyamping bila layar sempit.** Membiarkannya melar mengikuti modal mengubah pemenggalan baris, sehingga yang dilihat staf bukan lagi susunan yang akan diterima pasien.
- **`sandbox` di iframe DAN CSP `sandbox; default-src 'none'; style-src 'unsafe-inline'` di responsnya.** Keduanya cadangan atas `lolos()` di `core/suratHtml.ts`, bukan penggantinya -- tapi taruhannya naik: sejak pratinjau ini ada, HTML surat sampai ke peramban petugas, bukan lagi cuma ke Chromium pencetak PDF. Komentar di berkas itu ikut diperbarui; klaim lamanya ("hanya pernah diserahkan ke Chromium") kini keliru.

Ikut diperbaiki di jalan yang sama: **`terkunci` dan alasannya dulu diturunkan DUA kali** di `SuratTable.tsx` -- sekali sebagai boolean, sekali lagi sebagai rangkaian `title` dengan urutan cabang yang berbeda. Selama keduanya kebetulan sepakat tidak ada yang terlihat; menyimpang sedikit saja menghasilkan tombol mati tanpa keterangan atau keterangan yang menyebut sebab yang salah. Sekarang satu fungsi `alasanTerkunci()` (`undefined` = boleh kirim), dan itu jadi wajib begitu modalnya ikut memakai penurunan yang sama. Tombol **Kirim ada juga di dalam modal**, karena menutup pratinjau untuk mencari kembali barisnya di tabel adalah jarak yang mengundang orang melewati pratinjaunya sama sekali; kegagalan kirim WAJIB tampil di dalam modal juga -- `<dialog>` yang terbuka membuat halaman di belakangnya inert, jadi pesan di baris tabel ada di layar tapi tertutup backdrop.

**Logo dan QR pengesahan -- keduanya DIAMBIL DARI KHANZA, bukan dirancang ulang.** Surat versi pertama polos: tanpa logo rumah sakit dan tanpa QR, sementara `rptSuratSakit5.jrxml` dan `rptSuratSehat.jrxml` punya keduanya. Bentuknya dibaca dari jrxml-nya langsung -- logo `70x70` di pojok kiri kop dengan teks tetap terpusat pada lebar penuh, dan `jr:QRCode` ber-`errorCorrectionLevel="H"`. Tujuh hal yang menempel:

- **Yang disebut "barcode" itu QR, dan isinya `$P{finger}` -- parameter yang halaman ini SUDAH punya padanannya.** `core/suratDoc.ts`'s `teksAsalUsul()` menyusunnya persis seperti `SuratSakit.java`: "Dikeluarkan di {nama RS}, Kabupaten/Kota {kabupaten}" / "Ditandatangani secara elektronik oleh {dokter}" / "ID {kode dokter}" / tanggal `dd-mm-YYYY`. Menyimpang satu kata pun membuat QR di sini dan QR yang dicetak di loket berisi teks berbeda untuk surat yang SAMA -- dan membandingkan keduanya adalah satu-satunya guna QR ini.
- **"ID" di sini kode dokter, dan Khanza kadang menaruh yang lain.** Khanza mendahulukan `sha1(sidikjari.sidikjari)` -- SHA1 atas cetakan SIDIK JARI dokter -- lalu jatuh ke kode dokter bila belum terdaftar. Tabel `sidikjari` **0 baris** di mesin ini, jadi Khanza sendiri pun sedang mencetak kode dokter. Tabel itu sengaja TIDAK dibaca: ia tak bisa diuji terhadap satu baris pun (pelajaran `RAD_REQUEST`), dan menaruh turunan biometrik pegawai ke dalam berkas yang diteruskan tanpa batas lewat WhatsApp adalah keputusan RS, bukan efek samping "menambahkan QR". Akibatnya: pada RS yang sudah mendaftarkan sidik jari, baris ID-nya berbeda dari QR Khanza.
- **Catatan kaki teks dan QR KEDUANYA ada, dan itu bukan pengulangan.** Khanza menaruh `finger` HANYA di dalam QR dan tidak pernah mencetaknya sebagai tulisan -- benar untuk kertas yang diserahkan di loket. Berkas ini beredar lepas, jadi pembaca tanpa pemindai tetap harus bisa membaca asal-usulnya. Catatan kaki melayani MANUSIA, QR melayani PEMINDAI; itu pula yang membuat **kegagalan QR tidak menjatuhkan suratnya** (`buatQrAsalUsul()` mencatat `warn` lalu mengembalikan kosong) -- yang dibutuhkan pasien adalah suratnya, dan keterangan yang sama tetap tercetak.
- **LETAKNYA bagian dari artinya, dan itu dibaca dari koordinat elemen jrxml -- bukan dipilih.** QR duduk DI DALAM blok tanda tangan, di ruang tanda tangan antara "Dokter Pemeriksa," dan nama dokter: `rptSuratSakit5` menaruh tanggal di y=306, "Pemeriksa" y=321, **QR y=340**, `nm_dokter` y=419 -- ketiganya pada x=373 yang sama; `rptSuratSehat` sama persis (y=245 / **y=258** / y=322 pada x=130). Versi pertama menaruhnya di pojok kiri bawah halaman, dan di sana ia terbaca sebagai gambar yang berdiri sendiri alih-alih sebagai tanda tangan elektronik atas nama dokter yang tercetak tepat di bawahnya -- padahal justru itu yang disahkannya. Unit test-nya memeriksa **URUTAN** ketiganya, bukan keberadaan gambarnya: asersi "ada `<img>` QR" lolos sepenuhnya pada versi yang salah letak. Saat QR tidak ada, `div.ruang` 20mm kembali menggantikannya -- kalau tidak, nama dokter naik menempel ke kata "Pemeriksa," dan suratnya kehilangan tempat untuk ditandatangani bila dicetak.
- **Logo hanya bisa dijauhkan dari garis kop lewat `min-height`**, karena ia `position: absolute` sehingga tidak punya margin/padding sendiri yang bisa mendorong garis ganda itu. `.kop.berlogo { min-height: 24mm }` = 20mm logo + 4mm jarak. Tanpa selisih itu logonya menempel di garis sementara teks di sebelahnya punya jarak, dan yang terlihat bukan "logo terlalu besar" melainkan kop yang miring sebelah.
- **QR tidak memuat satu pun data pasien**, dan Khanza pun tidak. Nama pasien memang tercetak besar di badan surat, tapi bentuk yang terbaca mesin membuat pemanenan borongan jadi murah -- QR ini mengesahkan SIAPA YANG MENERBITKAN, bukan siapa yang disebut. Dipatok unit test tersendiri.
- **MIME logo diturunkan dari ISINYA** (`mimeGambar()`, magic bytes), bukan ditulis `image/png` mati di kode. `setting.logo` adalah `longblob` yang diunggah sendiri RS lewat layar Khanza dan tidak ada kolom yang menyebut jenisnya; instalasi yang mengunggah JPEG akan mendapat data URI yang berbohong, dan yang muncul bukan galat melainkan kop tanpa logo -- Chromium memaafkannya lewat penciuman tipe, CSP tidak. Tidak dikenali = surat dicetak TANPA logo, bukan ditebak.
- **Blobnya di-cache satu jam sebagai DATA URI** (`getHospitalLogoDataUri()`), bukan ditempelkan ke query kop surat. 73 KB itu akan menyeberang lewat kolam `sik` ber-`pool.max: 2` untuk SETIAP pratinjau yang dibuka staf. Yang di-cache data URI-nya supaya base64 atas 73 KB terjadi sekali per jam, bukan sekali per surat. **Akibat yang harus disadari**: PDF per surat naik dari ~73 KB jadi ~191 KB, karena logonya 1050x1050 sementara ditampilkan 76 px. Mengecilkannya butuh paket pengolah gambar baru, dan itu ditolak dengan alasan yang sama seperti `pdfkit`.

CSP rute pratinjau karena itu ditambah `img-src data:` -- **`data:` saja**, bukan `'self'` apalagi `*`: kedua gambar memang tertanam, jadi izin ini tidak membuka jalan keluar, sementara alamat jarak jauh akan mengubah surat jadi alat yang memberi tahu pihak luar kapan sebuah surat pasien dibuka. `waitUntil: 'load'` di `lib/pdf.ts` jadi mengikat: ia baru menyala setelah tiap `<img>` selesai didekode, jadi PDF tidak pernah tercetak dengan kop yang logonya belum muncul.

**Empat jebakan yang ditemukan saat verifikasi, dan tiga di antaranya lolos dari `tsc` maupun `build`:**

- **`requireRole()` MENGEMBALIKAN respons 403, ia tidak melemparnya.** Versi pertama `pratinjau/route.ts` menulis `await requireRole('admin');` lalu membuang hasilnya -- operator menerima HTTP 200 berikut PDF berisi nama, umur, dan alamat pasien. `proxy.ts` tidak menangkapnya karena ia hanya memeriksa bahwa seseorang sudah LOGIN; perannya diperiksa `page.tsx`, dan route handler tidak punya page.tsx. Persis alasan aturan dua lapis ditulis. **Ditemukan uji HTTP, bukan dibaca ulang.**
- **Berkas `'use server'` tidak boleh mengekspor TIPE.** `export type { JenisSurat }` lolos `tsc` (tipe terhapus) DAN lolos `next build`, lalu meledak sebagai `ReferenceError: JenisSurat is not defined` saat server action pertama dipanggil. Tipe bersamanya sekarang tinggal di `core/suratDoc.ts`, modul murni yang aman diimpor komponen klien.
- **Modul `khanza/` yang tidak terdaftar di `khanza/index.ts` TIDAK PERNAH diperiksa `verify:plans`** -- pendaftarannya efek samping impor, jadi lupa menambahkannya ke barrel tidak menghasilkan satu pun galat, cuma pemeriksaan yang diam-diam tidak berjalan.
- **Login me-redirect ke `AUTH_URL` yang menunjuk port 3100**, yaitu instance PM2 dengan build LAMA. Uji peramban yang mengikuti redirect itu akan menguji kode lama; bentuk baru dari jebakan yang sudah tercatat. Cookie tidak membedakan port, jadi perbaikannya cukup kembali ke port uji sesudah login.

### Kelas kesepuluh: SURAT SAKIT OTOMATIS (`migrations/027`) -- berkas yang berangkat tanpa dilihat siapa pun

`administrasi.auto_enabled` (tab Pengaturan di `/administrasi`, admin-only) membuat surat keterangan sakit terkirim sendiri begitu dokter menyimpannya di Khanza. Sembilan kelas sebelumnya semuanya punya SESUATU yang meninjau: staf menekan kirim, atau isinya cuma kalimat yang salahnya berumur sekejap. Yang ini menggabungkan keduanya ke arah yang paling mahal -- **berkas, tanpa peninjau** -- dan seluruh bentuknya adalah pembayaran atas itu.

**Kelas PINDAI, dan itu bukan pilihan melainkan paksaan dari bentuk tabelnya.** `suratsakit` punya LIMA kolom (`no_surat`, `no_rawat`, `tanggalawal`, `tanggalakhir`, `lamasakit`) dan **tidak satu pun stempel waktu** -- satu-satunya pemicu di proyek ini yang begitu. Watermark karena itu mustahil benar. Satu-satunya penanda urutan adalah `no_surat`, dan tanggal di dalamnya BUKAN tanggal barisnya tersimpan: `SuratSakit.java` (`Valid.autoNomer3`) merakit prefiksnya dari kotak **Tanggal Awal** saat nomornya dibuatkan, bukan dari hari ini dan bukan pula dari `tanggalawal` yang akhirnya tersimpan (staf masih bisa menggeser tanggalnya sesudah nomornya keluar). Diukur atas 18 baris: cocok `tanggalawal` **13**, cocok tanggal kunjungan **15** -- tidak andal keduanya. Watermark di atas nomor yang tidak monoton terhadap urutan penyimpanan MELEWATI surat secara permanen tanpa galat, tanpa baris `outbox`, tanpa satu pun tanda di layar; kelas kegagalan yang sama persis dengan prefiks `nobooking`. Karena itu: jendela yang dipindai ulang tiap siklus, dedup murni lewat kunci idempoten.

**Berkas ini sempat menyatakan `no_surat` menyandikan "tanggal surat DIBUAT" dan itu KELIRU** -- klaim lama di `khanza/suratPasien.ts` yang baru terbantah saat sumber Khanza-nya dibaca. Sebagai PEMANGKAS ia tetap sempurna (PRIMARY KEY, terurut leksikal, `range` tanpa kolom bantu); yang salah adalah memperlakukannya sebagai penanda KEJADIAN.

**Jendelanya merentang KE DUA ARAH dari hari ini, dan arah majunya yang paling gampang dikira salah.** Karena nomornya mengikuti tanggal mulai istirahat, surat yang ditulis hari ini untuk istirahat pekan depan bernomor lebih BESAR daripada prefiks hari ini -- batas atas yang berhenti di hari ini membuang persis surat-surat itu. Diukur: `tanggalawal` mendahului kunjungan sampai **6 hari**. Arah mundur memberi kesempatan kedua pada siklus yang gagal tanpa mekanisme percobaan ulang tersendiri.

**`administrasi.auto_sejak` adalah LANTAINYA**, ditulis tanggal hari ini tiap kali sakelarnya dinyalakan. Tanpa itu, menyalakan sakelar berarti seluruh isi jendela -- termasuk surat pasien yang sudah pulang seminggu lalu -- langsung jadi berkas WhatsApp pada siklus berikutnya. Pelajaran `LAB_REQUEST`. **Konsekuensi yang harus disadari**: surat bernomor sebelum hari aktivasi tidak pernah terkirim otomatis, selamanya -- dan itu ikut menjaring surat yang ditulis hari ini untuk istirahat yang sudah dimulai kemarin. Tab Surat sakit adalah pemulihnya, dan halamannya mengatakan ini di depan staf.

**Kode pemicunya `SURAT_SAKIT`, BUKAN `ADMINISTRASI`, dan pemisahan itu yang memuat seluruh perbedaan kebijakannya.** Kode pemicu adalah yang menentukan dua hal di `core/optOut.ts` dan `core/quietHours.ts`, dan keduanya harus berlawanan antara dua jalur yang mengirim surat yang SAMA:

| | daftar tolak | jam tenang |
|---|---|---|
| `ADMINISTRASI` (staf menekan kirim) | tidak terikat | DILEWATI |
| `SURAT_SAKIT` (otomatis) | **terikat** | **tunduk** |

Yang membenarkan jalur manual bukan ISI pesannya melainkan ADANYA orang yang menunggunya -- pasien yang sedang di loket atau baru menelepon memintanya. Begitu pengirimnya jadwal, kedua alasan itu gugur sekaligus: yang minta berhenti memang sedang menghentikan justru ini, dan surat yang tersimpan pukul 22.30 lalu dikirim seketika membangunkan orang untuk berkas yang sama gunanya bila tiba pukul 07.00. Menumpang satu kode memaksa keduanya sama, dan salah ke arah mana pun. Dipatok unit test **berpasangan** di kedua berkas -- yang dijaga bukan nilai masing-masing melainkan bahwa keduanya BERBEDA.

**Kunci idempotennya TANPA stempel waktu**, juga kebalikan dari jalur manual. Di sana stempel waktu ada supaya staf bisa mengirim ulang, dan itu benar karena ada manusia yang memutuskan tiap kalinya. Di sini kunci yang selalu baru berarti jendela pindai mengirimkan surat yang sama setiap lima menit selama berhari-hari.

**Hanya surat SAKIT, dan itu bukan pembatasan yang bisa dilonggarkan belakangan.** Surat sehat tidak punya baris tersimpan di Khanza sama sekali -- yang ada cuma KUNJUNGAN, dan Khanza mencetak suratnya langsung dari layar registrasi. Tidak ada kejadian "surat sehat disimpan" untuk dipicu; mengotomatiskannya berarti menerbitkan surat keterangan sehat untuk setiap orang yang mendaftar.

**Chromium sekarang berjalan di KEDUA proses, dan di worker taruhannya berbeda.** `lib/pdf.ts` dulu menyatakan dirinya "dijalankan di proses WEB, bukan worker"; itu tidak lagi benar. Yang membuatnya bisa diterima: `userDataDir` sendiri di direktori sementara (tidak pernah `.wwebjs_auth`) dan penutupan di `finally` berikut SIGKILL cadangan -- keduanya sudah ada, dan di worker keduanya berhenti jadi kerapian dan menjadi syarat hidup, karena justru proses inilah yang pernah jatuh ke crash loop 29 kali karena Chromium yatim memegang direktori sesi. Tiga pagar yang menempel padanya: siklus **5 menit** (bukan 60 detik), **kuota per siklus** (`administrasi.auto_max_per_siklus`, default 10; kelebihannya dikirim siklus berikutnya, tidak dibuang), dan siklusnya **DIHENTIKAN pada kegagalan render pertama** alih-alih meluncurkan yang berikutnya -- `suratKeHtml()` merangkai string yang seluruhnya kita lolos sendiri, jadi kegagalan di sana hampir pasti Chromium-nya yang rusak, bukan satu surat yang beracun.

**Urutan pemeriksaan menentukan apa yang tercatat, dan ketiga hasilnya BERBEDA** (`core/suratOtomatis.ts`, fungsi murni):

- **poli sensitif** -> MENOLAK, dan **tidak menulis baris `outbox` apa pun**. Menulisnya berarti `enqueueMessage` merender template generik lalu benar-benar mengirimkannya -- kebalikan dari yang diminta. Akibatnya ia dipertimbangkan ulang tiap siklus selama masih di jendela; itu murah, dan tab Surat sakit sudah menandainya di layar.
- **nomor tak terpakai / daftar tolak** -> baris `outbox` **tanpa lampiran**. Statusnya ditentukan `enqueueMessage` sendiri (`skipped_no_contact` / `skipped_opt_out`), jadi ia terlihat di Antrean DAN tersaring dari siklus berikutnya lewat kunci idempoten. Tanpa lampiran = tanpa peluncuran Chromium untuk berkas yang toh tidak pergi ke mana pun.
- **kuota** -> bukan penolakan sama sekali; dikirim siklus berikutnya.

Kuota diperiksa **paling akhir** justru karena itu: surat yang toh ditolak tidak boleh memakan jatah, kalau tidak satu pasien poli sensitif di depan antrean cukup untuk menunda surat pasien lain tanpa sebab yang bisa dilihat siapa pun. Dipatok unit test tersendiri, berikut asersi bahwa `masuk = kirim + lewat` selalu genap -- selisih yang tidak tercatat adalah persis cara sebuah surat hilang diam-diam.

**Nomornya WAJIB lewat `resolvePhone()`, bukan `normalizePhone(no_tlp)`.** Ditemukan saat menulis, sebelum sempat jadi bug: koreksi manual dari `/nomor-bermasalah` MENGALAHKAN normalisasi otomatis (F2.1-F2.3), jadi keputusan yang berangkat dari `no_tlp` mentah akan menolak persis pasien yang nomornya sudah dibetulkan petugas -- di rumah sakit ini 40% nomor tidak terpakai, jadi itu bukan kasus pinggiran melainkan alasan halaman koreksi nomor ada. Bentuknya dipaksa lewat tipe: `KandidatSurat` menerima `phoneE164` yang SUDAH diselesaikan, sehingga fungsi keputusannya tidak punya jalan membaca `no_tlp` sendiri walau ia mau.

**`saringKunciBaru()` naik ke `pipeline.ts` dan dipakai bersama** dengan `BROADCAST_FOLLOWUP`. `uq_idem` tetap penjaga terakhirnya; yang dibeli penyaringan di depan berbeda per pemakainya -- di broadcast, baris `broadcast_campaign` yang mengaku punya penerima padahal nol pesan baru; di sini, satu peluncuran Chromium plus satu PDF berisi identitas pasien untuk pesan yang toh ditolak, dikalikan ribuan kali karena jendelanya membaca ulang surat yang sama tiap siklus selama berhari-hari.

`simpanPdfSurat()` juga naik ke `lib/mediaStorage.ts`: ia dulu hanya ada di berkas `'use server'` milik dashboard, dan worker tidak boleh mengimpor berkas itu. Menyalinnya berarti dua tempat memutuskan sendiri di mana surat pasien disimpan, dan yang menyimpang tidak akan pernah ikut terpangkas `cleanupOrphanMedia()`.

### Kelas kesebelas: PENGADAAN (`/farmasi`, migrations/028) -- nota pembelian, dan tabelnya tanpa jam

Tab keempat di `/farmasi`. Sumbernya menu **Transaksi Pengadaan Obat, Alkes & BHP Medis** di Khanza (`src/inventory/DlgPembelian.java`), yang menulis satu baris `pembelian` (796 baris di sini) berikut sekian baris `detailbeli` (4.597). Setiap pembelian yang disimpan dikirim ke gudang/apotek sebagai nota: pemasok, daftar barang berikut jumlah dan harga beli, potongan, PPN, tagihan.

**Kelas PINDAI, dan itu paksaan dari bentuk tabelnya.** `pembelian` punya sebelas kolom dan **tidak satu pun stempel waktu** -- yang ada cuma `tgl_beli` bertipe DATE, dan tanggal itu DIPILIH staf (tanggal nota pemasok), bukan diisi jam server. Jadi tidak ada satu pun nilai di tabel itu yang menyatakan "baris ini tersimpan pukul sekian". Yang dipakai: jendela ±N hari yang dibaca ulang tiap siklus, dedup murni lewat kunci idempoten -- bentuk yang sama persis dengan `SURAT_SAKIT`, lewat sebab yang sama. Perhitungan jendelanya karena itu **disatukan** di `core/jendelaPindai.ts` dan dipakai keduanya; `jendelaSuratOtomatis()` sekarang cuma pembungkus tipis di atasnya, nol perubahan perilaku.

**`riwayat_barang_medis` PUNYA jam, dan sengaja tidak dipakai.** Ia menggoda: `posisi='Pengadaan'`, `status='Simpan'`, plus `tanggal` DATE dan `jam` TIME yang benar-benar diisi saat penyimpanan -- persis waktu kejadian yang tidak dipunyai `pembelian`. Ditolak karena dua hal terukur. (1) **Tidak ada indeks yang bisa melayani penyaringan waktu**: satu-satunya kunci di sana `kode_brng` dan `kd_bangsal`, jadi menyaring `tanggal >= X` berarti pemindaian penuh atas **114.092 baris** yang bertambah ~100 sehari (58 ribu di antaranya dari pemberian obat, yang sama sekali tidak ada urusannya dengan pengadaan) -- tiap siklus, selamanya. (2) **`no_faktur`-nya KOSONG di instalasi ini**: `Trackobat.catatRiwayat(...)` dipanggil lewat dua cabang, dan cabang non-batch (`DlgPembelian.java:998`, yang dipakai di sini karena `farmasi.stok_pakai_batch` mati) meneruskan `no_faktur=""` -- terbukti pada seluruh 5.374 baris `Pengadaan`. Nomor fakturnya cuma ada sebagai kata pertama di dalam `keterangan`, jadi menautkannya berarti bergantung pada penguraian teks bebas yang bentuknya berbeda antar cabang kode Khanza.

**Pemangkasnya `no_faktur`, dan arahnya DIUKUR.** Bentuknya `PG` + `YYYYMMDD` + 3 digit; ia PRIMARY KEY dan terurut leksikal, jadi rentang tanggal jatuh langsung jadi `range` pada PRIMARY (terukur `rows~9`). `DlgPembelian.java:1759` merakit prefiksnya lewat `Valid.autoNomer3` dari isi kotak **Tanggal Beli** saat nomornya dibuatkan. Atas seluruh 910 baris: prefiks lebih MAJU daripada `tgl_beli` pada **9 baris** (sampai 31 hari), lebih MUNDUR pada **0**. Nol pada arah mundur itu yang menentukan artinya -- alurnya selalu "nomor dibuatkan hari ini, lalu `tgl_beli` digeser mundur ke tanggal nota pemasok". Jadi prefiks `no_faktur` adalah penanda **kapan ini DIMASUKKAN**, dan itulah yang dibutuhkan pemicu. Memakai `tgl_beli` sebagai pemangkas justru salah: nota bertanggal bulan lalu yang dimasukkan hari ini akan jatuh di luar jendela dan tidak pernah diberitahukan, tanpa satu pun galat -- kelas kegagalan yang sama dengan prefiks `nobooking`. Jendelanya tetap DUA arah, karena staf yang mengubah Tanggal Beli SEBELUM menekan tombol nomor menghasilkan prefiks di masa depan.

**Rinciannya query TERPISAH, bukan satu join.** Satu faktur berisi 5,7 barang rata-rata dan 58 pada yang terbanyak; menjoinkannya berarti keempat angka rupiah header berulang sebanyak barangnya lalu dibuang lagi di sisi Node. Dua query dengan `IN` lebih murah DAN menghasilkan bentuk yang langsung dipakai. Keduanya tanpa izin pindai penuh (`range PRIMARY` dan `ref no_faktur`), dan izinnya sengaja TIDAK ditulis walau "aman kalau ada".

**`farmasi.pengadaan_harga` MENYALA secara bawaan**, berbeda dari kebanyakan sakelar di proyek ini -- yang diminta adalah nota pembelian, dan nota tanpa harga bukan nota. Kunci ini ada untuk MEMATIKAN harga, bukan untuk menambah satu langkah sebelum fiturnya berguna; yang menahan seluruhnya tetap `farmasi.pengadaan_enabled` yang mati. Saat dimatikan, `h_beli`/`total` **tidak di-SELECT sama sekali** -- pola `sertakan_diagnosa`, dibuktikan pada `Object.keys()` baris hasilnya dan bukan dengan membaca SQL. `barisBarangTeks()` memutuskan lewat `undefined`, bukan lewat flag terpisah, sehingga "harga tidak ditampilkan" dan "harga tidak pernah dibaca" adalah SATU keadaan yang sama.

**`kadaluarsa` sengaja tidak diambil, dan itu temuan dari data.** Dari 1.257 baris detail sepanjang 2026, **251 (20%) sudah lewat pada hari barangnya dibeli** -- kolom itu jelas tidak diisi dengan disiplin di sini. Mencetak "kadaluarsa 2025-02-28" pada barang yang dibeli hari ini membuat seluruh pesannya terbaca sebagai sistem rusak, lalu yang benar ikut tidak dipercaya.

**Nol dibedakan dari tidak tercatat.** `Number(null)` dan `Number('')` sama-sama menjawab `0` dan lolos `Number.isFinite`, jadi `h_beli` yang NULL akan dicetak **"Rp0"** -- bukan "tidak diketahui" melainkan "gratis", pada angka yang dipakai apotek mencocokkan nota pemasok. `keAngka()` menolaknya lebih dulu. **Ditemukan unit test, bukan diperkirakan.**

**Daftar tolak tidak berlaku dan jam tenang dilewati, dan keduanya terjawab sendiri**: tidak ada nomor pasien untuk dicocokkan, dan tidak ada poli pada sebuah pembelian. `PENGADAAN` karena itu sengaja TIDAK didaftarkan ke `OPT_OUT_TRIGGERS`. Diukur pula bahwa jam tenang nyaris tidak pernah menggigit di sini: dari 910 faktur, **tidak satu pun tersimpan lewat pukul 20:00**.

**Tujuan diperiksa DI DEPAN, sebelum `sik` disentuh.** Sakelar menyala tanpa satu pun tujuan tercentang bergejala persis seperti yang benar (halaman wajar, nol pesan keluar), jadi ia dicatat `warn` -- dan tanpa membaca `pembelian` lebih dulu, karena tidak ada gunanya membaca sesuatu yang tidak akan dikirim ke mana pun.

**`farmasi_target.terima_pengadaan` -- kolom KEEMPAT, dan pemisahannya paling tajam dari keempatnya**: nota pembelian memuat harga beli dari pemasok, yang punya nilai dagang tersendiri. Grup shift apotek sangat wajar perlu tahu tiap resep tanpa ikut membaca harga yang dibayar RS ke pemasoknya; bagian pengadaan justru kebalikannya. Akibat lanjutan di UI: satu kolom per centang membuat yang ketiga tersembunyi di bawah `xl` dan yang keempat praktis tidak pernah terlihat, sehingga pilihan yang sengaja dipisah di database berakhir tidak bisa dijangkau siapa pun. **Pratinjaunya membaca nilai TERSIMPAN, bukan isi kotak yang sedang diketik**, dan itu pilihan yang sama dengan tombol "Kirim peringatan uji" di `/pengaturan`: yang perlu dibuktikan staf adalah apa yang akan dikirim WORKER, dan worker membaca `app_setting`. Halamannya mengatakan ini di depan staf supaya "kenapa suntingan saya belum kelihatan" terjawab tanpa menebak.

Kunci idempotennya `(no_faktur, chat_id)` **tanpa stempel waktu** -- jendela pindai membaca faktur yang sama tiap lima menit selama berhari-hari, jadi kunci yang selalu baru berarti gudang dibanjiri nota yang sama. `chat_id` wajib ikut, dengan alasan yang sudah dibayar di notifikasi farmasi. `event_at` memakai waktu DETEKSI, bukan `tgl_beli`: tanggal nota pemasok bisa berumur berminggu-minggu, dan memakainya membuat nota yang baru dimasukkan dinilai basi lalu ditandai `expired` (F5.3) tanpa pernah terkirim. Grant untuk kolom baru **tidak** diperlukan (tabelnya sudah ber-grant; kolom bukan tabel) -- dibuktikan lewat `UPDATE` empiris, bukan diasumsikan.

### Kelas ketiga belas: HIBAH (`/farmasi`, migrations/031) -- barang masuk tanpa pemasok

Tab ketujuh di `/farmasi`. Sumbernya menu **Hibah Obat & BHP** di Khanza (`src/inventory/InventoryHibahObatBHP.java`), yang menulis satu baris `hibah_obat_bhp` berikut sekian baris `detailhibah_obat_bhp`.

**Kembaran PENGADAAN, dan kemiripannya DIPAKAI alih-alih cuma dicatat.** Kelas PINDAI lewat sebab yang sama persis (`hibah_obat_bhp` punya tujuh kolom dan tidak satu pun stempel waktu -- hanya `tgl_hibah` bertipe DATE yang DIPILIH staf), pemangkas prefiks pada PRIMARY KEY, kuota per siklus, lantai aktivasi. Yang berbeda dari sekadar "mirip": aturan bersamanya benar-benar **satu penurunan** -- pembulatan rupiah, penanda tanggal kosong Khanza, pengelompokan per nomor, dan aturan pemecahan pesan panjang pindah ke `core/notaBarang.ts` dan dipakai KEDUANYA; jendelanya sudah berbagi `core/jendelaPindai.ts`. Ke-20 uji pengadaan yang ada lolos tanpa satu asersi pun berubah, dan itu yang membuktikan perpindahannya nol-perubahan-perilaku. **PENGADAAN dan SURAT PEMESANAN adalah pasangan (pesanan dikirim → barang datang); hibah bukan tahap ketiga dari alur itu** melainkan jalur pemasukan yang berdiri sendiri -- tidak ada pesanan yang mendahuluinya, tidak ada yang ditagihkan sesudahnya. Karena itu tabnya ditaruh SESUDAH keduanya, bukan di antaranya.

**DUA penilaian atas barang yang sama, dan Khanza memberi keduanya nama sendiri di layar** (`InventoryHibahObatBHP.java:64-65`): `h_hibah`/`totalhibah` = "Nilai Hibah", yang **disebut pemberi**; `h_diakui`/`totalnilai` = "Nilai Diakui", yang **diakui RS** -- dan yang kedua itulah yang dijurnal (`PERSEDIAAN HIBAH OBAT & BHP` berpasangan dengan `PENDAPATAN HIBAH`, dan hanya bila `totalnilai > 0`). Karena itu nilai DIAKUI yang jadi angka utama tiap baris. **Nilai yang disebut pemberi ditampilkan HANYA saat berbeda**: pada seluruh 14 baris rincian di database uji keduanya sama persis, jadi mencetak dua angka identik di tiap baris menggandakan panjang pesan untuk informasi nol -- dan yang lebih buruk, pembacanya berhenti memperhatikan bedanya sehingga selisih yang sungguhan ikut terlewat. Perbandingannya lewat `nilaiSama()`, bukan `===` mentah: mysql2 menyerahkan `double` kadang sebagai string, dan `'2000'` vs `2000` yang dilaporkan sebagai selisih membuat seluruh notanya terbaca seperti ada yang salah. `null` di salah satu sisi **bukan** "kebetulan cocok" -- angka yang tidak tercatat bukan angka yang sama.

**Sakelar nilai TIDAK memutus kedua total header, dan versi pertama salah di sini.** `farmasi.hibah_nilai` awalnya memutus keduanya juga, dengan alasan yang terdengar lebih ketat ("tidak ada yang ditagihkan pada sebuah hibah, jadi tidak ada alasan angkanya tetap dibaca"). Alasan itu runtuh begitu hasilnya dilihat: templatenya menulis label kedua total sebagai baris tersendiri, jadi mematikan sakelarnya menghasilkan `Total nilai hibah :` dan `*Nilai diakui : *` -- dua baris menggantung yang terbaca sebagai sistem rusak, dan sejak itu angka yang benar pun tidak dipercaya. Satu-satunya jalan keluarnya adalah menyuruh staf ikut menyunting templatenya, dan **invarian dua-langkah semacam itu adalah yang berulang kali terbukti gagal DIAM di proyek ini**. Jadi sakelarnya mengatur apa yang bisa diaturnya sendirian: nilai PER BARANG (dan saat mati, `h_hibah`/`h_diakui`/`subtotaldiakui` tidak di-SELECT sama sekali -- dibuktikan pada `Object.keys()` baris hasilnya, bukan dengan membaca SQL). RS yang tidak ingin satu angka pun beredar menghapus `{total_hibah}` dan `{total_diakui}` dari templatenya, satu tindakan yang terlihat di halaman yang sedang dibukanya. `farmasi.pemesanan_harga` mewarisi keputusan yang sama.

**Pemangkasnya prefiks `no_hibah` (`HO` + `YYYYMMDD` + 3 digit), dan PENGUKURANNYA BERBEDA DARI PENGADAAN -- itu wajib disadari.** Untuk pengadaan, arah penyimpangan prefiks terhadap tanggalnya diukur atas 910 baris (9 maju, **0 mundur**), dan nol pada arah mundur itulah yang membuktikan prefiksnya penanda "kapan DIMASUKKAN". Di sini tabelnya kosong di produksi; yang ada cuma 6 baris di dua database uji, dan keenamnya berselisih **nol hari**. Enam baris tidak membuktikan apa pun tentang arah penyimpangannya -- yang menopang keputusan ini adalah **kesamaan MEKANISMENYA di sumber Khanza** (`Valid.autoNomer3` dari kotak tanggal yang dipilih staf, sampai ke nama variabelnya yang tetap `TglBeli`), bukan pengukuran. Karena itu jendelanya tetap merentang KE DUA ARAH: kalau ternyata menyimpang, ia menyimpang ke arah yang sudah dijaring.

**TANPA izin pindai penuh, dan itu tidak akan berubah saat tabelnya terisi.** `sks` dan `permintaan_lab` perlu izin sementara justru karena kolom pemangkasnya BUKAN primary key, sehingga MariaDB memilih pindai penuh selagi tabelnya kecil. Di sini `no_hibah` dan `(no_hibah, kode_brng, no_batch)` ADALAH primary key masing-masing tabel: EXPLAIN yang sama menghasilkan `range PRIMARY` di `alca` (0 baris) MAUPUN salinan uji (3 baris). Izinnya sengaja tidak ditulis walau "aman kalau ada".

**`riwayat_barang_medis` ditolak dengan dua alasan yang sama seperti pengadaan, dan di sini lebih kuat lagi**: tidak ada indeks yang bisa melayani penyaringan waktu atas 114.092 baris yang bertambah ~100 sehari, dan `InventoryHibahObatBHP.java:824` (cabang non-batch, yang dipakai di sini) meneruskan `no_faktur=""` persis seperti `DlgPembelian.java:998`. Di instalasi ini tabel itu bahkan **tidak punya satu baris pun ber-`posisi='Hibah'`** -- terukur, bukan diduga.

**`kadaluarsa` dan `no_batch` tidak diambil**, kesimpulan yang sama dengan pengadaan lewat sebab yang berbeda: di sana kolomnya terisi tapi 20% sudah lewat pada hari pembeliannya, di sini ia bernilai `'0000-00-00'` pada SELURUH 14 baris rincian. `subtotalhibah` juga tidak -- ia tidak menambah apa pun yang tidak sudah terjawab `{total_hibah}` di kepala nota, sementara ia menambah satu angka lagi pada baris yang sudah punya empat.

**`nama_pemberi` bisa berisi `'-'`**, pola yang sama persis dengan `penjab.png_jawab` dan `pasien.pekerjaan` -- terbukti pada baris H0001 di database uji. Dibersihkan lewat `isianSurat()` yang SUDAH ADA di `core/suratDoc.ts` alih-alih menyalin daftar penandanya ke tempat ketiga: daftar itu tumbuh dari pengamatan atas data Khanza sungguhan, dan salinan ketiga adalah yang paling mungkin ketinggalan saat penanda berikutnya ditemukan. Aman karena `core/suratDoc.ts` **tidak mengimpor apa pun**.

**Semua join LEFT, dan `kode_pemberi` memang NULLABLE** (berbeda dari `kd_bangsal` yang NOT NULL) -- jadi LEFT di sini bukan cuma kehati-hatian terhadap master yang terhapus, barisnya memang boleh tidak menunjuk pemberi mana pun. Layar pencarian Khanza memakai INNER; untuk layar yang dibuka orang hilangnya satu baris terlihat, untuk PEMICU hilangnya berarti satu penerimaan barang tidak pernah diberitakan tanpa satu pun galat.

Daftar tolak tidak berlaku dan jam tenang dilewati, keduanya terjawab sendiri: tidak ada nomor pasien untuk dicocokkan dan tidak ada poli pada sebuah hibah. `FARMASI_HIBAH` karena itu sengaja TIDAK didaftarkan ke `OPT_OUT_TRIGGERS`. Kunci idempotennya `(no_hibah, chat_id)` tanpa stempel waktu. `event_at` memakai waktu DETEKSI, bukan `tgl_hibah` -- tanggal serah terima bisa berumur berminggu-minggu saat entrinya dibuat, dan memakainya membuat nota yang baru dimasukkan dinilai basi lalu ditandai `expired`. Siklusnya **terpisah** dari pengadaan (`loop('hibah', ...)` tersendiri), bukan digabung: sakelarnya terpisah, jadi satu siklus gabungan yang gagal pada setengah pertamanya akan menghentikan setengah yang satunya -- fitur yang dimatikan RS bisa menjatuhkan fitur yang dinyalakannya.

**`farmasi_target.terima_hibah` terpisah dari `terima_pengadaan`, dan pemisahannya soal BATAS KERAHASIAAN**: harga beli pemasok punya nilai dagang dan wajar dibatasi ke bagian pengadaan, sementara nilai barang PEMBERIAN justru sering perlu dilihat lebih luas -- kepala instalasi, akuntansi, sampai bagian yang menyusun ucapan terima kasih ke pemberinya. **Penomoran kolom di tabel ini sudah terlanjur menyimpang** (028 menyebut dirinya "KEEMPAT", 030 menyebut dirinya "KEENAM"), jadi kolom baru ini sengaja TIDAK diberi nomor: yang mengikat adalah daftar pertanyaannya, bukan urutannya.

**Nomor migrasinya 031, bukan 029.** Berkas ini pertama ditulis sebagai 029 lalu diganti nama begitu ketahuan 030 sudah terlanjur diterapkan lebih dulu di mesin ini -- berkas migrasi yang urutan namanya berbeda dari urutan penerapannya menyesatkan pembaca berikutnya. Baris `schema_migrations`-nya ikut diganti (tidak ada checksum, jadi aman).

**Yang WAJIB diketahui sebelum menyalakannya: tabelnya KOSONG di produksi.** `COUNT(*)` = 0 pada `alca` maupun `sik` -- keadaan yang sama dengan `permintaan_radiologi` saat RAD_REQUEST dibuat, dan **`information_schema.TABLE_ROWS` tidak dipakai untuk menyimpulkan itu** (pelajaran 030). Query-nya dibuktikan atas data hibah sungguhan dari instalasi Khanza lain (`sik-dev-alca` dan `sik-ridda-dev`: 6 baris hibah, 14 baris rincian) berikut satu kiriman WhatsApp nyata, tapi belum pernah berjalan atas satu baris pun milik RS ini. `npm run dryrun:hibah -- [database]` ada persis untuk ini, dengan alasan yang sama yang melahirkan `dryrun:bpjs`: tanpa cara mengarahkan ke database lain, satu-satunya "bukti" yang bisa didapat adalah nol baris -- yang tidak membedakan "query benar, datanya memang belum ada" dari "query salah". Ia mencetak DUA jendela (jendela worker dan seluruh riwayat) justru supaya pembedaan itu terbaca. Halaman `/farmasi?tab=hibah` mengatakan hal yang sama di depan staf, dan tombol pratinjaunya membedakan "belum ada yang baru" dari "belum pernah ada sama sekali" -- tanpa pembedaan itu keduanya terbaca sama, dan staf menyimpulkan fiturnya rusak. **Mengarahkan `dryrun:hibah` ke database lain butuh grant `SELECT` untuk `wakhanza_ro` pada database itu** (diberikan sementara saat verifikasi lalu dicabut; berikan lagi bila perlu).

### Tujuan tambahan untuk pemicu pasien (`template_target`, migrations/018)

Sampai fitur ini ada, penerima sebuah pemicu pasien ditentukan sepenuhnya oleh kejadiannya: satu baris `reg_periksa` -> satu pasien -> satu nomor dari `sik.pasien.no_tlp`. NOTIFIKASI FARMASI memperkenalkan bentuk kedua -- tujuan yang DIPILIH staf, berupa grup WhatsApp atau nomor petugas -- tapi hanya untuk dua pemicunya sendiri. Ini membawa bentuk itu ke ketujuh pemicu pasien, diatur lewat tombol **Tujuan** di `/template`.

**Sengaja MEMAKAI ULANG mekanisme farmasi, bukan membangun jalur kedua**: alamatnya tetap `outbox.chat_id` (016), validasi/normalisasinya tetap `core/farmasiTarget.ts`, daftar grupnya tetap `wa_group` yang diisi worker lewat `wa_session.command`. Yang benar-benar baru cuma dua pertanyaan: ke mana sebuah pemicu boleh dikirim, dan apakah pasiennya masih ikut dikirimi.

**`template.tujuan_mode` punya TIGA nilai, bukan satu boolean "kirim ke grup juga".** `pasien` (default) = persis perilaku sebelum migrasi ini. `pasien_dan_tujuan` = pasien tetap dapat, tiap tujuan dapat salinan. `tujuan` = HANYA tujuan; pasien tidak dikirimi sama sekali. Nilai ketiga ada karena beberapa pemicu lebih masuk akal sebagai koordinasi internal daripada pemberitahuan pasien (mis. QUEUE_REG ke grup loket) -- dan tanpa nilai itu, satu-satunya cara mencapainya adalah mengosongkan nomor pasien, yang mustahil karena nomornya berasal dari `sik` yang read-only. Default `pasien` bukan sekadar nilai awal yang aman: ia yang memastikan migrasinya **nol perubahan perilaku** sampai ada yang memutuskan sebaliknya di dashboard.

**Penyebarannya di SATU tempat, `enqueuePemicuPasien()` di `pipeline.ts`** -- dipakai ketiganya (`sisipCycle`, `pollerBooking`, `scheduler`). Tiga tempat yang menafsirkan sendiri "ke mana pemicu ini dikirim" adalah persis bentuk kegagalan yang sudah dibayar di `respectsOptOut()`: cukup satu yang lupa diperbarui untuk membuat satu pemicu diam-diam berperilaku lain. `enqueueMessage()` sendiri TIDAK diubah -- ia tetap primitif satu-penerima, karena broadcast/balasan otomatis/farmasi sudah menentukan penerimanya sendiri.

**Kunci idempoten salinan di-HASH ULANG, bukan disambung** (`turunkanKunciTujuan()`). `outbox.idempotency_key` VARCHAR(64) sementara SHA1 hex sudah 40 karakter; sambungan dengan JID grup 24 karakter jadi 65 dan MariaDB non-strict **memotongnya diam-diam** tepat di bagian yang membedakan satu tujuan dari tujuan lain -- tujuan kedua dan seterusnya lalu ditolak `uq_idem` sebagai duplikat, tanpa satu pun galat karena INSERT-nya memang `ignoreDuplicates`. Hanya grup pertama yang pernah menerima apa pun.

Empat perilaku yang menempel, dan semuanya AKIBAT dari memakai ulang jalur yang ada -- bukan pilihan bebas:

- **Salinan ke tujuan tidak tunduk pada daftar tolak, dan itu terjadi sendirinya.** `enqueueMessage` hanya memeriksa `opt_out` bila ada `phone_e164`, sementara baris bertujuan `chat_id` memang tidak punya. Konsisten dengan farmasi: pasien tidak bisa memberhentikan koordinasi kerja internal RS. **Yang harus disadari**: pasien yang sudah minta berhenti tetap namanya muncul di grup, karena yang ia hentikan adalah pesan KEPADANYA. Halaman `/template` mengatakan ini di depan staf, bukan cuma di sini.
- **Jam tenang berlaku sama untuk salinan maupun aslinya** -- keduanya memakai `trigger_code` yang sama sehingga `computeScheduledAt` memberi `scheduled_at` yang sama. Membuat salinannya melewati jam tenang menuntut jam tenang per-penerima, perubahan yang jauh lebih besar daripada yang diminta.
- **Poli sensitif tetap terlindungi tanpa kode tambahan** -- `checkPrivacy` berjalan di dalam `enqueueMessage` untuk setiap baris, jadi salinan ke grup ikut diganti template generik.
- **`no_rkm_medis` tetap dicatat pada salinannya**, supaya pencarian di `/antrean` menemukan seluruh tempat pesan itu pergi -- pertanyaan "ke mana saja pesan ini dikirim" justru itu yang perlu dijawab saat ada yang menelepon.

**Mode `tujuan` tanpa tujuan aktif = pesan tidak pergi ke mana pun, dan itu dijaga tiga lapis** karena bentuk kegagalannya tak terlihat: tidak ada baris `outbox` yang dibuat, jadi tidak ada yang muncul di Antrean maupun Ringkasan -- pemicunya sekadar diam. (1) `setTujuanModeAction` menolak mengubah mode selama belum ada tujuan aktif; (2) Hapus dan Nonaktifkan menolak membuang tujuan aktif TERAKHIR selama modenya masih `tujuan`; (3) kalau toh terjadi (baris disunting lewat SQL), `enqueuePemicuPasien` mencatat `ERROR` dan **tidak** jatuh kembali ke pasien -- RS sudah memutuskan pesan ini bukan untuk pasien, dan membatalkan keputusan itu diam-diam lebih buruk daripada tidak mengirim.

Unik per **(pemicu, tujuan)**, bukan per tujuan saja seperti `farmasi_target.uq_chat` -- satu grup loket sangat wajar menerima QUEUE_REG maupun BILLING_READY, jadi keunikan menyeluruh akan menolak pemasangan yang benar. Tombol **Kirim uji** memakai `trigger_code` `FARMASI_UJI`, bukan kode pemicunya sendiri: baris uji dengan kode pemicu sungguhan akan tercampur dengan notifikasi pasien di Antrean/Ringkasan lalu ikut terhitung sebagai pengiriman pemicu itu. Grant `UPDATE`/`DELETE` untuk `template_target` diterapkan manual lewat root, dan sekali lagi terbukti tidak diwarisi (`ERROR 1142` sebelum, berhasil sesudah).

### Halaman Pesan masuk (`/pesan-masuk`) -- arah MASUK, dan tempat mencari ID

Admin-only. Menampilkan pesan yang diterima nomor RS (perorangan maupun grup) berikut **ID pengirim** dan **ID grup** yang bisa disalin, plus daftar grup yang diikuti. Ia menjawab dua hal yang sebelumnya tidak terjawab dari mana pun: "apa yang masuk hari ini" dan "apa kode grup ini".

**`auto_reply_log` tidak bisa dipakai, dan itu bukan soal kolom yang kurang.** Tiga hal membuatnya buta pada pertanyaan ini, ketiganya benar untuk tujuannya sendiri: ia hanya ditulis kalau `autoreply.enabled` menyala (`handleInboundMessage()` berhenti di baris pertama saat mati -- **nol baris tidak bisa dibedakan dari nol pesan**); pesan grup tidak pernah sampai ke sana karena dibuang di baris kedua pendengar; dan pesan tanpa huruf/angka (stiker, "👍") sengaja tidak dicatat supaya tidak memakan kuota. Karena itu `inbound_message` (`migrations/017`) berdiri sendiri, dan keduanya tetap ada.

**Pesan GRUP kini dicatat, tapi tetap TIDAK dibalas dan TIDAK memicu opt-out.** Sebelumnya ia dibuang tanpa jejak -- itulah kenapa tidak ada satu pun cara melihat id grup dari dashboard. Dua pengecualiannya disengaja: opt-out berkunci pada NOMOR sementara yang mengetik di grup adalah salah satu peserta (ia tidak sedang meminta apa pun atas nama dirinya sebagai pasien), dan membalas di dalam grup berarti seluruh anggota menerima jawaban atas pertanyaan satu orang -- satu percakapan ramai jadi rentetan balasan, persis pola yang memblokir nomor RS. `isGroupAddress()` sengaja terpisah dari `isKnownNonIndividualAddress()`: status (`@broadcast`) dan saluran TIDAK ikut dicatat, karena nomor RS menerima status dari setiap kontaknya dan itu ribuan baris sehari yang tidak seorang pun cari.

**`chat_id` vs `pengirim_id`** -- pada pesan grup yang pertama adalah GRUPNYA, yang kedua PESERTANYA. Pembedaan itulah inti halaman ini; keduanya ditampilkan berdampingan berikut tombol salin.

**Tabel tanpa grant `UPDATE`**, sama seperti `auto_reply_log` -- baris catatan tidak pernah ditulis ulang. Konsekuensi yang menentukan bentuk kodenya: `dibalas` harus sudah pasti saat insert, jadi pencatatan diletakkan SESUDAH balasan otomatis memutuskan, dan `handleInboundMessageSafely()` diubah mengembalikan hasilnya alih-alih `void`. Kegagalannya dilaporkan `no_match` -- yang pasti benar saat itu adalah tidak ada balasan yang terkirim, dan mencatatnya sebagai "dibalas" akan menyembunyikan justru pertanyaan yang perlu dijawab manusia.

**`inbox.simpan_teks` default MENYALA -- kebalikan dari `autoreply.log_inbound_text`, dan itu bukan inkonsistensi.** Kolom di `auto_reply_log` ada untuk MENYETEL KATA KUNCI, dan itu sudah terjawab kolom `outcome` tanpa menyimpan sepatah kata pun milik pasien. Halaman ini ada untuk MEMBACA pesannya; tanpa teks ia menampilkan daftar baris kosong dan tidak menjawab apa pun. Yang harus disadari RS: isinya bisa memuat keluhan medis, tabel ini bukan rekam medis, ia ikut tercadangkan. Karena itu masa simpannya **30 hari** (`inbox.simpan_hari`), bukan 90 seperti tabel lain, dan sakelarnya ada di halamannya sendiri -- di depan barang buktinya, tempat keputusan itu paling tepat diambil. **`panjang_teks` tetap diisi walau teksnya tidak disimpan**: tanpa itu "pertanyaan panjang dari pasien" tidak bisa dibedakan dari "stiker", padahal itu yang menentukan apakah ada yang harus dibalas manusia.

**Baris tanpa nomor ditampilkan sebagai "tidak terpetakan", bukan disembunyikan.** Pengalamatan `@lid` yang gagal dipetakan pernah membuat pesan pasien hilang berjam-jam tanpa jejak; keadaan itu harus terlihat sebagai kolom kosong di layar, bukan sebagai ketiadaan baris.

**Pembacaan grup KOSONG tidak pernah menghapus apa pun, dan ini bug yang benar-benar terjadi.** Versi pertama `syncGroups()` menghapus grup yang tidak muncul di pembacaan terakhir -- masuk akal ("RS sudah keluar dari grup itu") sampai pembacaannya sendiri yang kosong. `wa_session.status` menjadi `ready` beberapa detik setelah worker menyala, tapi koleksi chat di dalam Chromium belum tentu ikut terisi saat itu; menekan "Muat daftar grup" di sela itu membaca nol grup dan **menghapus ketujuh grup nyata sekaligus**, tanpa satu pun galat. Terbaca di log sebagai `jumlah:0, dihapus:7` tepat empat menit setelah `jumlah:7, dihapus:0`. Nol nyaris selalu berarti "belum tersinkron", hampir tidak pernah "memang tidak ada" -- jadi daftar lama dipertahankan dan yang terjadi dicatat sebagai `warn`. Halamannya juga mengatakan ini: tersambung ≠ riwayat chat selesai disalin.

**`CopyButton` punya jalur cadangan `document.execCommand('copy')`, dan itu keharusan.** `navigator.clipboard.writeText` menuntut izin `clipboard-write` dan terbukti menjawab `NotAllowedError: Write permission denied` pada peramban terkendali -- di headless MAUPUN headed. Tidak ada cara memastikan dari sini bahwa peramban di meja petugas berperilaku lain, dan tombol salin yang diam-diam gagal berarti staf menempel ID lama yang masih ada di papan klip -- tujuan yang diterima WhatsApp tanpa keluhan dan tidak pernah sampai ke siapa pun. Kalau keduanya gagal, ikonnya memerah dan teksnya tetap terlihat untuk disalin manual.

`mintaSyncGrup()` ada di `lib/waGroups.ts` karena DUA halaman memintanya (`/farmasi` untuk memilih tujuan, `/pesan-masuk` untuk melihat ID) -- dua server action yang sama-sama menulis `wa_session.command` adalah duplikasi yang cepat atau lambat berbeda.

### Alamat pengirim: `@lid`, bukan cuma `@c.us` (`core/waAddress.ts`)

Sampai suatu titik `message.from` selalu `<nomor>@c.us`, jadi penyaringnya cukup `endsWith('@c.us')` (menolak grup) dan nomornya diambil dengan `replace('@c.us','')`. WhatsApp memindahkan percakapan ke pengalamatan **LID** (`<id>@lid`) — identitas stabil per pengguna yang SENGAJA tidak memuat nomor telepon — dan sejak itu setiap pesan dari nomor yang sudah dipindahkan **dibuang di baris kedua listener**.

**Gejalanya adalah yang paling menyesatkan yang mungkin**, dan itu bagian terpenting untuk diingat: PM2 online, `wa_session` `ready`, kirim keluar normal, `autoreply.enabled` menyala, aturan kata kunci benar, `verify:db`/`verify:plans` lolos — dan `auto_reply_log` **0 baris**. Bukan karena diproses lalu gagal, tapi karena pesannya dibuang sebelum ada satu pun kode yang mencatatnya. Semua yang biasa dipakai untuk menyimpulkan "sistem sehat" menunjukkan sehat.

Tiga hal yang menempel di sini:

- **Penyaringnya daftar-IZIN (`c.us`, `lid`), bukan daftar-tolak grup.** Server baru yang belum dikenal ditolak sampai ada yang memutuskan sadar-sadar — tapi ditolak dengan `warn`, bukan diam (lihat di bawah).
- **Bagian `user` sebuah LID BUKAN nomor telepon, padahal bentuknya persis nomor**: `280925422235727` itu 15 digit, lolos pemeriksaan "8–15 digit" apa pun. Karena itu nomor HANYA diambil berdasarkan SERVER-nya (`phoneFromAddress` mengembalikan null untuk `@lid`), tidak pernah berdasarkan bentuk angkanya. Salah di titik ini berarti balasan terkirim ke nomor asing, daftar tolak tercatat atas nomor yang salah, dan kuota orang lain yang termakan — semuanya tanpa error. Dipatok unit test tersendiri.
- **Nomor E.164 wajib diperoleh sebelum apa pun dikerjakan**, karena semua yang di hilir berkunci pada nomor dan bukan pada identitas obrolan: `opt_out.phone_e164`, kuota `auto_reply_log`, dan pengiriman (`<nomor>@c.us`). Untuk `@lid`, `resolvePhoneE164()` di `wa-client.ts` mencoba tiga jalur berurutan (`kontak.id` → `kontak.number` → `WWebJS.enforceLidAndPnRetrieval`) dan **mencatat jalur mana yang berhasil**, supaya perubahan WhatsApp berikutnya memberi tahu jalur mana yang tumbang alih-alih cuma "tidak membalas". Gagal ketiganya = pesan **dilewati dengan peringatan**, bukan ditebak.

**Level log dipilih supaya peringatan tetap berarti.** Nomor WhatsApp RS menerima status/story dari SETIAP kontaknya (`@broadcast`), ditambah grup dan saluran — mencatat semuanya sebagai `warn` membuat `warn` tidak berarti apa-apa dalam sehari. Karena itu `isKnownNonIndividualAddress()` memisahkan "bukan perorangan dan itu wajar" (`debug`) dari "server belum pernah dilihat" (`warn`). Jejak amplop (`info`) hanya untuk lalu lintas perorangan — jenis, akhiran alamat, panjang teks; **tidak pernah isinya** (§9.7, alasan yang sama dengan `autoreply.log_inbound_text` yang default mati). Jejak inilah yang absen dan membuat bug ini butuh berjam-jam plus tiga pesan pasien yang hilang untuk ditemukan.

### `kunciPesanMasuk()` -- id pesan yang tidak selalu ada, dan tiga tafsir yang berbeda

`message.id._serialized` **sering hilang pada pesan grup**, dan itu bukan kelainan yang bisa diperbaiki: whatsapp-web.js mengisi `Message.id` apa adanya dari objek `MsgKey` milik WhatsApp Web (`this.id = data.id`), sementara `_serialized` di sana adalah **getter pada PROTOTYPE**. Objeknya menyeberang dari Chromium ke Node lewat serialisasi puppeteer, dan getter prototipe tidak ikut menyeberang -- jadi ada-tidaknya bergantung pada jalur mana yang kebetulan dipakai untuk pesan itu.

Dua jalur lama (`inboundLog.ts`, `wa-client.ts`) sudah memakai cadangan `from:timestamp` sejak awal justru karena ini. Jalur balasan stok grup yang ditambahkan belakangan adalah **satu-satunya yang memperlakukannya sebagai fatal lalu diam** -- sehingga tidak satu pun pertanyaan dari grup pernah dijawab, tanpa satu pun galat di mana pun. Yang terlihat di dashboard: `inbound_message` terisi normal (pencatatannya memakai cadangan), `outbox` kosong, sistem tampak sehat.

Bentuk kegagalannya sama persis dengan yang sudah dibayar di `respectsOptOut()` dan `core/outboxStatus.ts`: **tiga tempat berjauhan menafsirkan sendiri satu hal yang sama, dan cukup satu yang berbeda untuk membuat satu jalur diam-diam berperilaku lain.** Karena itu perbaikannya bukan menyalin cadangan ke tempat ketiga melainkan satu fungsi di `core/waAddress.ts` yang dipakai ketiganya.

Tabrakan cadangannya -- dua pesan BERBEDA dari obrolan yang sama pada detik yang sama -- gagal ke arah yang aman: satu pesan tidak dijawab, bukan satu pesan dijawab dua kali. Untuk keperluan sebenarnya (pesan yang SAMA diserahkan ulang sesudah sesi dipulihkan) kuncinya tetap stabil.

### `{cara_bayar}` — nama penjamin, dan kodenya yang tidak pernah ikut keluar

`reg_periksa.kd_pj` menunjuk `penjab`, dan yang berarti bagi pasien adalah `png_jawab` ("BPJS Kesehatan"), bukan kodenya ("A02"). `{cara_bayar}` menambahkannya ke **ketujuh pemicu pasien** — dan hanya ke sana.

**Kodenya tidak di-`SELECT` sama sekali.** Kelima query pemicu mengambil `pj.png_jawab` saja; `r.kd_pj` cuma jadi kondisi join dan tidak pernah ikut keluar dari SQL. Ini bukan kerapian melainkan penegakan: sekali kolomnya tidak ada di tipe barisnya, merender kodenya bukan terlarang melainkan **mustahil** — prinsip yang sama dengan cara privasi ditegakkan (§"Privasi ditegakkan lewat kolom yang tidak pernah diambil"). Dibuktikan langsung: baris hasil `pollQueueReg()`/`pollPharmacyReady()`/`pollBillingReady()` diperiksa tidak punya properti `kd_pj` sama sekali.

Tiga hal yang menempel, dan ketiganya gampang keliru ke arah yang tidak berbunyi:

- **`penjab.status` sengaja TIDAK disaring, dan ini KEBALIKAN dari pelajaran jadwal dokter.** Di sana `d.status='1'` DAN `p.status='1'` wajib, karena pertanyaannya "layanan apa yang MASIH dilayani" dan baris mati membuat pasien datang ke poli yang sudah tutup. Di sini pertanyaannya berbeda: siapa penjamin sebuah kunjungan yang SUDAH terjadi. Asuransi yang dinonaktifkan bulan lalu tetap penjamin kunjungan bulan lalu; menyaringnya mengganti fakta yang benar dengan kekosongan.
- **`-` adalah penanda "tidak diisi", bukan nama.** `penjab` punya baris `kd_pj='-'` yang `png_jawab`-nya juga `'-'` (`listPenjab()` sudah membuangnya dari daftar pilihan dengan alasan yang sama), dan 49 baris `reg_periksa` di mesin ini memakainya. Diteruskan apa adanya, pesannya berbunyi "Cara bayar: -" — bagi pasien terbaca seperti sistem rusak. `core/penjamin.ts`'s `namaPenjamin()` mengembalikannya sebagai string kosong, sehingga perlakuannya sama dengan variabel lain yang tidak terisi. **TIDAK ditebak jadi "Umum"**: `UMUM` adalah baris `penjab` tersendiri (`A01`), jadi kosong berarti datanya belum diisi petugas — bukan bahwa pasiennya bayar sendiri. Menebak di sini menghasilkan jawaban percaya-diri-dan-keliru, kesalahan yang sama yang membuat `detectPoli()` mengembalikan null saat ambigu.
- **`reg_periksa.p_jawab` sama sekali berbeda dari `kd_pj`.** Yang pertama penanggung jawab, seorang ORANG (PRD §10 #3); yang kedua penjamin, sebuah INSTANSI. Namanya nyaris sama dan keduanya ada di tabel yang sama; hanya yang kedua yang dibaca.

**Konteks lain sengaja TIDAK mendapatkannya.** BROADCAST dikecualikan walau segmennya PUNYA `png_jawab` (kolom tabel pratinjau): yang ada di sana penjamin pada SATU kunjungan terpilih lewat `MAX(no_rawat)`, sementara pasien yang sama bisa datang sebagai BPJS bulan lalu dan umum minggu ini — alasan yang sama persis membuat `{nama_poli}` juga tidak ada di sana. NOTIFIKASI FARMASI dikecualikan karena alasan berbeda: penjamin jelas berguna bagi apotek (formularium BPJS berbeda dari pembelian umum), tapi daftar itu dibaca sekian orang di grup WhatsApp yang keanggotaannya diatur di luar sistem ini, dan "DINAS SOSIAL"/"JASA RAHARJA" mengatakan hal yang lebih pribadi daripada sekadar ada resep masuk — apotek toh membacanya di SIMRS lewat `{no_resep}`, tempat kendali aksesnya memang ada.

**`worker/triggerVars.ts` lahir dari fitur ini, dan sebabnya layak dicatat.** Pemetaan baris→variabel dulu ditulis DUA kali: sekali di tiap poller, sekali lagi di `scripts/poll-dryrun.ts`. Menambahkan `{cara_bayar}` langsung membuktikan kenapa itu salah — sisi worker terisi, sisi dryrun kosong. Yang membuatnya lebih berbahaya daripada penyimpangan biasa: yang tertinggal adalah **pratinjaunya**. `poll:dryrun` ada justru untuk menjawab "apa yang AKAN terkirim" sebelum ada pesan sungguhan ke pasien, jadi pratinjau yang menampilkan variabel kosong sementara produksi mengisinya membuat staf menyimpulkan variabelnya tidak jalan lalu membuangnya dari template. Bentuk kegagalan yang sama dengan `respectsOptOut()`, `core/outboxStatus.ts`, dan `kunciPesanMasuk()`.

Dropdown "+ Sisipkan variabel" di `/template` dan `/pengaturan` membaca `TRIGGER_TEMPLATE_VARIABLES` yang sama, jadi variabelnya muncul sendiri tanpa satu baris pun perubahan UI — dan `findUnknownVariables()` menolaknya di konteks broadcast tanpa cabang tambahan.

**Risiko yang justru dibawa refaktornya, dan bagaimana ditutup**: semua variabel template bertipe **opsional**, jadi kalau penyatuan itu tidak sengaja menjatuhkan `nama_dokter` dari QUEUE_REG, `tsc` tidak mengeluh dan tidak ada test yang gagal — pesannya cuma kehilangan satu bagian tanpa galat. Ditutup lewat golden test terhadap baris `sik` sungguhan: pemetaan lama ditulis ulang sebagai nilai HARAPAN dan dibandingkan kunci per kunci. Hasilnya utuh (QUEUE_REG 7, RESULT_READY 6, PHARMACY_READY 6, BILLING_READY 5, BOOK_* 6), hanya `cara_bayar` yang bertambah.

### Tiga tabel template yang sengaja TIDAK digabung

`template` (PK `trigger_code`, **satu baris per pemicu** -- sembilan sejak `migrations/025`, tujuh sebelumnya) dipilih **otomatis oleh worker** lewat `Template.findByPk(triggerCode)` saat pemicunya terdeteksi di `sik` -- staf tidak pernah memilihnya. Jumlahnya bertambah hanya saat ada PEMICU baru, tidak pernah seiring pemakaian; itu yang membuatnya tetap tidak perlu paginasi. `broadcast_template` (PK `id` auto-increment, sebanyak yang staf mau, `migrations/008`) dipilih **manual** dari dropdown di `/broadcast` dan `/broadcast-terjadwal`. Keduanya dikelola di halaman `/template` yang sama tapi di dua bagian berlabel jelas. `auto_reply_rule` (`migrations/010`) dipilih **oleh kata kunci pada pesan pasien**, dikelola di `/balasan-otomatis` -- bukan di `/template`, karena yang disunting bukan cuma teksnya melainkan juga kapan ia terpakai.

Menggabungkannya akan memaksa `trigger_code` palsu untuk baris broadcast, dan membuat `findByPk()` milik worker bisa tidak sengaja mengambil pesan broadcast.

**Variabel divalidasi per konteks, dengan satu renderer.** `core/template.ts` punya tiga daftar: `TRIGGER_TEMPLATE_VARIABLES` (11, default `findUnknownVariables`), `BROADCAST_TEMPLATE_VARIABLES` (5), `AUTOREPLY_TEMPLATE_VARIABLES` (8). `KNOWN_TEMPLATE_VARIABLES` sekarang gabungan ketiganya -- itu yang DIMENGERTI `renderTemplate`, bukan yang BOLEH dipakai di satu tempat. Semua ditolak SAAT DISIMPAN, bukan saat kirim. Balasan otomatis sengaja **tidak** punya `{nama_pasien}`/`{no_rm}`: pemicunya nomor yang mengirim WhatsApp, yang belum tentu pasien terdaftar mana pun, dan nomor bisa berpindah tangan.

**Template broadcast DISALIN, bukan diacu.** Memilih template mengisi kotak teks; `broadcast_campaign.message_body` dan `broadcast_schedule.message_body` menyimpan salinannya sendiri. Tidak ada foreign key ke `broadcast_template`, jadi menyunting atau menghapus template TIDAK mengubah jadwal yang sedang berjalan maupun pesan yang sudah terkirim -- template murni alat bantu penyusunan. Itu sebabnya `deleteBroadcastTemplateAction` aman tanpa pemeriksaan "sedang dipakai jadwal mana".

`broadcast_template` butuh grant `UPDATE`/`DELETE` per-tabel (sunting/hapus staf), sama seperti `broadcast_schedule` -- dan sekali lagi terbukti tidak diwarisi: `INSERT` lolos lewat grant skema-lebar, `UPDATE` ditolak `ERROR 1142` sampai grant eksplisitnya diterapkan lewat root.

### Berhenti berlangganan: frasanya, dan CAKUPANNYA yang sengaja sempit

`core/optOut.ts` memegang dua hal sekaligus, dan sengaja satu berkas karena keduanya menyusun **satu janji** ke pasien yang tidak boleh terpecah dua tempat: frasa yang dikenali, dan daftar pemicu yang tunduk padanya.

**Frasanya `"Berhenti Kirim Otomatis"`**, menggantikan `stop`/`berhenti`/`unsubscribe`. Tiga kata, bukan satu -- dan justru karena panjang, ia boleh dicocokkan sebagai BAGIAN dari kalimat alih-alih harus sama persis dengan seluruh pesan. Pola lama `^(stop|berhenti)$` terpaksa ketat karena satu kata seperti "berhenti" gampang muncul di kalimat biasa; akibatnya `"stop dong"` dan `"saya mau berhenti"` TIDAK berhenti padahal maksud pasiennya jelas. Frasa sepanjang ini praktis mustahil terketik tanpa sengaja, jadi pencocokan yang lebih longgar justru lebih aman **sekaligus** lebih memaafkan. Konsekuensi yang harus disadari: **`STOP` polos tidak lagi memberhentikan apa pun** -- ia jatuh ke pencocokan balasan otomatis seperti pesan biasa.

**Hanya pemicu otomatis KE PASIEN yang terikat** (`OPT_OUT_TRIGGERS`, dua belas): QUEUE_REG, BOOK_CONFIRM, BOOK_CANCEL, BOOK_REMIND, RESULT_READY, PHARMACY_READY, BILLING_READY, BPJS_KONTROL, KONTROL_ULANG, LAB_REQUEST, RAD_REQUEST, SURAT_SAKIT. **BROADCAST dan AUTO_REPLY sengaja TIDAK** -- keputusan rumah sakit, bukan default teknis:

- BROADCAST/broadcast terjadwal = pengumuman yang disusun staf, kanal berbeda dari notifikasi kunjungan.
- AUTO_REPLY = jawaban atas pesan yang pasiennya sendiri kirim barusan. Mendiamkan orang yang baru saja bertanya bukan menghormati permintaannya, melainkan membuat sistem tampak rusak.

`respectsOptOut()` adalah SATU-SATUNYA sumber kebenarannya, dipakai di tiga tempat: `enqueueMessage()`, dispatcher (pemeriksaan kedua sebelum kirim), dan pencoretan antrean saat permintaan berhenti masuk. Kalau ketiganya menafsirkan sendiri-sendiri, cukup satu yang lupa diperbarui untuk membocorkan pesan ke pasien yang sudah minta berhenti. Kode pemicu yang tidak terdaftar dianggap **tidak terikat** -- pemicu baru harus didaftarkan secara sadar, karena default "terikat" akan membuat kanal baru diam-diam berhenti terkirim tanpa ada yang memutuskan.

**Pencoretan antrean saat opt-out masuk WAJIB menyertakan `triggerCode`.** Tanpa itu, broadcast dan balasan otomatis yang kebetulan sedang mengantre untuk nomor itu ikut tercoret -- membuat cakupannya bergantung pada kebetulan waktu: yang telanjur mengantre hilang, yang belum tetap terkirim.

**Teks yang dibaca pasien tidak boleh menjanjikan lebih luas dari yang dijalankan mesin -- maupun lebih sempit.** `OPT_OUT_CONFIRMATION` menyebut "pengingat kontrol" tanpa kata BPJS sejak `migrations/032`, karena sejak itu ADA DUA pemicu pengingat kontrol yang terikat: menyebut salah satunya membuat pasien non-BPJS wajar menyimpulkan pengingatnya tidak ikut berhenti, lalu mengeluh justru saat sistemnya bekerja benar. Tiga tempat ikut berubah dan harus tetap sinkron: teks konfirmasi (`OPT_OUT_CONFIRMATION` di `wa-client.ts`, menyebut eksplisit apa yang berhenti DAN apa yang tetap datang), isi ketujuh template (`migrations/011` mengganti "Balas STOP..." lewat `REPLACE()` agar suntingan staf tidak hilang), dan deskripsi halaman `/daftar-tolak` yang dulu berbunyi "seluruh pengiriman berikutnya dilewati" -- kalimat yang kini keliru.

### Pencarian antrean: satu kotak untuk tiga hal yang penelepon tahu

`/antrean` hanya bisa disaring per status sampai fitur ini ada. Itu menjawab "apa yang sedang gagal", tapi bukan pertanyaan yang benar-benar datang lewat telepon: **"kenapa pasien ini tidak menerima pesan?"** Satu-satunya jalan menjawabnya adalah SQL langsung ke `outbox` -- yang justru dilarang untuk petugas (`RUNBOOK.md` §8), jadi praktisnya tidak terjawab sama sekali.

Kotaknya menerima **tiga** bentuk masukan sekaligus (di-OR), karena penelepon hanya tahu salah satu: no. RM, nomor WhatsApp-nya sendiri, atau kode pengiriman di baris terakhir pesan. Tiga hal yang menempel:

- **Nomor dinormalkan lewat `normalizePhone()` yang SAMA dipakai pipeline**, bukan dicocokkan apa adanya. Petugas mengetik `0822...` atau `+62822...` sementara yang tersimpan `62822...`; pencarian yang gagal karena bentuk penulisan akan terbaca sebagai "pesannya memang tidak ada" -- kesimpulan yang salah dan mahal. Diverifikasi: ketiga bentuk mengembalikan jumlah yang sama.
- **Kode pengiriman hanya bisa lewat `body LIKE`, dan itu memang satu pemindaian `outbox` per pencarian.** Kodenya sengaja tidak disimpan di kolom tersendiri (§ kode unik), dan karena diturunkan lewat hash dari `idempotency_key` ia juga tidak bisa dihitung mundur jadi baris tertentu. Ditanggung sadar-sadar: ini tindakan sesekali saat ada yang menelepon, bukan kueri yang berjalan sendiri, dan `outbox` dipangkas pada 90 hari sehingga tidak tumbuh tanpa batas. `no_rkm_medis` sendiri tetap lewat `ix_rm`.
- **Chip status WAJIB mempertahankan `q`.** Kalau tidak, menyaring "gagal" atas hasil pencarian justru membuang pencariannya dan menampilkan seluruh antrean -- petugas mengira pasiennya punya puluhan pesan gagal.

Nol hasil diberi kalimatnya sendiri yang menyebut masa simpan 90 hari. Tanpa itu, "tidak ditemukan" terbaca sebagai "pesannya tidak pernah dibuat", padahal sebab yang jauh lebih sering adalah pesannya sudah dipangkas.

### Daftar panjang = TABEL, penyuntingan = MODAL

`/template` dan `/balasan-otomatis` sempat berupa grid kartu yang tiap kartunya berisi form terbuka. Itu salah untuk pekerjaannya dan diganti tabel: kartu menjawab "seperti apa satu template", tabel menjawab **"apa saja yang ada, urutannya bagaimana, mana yang aktif"** -- dan yang kedua itulah yang ditanyakan staf saat membuka halaman. Empat aturan memakan ~1300px sebagai kartu, ~180px sebagai tabel. Yang lebih buruk dari tingginya: semua form terbuka sekaligus berarti tidak ada keadaan "sedang mengubah", sehingga tujuh tombol Simpan tampak sama-sama aktif dan tidak jelas mana yang sedang disunting.

`Modal` dan `ConfirmDialog` (`components/ui/Modal.tsx`) dibangun di atas elemen **`<dialog>` asli**, bukan div ber-`position:fixed`. `showModal()` memberi gratis empat hal yang kalau ditulis sendiri hampir selalu setengah jadi: fokus keyboard terkurung, Esc menutup, halaman di belakang jadi inert, backdrop digambar peramban. Petugas pendaftaran memakai keyboard jauh lebih banyak daripada tetikus. Yang harus dijaga: peramban bisa menutup dialog sendiri (Esc), jadi event `cancel` WAJIB menyinkronkan balik ke state React -- tanpa itu state mengira dialognya masih terbuka dan tombol "Ubah" berikutnya tidak membuka apa-apa. `ConfirmDialog` juga menggantikan `window.confirm()`, yang tidak ikut tema gelap dan bisa disenyapkan pengguna -- kalau disenyapkan, tombol Hapus berubah jadi menghapus tanpa bertanya.

Lebarnya prop `size` (`md` konfirmasi pendek · `lg` form berisi textarea panjang · `xl` isi yang lebarnya ditentukan dari luar, sejauh ini cuma pratinjau surat yang harus selebar A4), **bukan `className` dari luar**: dua utility Tailwind untuk properti yang sama menang menurut urutan Tailwind menghasilkan CSS-nya, bukan urutan penulisan, jadi `max-w-*` dari pemanggil bisa diam-diam KALAH. Menggantikan `wide?: boolean` yang lama -- satu boolean tidak bisa tumbuh ke ukuran ketiga tanpa jadi dua prop yang saling menimpa.

Tabel: header dan sel **wajib** memakai breakpoint `*:table-cell` yang sama persis. Kalau berbeda, ada rentang lebar di mana satu kolom punya judul tanpa isi dan seluruh kolom sesudahnya bergeser satu.

### `MessageEditor` -- kenapa BUKAN WYSIWYG

Semua kotak penyusun pesan (`/template` ×2, `/balasan-otomatis`, `/broadcast`, `/broadcast-terjadwal`, dan dua field pesan di `/pengaturan`) memakai `components/ui/MessageEditor.tsx`.

**Editor WYSIWYG biasa akan merusak pesan pasien.** Editor semacam itu menghasilkan HTML, dan `<b>` akan terkirim APA ADANYA lewat WhatsApp -- pesan resmi rumah sakit berisi tag mentah. WhatsApp bukan HTML; ia mengenali empat penanda di dalam teks biasa: `*tebal*` `_miring_` `~coret~` ` ```mono``` `. Jadi yang benar adalah **kotak teks biasa** yang menuliskan penanda itu lewat toolbar, plus pratinjau yang membacanya kembali. Staf dapat kemudahannya tanpa satu pun karakter asing masuk ke pesan.

Nilai tetap dipegang `<textarea name=...>` sungguhan, jadi Server Action membacanya lewat FormData persis seperti sebelumnya -- tidak ada input tersembunyi yang bisa tidak sinkron dengan yang dilihat staf.

`core/waFormat.ts` memegang tiga fungsi murni (`parseWaMarkup`, `toggleMarker`, `insertAt`), diuji unit 17 kasus. Dua hal yang menempel di sana:

- **Penanda pembuka yang diikuti spasi BUKAN penanda.** Tanpa aturan ini, `"harga 5 * 3 * 2"` tampil tebal di pratinjau padahal WhatsApp menampilkan bintangnya apa adanya. Pratinjau yang berbohong lebih buruk daripada tanpa pratinjau.
- **Tombol format menekan dua kali MELEPAS penandanya**, bukan menumpuk jadi `**tebal**` -- yang di WhatsApp justru tampil sebagai tanda bintang.

`WaPreview` diekspor terpisah karena halaman Broadcast punya pratinjau yang lebih berguna daripada pratinjau bawaan editor: ia mengganti variabel dengan data pasien PERTAMA dari hasil filter, jadi staf melihat kalimat jadi alih-alih `{nama_pasien}`. Pratinjau itu tetap harus menampilkan tebal/miring dengan benar, dan satu-satunya cara menjaminnya sama dengan editor adalah memakai perender yang sama (`showPreview={false}` + `<WaPreview>`). Perenderannya lewat elemen React, **tidak pernah** `dangerouslySetInnerHTML` -- isinya berasal dari ketikan staf DAN dari kolom `sik`, jadi penyisipan HTML jadi mustahil, bukan sekadar tersaring.

Dropdown "+ Sisipkan variabel" dan peringatan variabel tak dikenal ada karena variabel salah ketik selama ini hanya ketahuan SESUDAH pesannya terkirim kosong ke pasien -- server memang menolaknya saat disimpan, tapi peringatan saat mengetik jauh lebih murah.

### Paginasi: satu penurunan, `src/core/pagination.ts`

Komponen `Pagination` sudah dipakai bersama sejak Fase 3 -- tapi itu TAMPILANNYA saja. Penurunan angkanya (baca `?page`, hitung offset, hitung total halaman) disalin di tiap halaman dengan tiga nama konstanta berbeda (`PAGE_SIZE`, `JUMLAH_PER_HALAMAN`, `PER_HALAMAN`) dan **dua tafsir yang berbeda** -- bentuk kegagalan yang sama persis dengan `respectsOptOut()`, `core/outboxStatus.ts`, dan `kunciPesanMasuk()`: beberapa tempat berjauhan menafsirkan sendiri satu hal yang sama, dan cukup satu yang berbeda untuk membuat satu halaman diam-diam berperilaku lain.

**Tiga cacat yang lahir dari selisih itu, ketiganya tanpa satu pun galat:**

- **Nomor halaman tak berbatas ATAS.** `/audit`, `/log`, `/antrean` memakai `Math.max(1, Number(pageParam) || 1)` tanpa `Math.min`; hanya `/nomor-bermasalah` menjepit. `?page=999` menampilkan tabel kosong berikut tombol "Sebelumnya" menuju 998 -- juga kosong. Tidak ada jalan kembali selain menyunting URL sendiri, dan yang terlihat di layar persis sama dengan "memang tidak ada datanya".
- **`/daftar-tolak` memotong pada `limit: 200` tanpa kendali apa pun.** Nomor ke-201 tidak pernah bisa dilihat, tanpa galat dan tanpa keterangan. Mesin tetap menghormatinya (`respectsOptOut()` membaca database, bukan halaman), tapi petugas yang mencarinya untuk MENGHAPUS tidak akan pernah menemukannya.
- **`/pesan-masuk` memotong pada 100.** Ia memang menampilkan "Menampilkan 100 terbaru dari N", tapi tidak menyediakan satu pun cara menjangkau sisanya -- keterangan yang menyebut masalahnya lalu berhenti di situ.

**DUA fungsi, bukan satu, dan itu bukan selera.** Menjepit halaman ke `totalHalaman` menuntut `count` sudah diketahui, sementara query barisnya menuntut `offset` sudah diketahui. Karena itu `bacaHalaman(param)` -> `count` -> `hitungPaginasi(diminta, jumlah, ukuran)` -> `findAll({ limit, offset })`. Tetap dua query, persis seperti `findAndCountAll` yang digantikannya; yang berubah cuma urutannya, dan itu yang membuat jepitannya mungkin. `/nomor-bermasalah` menyerahkan jumlahnya dari GROUP BY yang sudah ada alih-alih COUNT tersendiri -- `hitungPaginasi` menerima angka dari mana saja, jadi penghematan itu tidak hilang saat ikut pola bersama.

**Ukuran dinamai menurut JENIS daftarnya** (`UKURAN_HALAMAN.riwayat` 50, `.konfigurasi` 25), bukan angka telanjang di tiap halaman: `25` di dalam berkas halaman tidak memberi tahu siapa pun kenapa ia bukan 50. Barisnya pun memang beda bentuk -- baris konfigurasi memuat tombol aksi dan teks berbaris-baris.

**`hrefHalaman()` punya dua hal yang gampang dikira hiasan:**

- **Larik dipertahankan sebagai kunci berulang** (`?kab=A&kab=B`), bukan digabung berkoma. Di `/broadcast-terjadwal` akibatnya lebih dari sekadar saringan hilang: query string yang sama juga mengisi form "Buat jadwal baru", jadi menekan Berikutnya akan mengosongkan form yang sedang disusun staf.
- **Nama parameternya bisa diganti** (`namaParam`, default `page`). Aturan "`page` ditulis terakhir supaya menang" benar untuk satu tabel per halaman dan **diam-diam salah** begitu ada dua: `/pesan-masuk` memuat tabel pesan (`page`) DAN tabel grup (`gpage`), masing-masing membawa halaman tabel satunya. Satu nama bersama membuat tombol di satu tabel ikut menggeser tabel satunya, dan yang terlihat petugas adalah baris yang hilang tanpa sebab.

**Yang SENGAJA tidak dipaginasi, dan alasannya harus dibaca sebelum "menyeragamkannya":** tabel `template` (satu baris per pemicu, PK-nya `trigger_code` -- bertambah hanya saat ada pemicu BARU, tidak pernah seiring pemakaian, jadi kendali halamannya tidak akan pernah bisa berpindah. Dulu tertulis "tepat tujuh baris selamanya", dan `migrations/025` membuktikan kata "selamanya" itu keliru: yang benar sejak awal adalah satu per pemicu); `WaGroup.findAll()` di `/farmasi` dan `/template` (mengisi DROPDOWN pemilih grup, bukan tabel -- daftar pilihan terpotong menyembunyikan grup tanpa satu pun tanda, dan staf menyimpulkan grupnya belum tersinkron); `TemplateTarget.findAll()` di `/template` (mengisi modal Tujuan per pemicu); dan `hitungAdminAktif()` yang **wajib** menghitung seluruh tabel -- ia menyalakan peringatan "tinggal satu admin" DAN jadi masukan pagar `core/userPolicy.ts`, jadi mempersempitnya ke satu halaman bisa membuat pagarnya menolak penonaktifan yang sah.

**Satu jebakan verifikasi yang hampir menipu, dan ia bentuknya persis seperti jebakan `trustHost`:** percobaan pertama menjalankan `npm start` sementara PM2 `wakhanza-web` sudah memegang port 3100. `next start` mati dengan `EADDRINUSE`, `curl` tetap menjawab 200 dari proses PM2, dan seluruh uji berjalan melawan **build LAMA** -- 29 "kegagalan" atas kode yang sebenarnya benar. Sejak itu skrip ujinya memeriksa lebih dulu bahwa halaman yang fiturnya BARU memang punya penandanya, lalu `exit 2` bila tidak. Perlu diketahui juga: `.next` di disk sudah build baru sementara proses PM2 masih memegang kode lama di memori -- `pm2 restart wakhanza-web` diperlukan supaya dashboard yang dipakai petugas ikut berubah.

**Verifikasi HTTP dijalankan lewat instance PM2 yang SUDAH ADA, bukan `next start` di port sendiri.** Nasihat sebelumnya di tempat ini berbunyi kebalikannya ("jalankan di port sendiri, jangan berebut dengan PM2"), dan itu **dicabut atas permintaan pemilik sistem** dengan alasan yang mengalahkan alasan aslinya: instalasi ini berjalan di atas **database produksi**, jadi instance PM2 itulah lingkungan yang sesungguhnya -- server uji terpisah membuktikan sesuatu yang tidak dipakai siapa pun. Urutannya `npm run build` lalu `pm2 restart wakhanza-web`, dan diuji lewat port 3100.

Nasihat lama itu juga terbukti melahirkan bentuk barunya sendiri dari jebakan yang justru ia maksudkan untuk dicegah: `pkill -f "next start -p 3197"` TIDAK mematikan servernya (npx melahirkan proses anak dengan baris perintah lain), port tetap dipegang proses lama, dan seluruh uji berikutnya berjalan melawan build lama -- tanpa satu pun galat, dan dengan seluruh asersi lain tetap hijau karena yang berubah cuma satu kalimat. Yang membocorkannya cuma `Get-Process -Id <pid> | Select StartTime`. **Kalau toh terpaksa memakai port sendiri, matikan lewat PID dan buktikan portnya KOSONG sebelum start -- `pkill` atas baris perintah `npx` tidak cukup.**

**Perubahan yang tidak bisa dibuktikan tanpa login, dibuktikan lewat `.next`, bukan lewat akun uji.** `grep -rl "<penanda>" .next/server` menjawab "apakah build ini memuat perubahannya" tanpa menyentuh `app_user` sama sekali. Membuat akun admin sementara untuk uji peramban bisa dilakukan lewat `npm run users` dan memang reversibel, tapi ia menambah akun berhak penuh ke sistem yang memegang data pasien -- tempuh hanya bila yang diuji memang perilaku sesudah login, dan hapus di alur yang sama.

### Design system dashboard -- `src/components/ui/`
Semua halaman `(dashboard)/**` dan `/login` memakai primitif dari `src/components/ui/` (barrel export lewat `index.ts`) alih-alih menulis ulang class Tailwind mentah per halaman: `Button`/`LinkButton` (varian `primary`/`secondary`/`destructive`/`ghost`, ukuran `xs`/`sm`/`md`), `Input`/`Textarea`/`Select` (prop `fieldSize`, BUKAN `size` -- `size` sudah jadi atribut HTML asli di `<select>`), `Card` (+ `cardClassName` string untuk kasus elemen bukan `<div>`, mis. `<form>`), `Badge` (+ `outboxStatusVariant()` untuk status `Outbox`), `PageHeader`, `FilterChip`, `CheckboxList` (pengganti `<select multiple>` asli -- checklist + "pilih semua" + pencarian-jika->8 opsi, dipakai filter wilayah/cara-bayar di `/broadcast` dan `/broadcast-terjadwal`), `EmptyState` (opsional `icon`/`title`/`action` -- bentuk lama `<EmptyState>teks</EmptyState>` tetap berlaku), `Tabs` (tab berbasis URL; `<nav>` + `aria-current`, **bukan** `role="tablist"` -- lihat §`/farmasi` dipecah jadi TAB) dan `Callout` (kotak keterangan berjudul, opsional dilipat lewat `<details>` asli), `StatCard` (kotak KPI + sparkline), `Pagination`, `Skeleton`/`SkeletonTable`, `icons.tsx` (~20 ikon garis 24-grid, digambar sendiri alih-alih menambah paket ikon yang menarik ribuan modul ke bundel klien), dan class helper tabel (`tableWrapperClass`/`theadClass`/`rowClass`/`cellClass`). `WindowModeFields` (`/broadcast-terjadwal`) menerima daftar preset lewat **prop**, bukan mengimpor `./filters` -- modul itu menarik `khanza/*` yang berujung ke koneksi database dan tidak boleh masuk bundel klien.

**Istilah mesin tidak pernah sampai ke mata petugas** (`src/components/ui/labels.ts`). `skipped_no_contact`, `failed_permanent`, `QUEUE_REG`, `qr_pending` adalah kunci enum dan kode pemicu -- bentuk yang benar untuk database, log, dan kunci idempoten, tapi bukan untuk petugas pendaftaran. Semua tampilan memakai `outboxStatusLabel()`/`triggerLabel()`/`waStatusLabel()`, dan kode aslinya TETAP tersedia berdampingan (atribut `title`, atau teks mono kecil di halaman Koneksi) supaya tiket dukungan dan baris log masih bisa dicocokkan. Label statusnya murni presentasi -- tidak satu pun dipakai untuk perbandingan, penyaringan, atau disimpan; `href` filter tetap memakai kode mesin. `TRIGGER_LABEL` sengaja statis, bukan join ke `template.label`: halaman Antrean/Log memuat ribuan baris (satu join per halaman tanpa manfaat) dan `BROADCAST` memang tidak punya baris `template`.

**Aturan yang sama berlaku untuk SATUAN: milidetik disimpan, detik ditampilkan** (`src/core/duration.ts`). Milidetik benar untuk mesin -- `send_log.duration_ms` diisi `Date.now() - startedAt`, `polling.interval_ms` diserahkan apa adanya ke `setTimeout` -- tapi "300000" tidak memberi tahu siapa pun bahwa itu lima menit. Konversinya ada di BATAS TAMPILAN saja: kunci `app_setting` tetap `*_ms`, isinya tetap milidetik, `getSettingNumber()` di worker tidak berubah sama sekali. Tiga hal yang menempel di sini:

- **Konversi HANYA di dua titik**: saat isi form Pengaturan disiapkan, dan saat dikirim balik (`petakan()` di `PengaturanClient.tsx`, kunci ditandai `storedAsMs: true`). **Jangan** mengonversi di dalam `onChange` -- staf yang mengetik "1,5" kehilangan komanya begitu "1," dibolak-balik jadi angka di tiap ketukan.
- **Keduanya wajib persis kebalikan satu sama lain**, dan itu bukan kerapian melainkan syarat kebenaran: form Pengaturan mengirim ULANG seluruh kunci saat Simpan ditekan, termasuk yang tidak disentuh. Konversi yang meleset sedikit akan menggeser nilai hanya karena halaman dibuka lalu disimpan. Karena itu nilai yang BUKAN angka (kosong, teks, negatif) diteruskan apa adanya, tidak dijadikan `0`/`NaN`. Diuji `duration.test.ts` ("bolak-balik tanpa berubah") DAN dibuktikan lewat browser: dua kali Simpan tanpa menyentuh apa pun, keempat nilai tetap `60000/300000/3000/8000`.
- **Mengetik menerima koma maupun titik**, menampilkan koma (id-ID). Menolak salah satunya hanya menghasilkan nilai tersimpan yang salah tanpa satu pun pesan galat.

Di halaman Log, `formatDurationSeconds()` memakai satu desimal di bawah 10 detik dan bilangan bulat di atasnya ("12,3 s" tidak menambah apa pun atas "12 s"), dan yang lebih cepat dari satu desimal terkecil ditulis `<0,1 s` -- bukan dibulatkan jadi `0,0 s`, yang terbaca seperti nol atau gagal. Nilai milidetiknya tetap ada di atribut `title`, sama seperti kode pemicu.

**Kerangka halaman `src/components/AppShell.tsx`** (menggantikan `SidebarNav.tsx` yang dihapus). Sidebar tetap di `lg:` ke atas; di bawah itu jadi bilah atas + laci yang menutup layar, karena sidebar `w-56` tetap memakan setengah lebar tablet. Tiga hal yang gampang dirusak tanpa sadar saat menyentuhnya:

- Laci tertutup memakai `invisible`, BUKAN sekadar `-translate-x-full`. Elemen yang hanya digeser keluar layar tetap bisa dijangkau Tab, sehingga fokus keyboard bisa "hilang" ke menu tak terlihat.
- Laci ditutup saat pindah halaman lewat **penyesuaian state saat render** (`if (pathname !== lastPath)`), bukan `useEffect(() => setOpen(false), [pathname])`. Yang kedua memicu render berantai dan ditolak aturan lint `react-hooks/set-state-in-effect`; ia juga tidak menangani tombol maju/mundur peramban kalau diganti `onClick` per tautan.
- Ikon menu dikirim dari layout sebagai **kunci string**, bukan elemen React. Layout adalah Server Component; mengirim elemen ikon lintas batas server-klien ikut mengirim penanda komponennya di payload RSC untuk tiap menu.

`main` di AppShell wajib `min-w-0`: tanpa itu tabel dengan `overflow-x-auto` memaksa flex item melebar dan SELURUH halaman ikut bergeser ke samping.

**Kenapa lewat props varian, bukan `className` untuk menimpa warna/padding/ukuran**: dua utility Tailwind untuk properti CSS yang SAMA (mis. `rounded-md` bawaan komponen ditimpa `rounded-full` lewat `className`) menang berdasarkan urutan Tailwind MENGHASILKAN CSS-nya (urutan di config/scale), bukan urutan kemunculan di string `className` -- override lewat `className` bisa diam-diam KALAH. Karena itu Button/Input/Textarea/Select/Badge menerima varian sebagai prop terpisah (`variant`, `size`/`fieldSize`) yang tidak pernah tumpang tindih dengan apa pun yang boleh dikirim lewat `className` (lebar, margin, dsb. saja). Jangan tambah `px-*`/`py-*`/`text-*`/`bg-*`/`rounded-*` lewat `className` ke komponen ini -- kalau ukuran/warna yang ada tidak cukup, tambah varian baru di komponennya, jangan ditimpa dari luar.

Token warna (`src/app/globals.css`'s `:root`/`.dark`, dipetakan di `tailwind.config.ts`): `background`, `foreground`, `primary`, `muted`, `destructive`, `card` (permukaan panel, sedikit lebih terang dari `background` di mode gelap supaya card terlihat "terangkat"), `ring` (fokus), `success`/`warning` (status selain bahaya -- dulu dihardcode `green-600`/`amber-500` di `Badge`, melanggar aturan di bawah), `chart-sent`/`chart-failed` (lihat §Halaman Ringkasan). Tambah token warna baru di SINI (dua tempat: `:root` dan `.dark`), jangan hardcode `dark:bg-slate-800` dsb. langsung di komponen halaman kecuali kasus yang MEMANG sengaja tidak ikut tema (contoh: QR code di `KoneksiClient.tsx` tetap `bg-white` di kedua tema karena butuh kontras penuh untuk bisa dipindai -- ada komentar di kode yang menjelaskan ini).

### Peringatan gangguan (`worker/alert.ts`) -- jalur yang tidak ikut mati bersama yang diberitakannya

Watchdog memang memulihkan sesi yang tersangkut sendiri, tapi kalau pemulihannya gagal berulang tidak ada satu pun jalur yang memberi tahu siapa-siapa: panel di `/ringkasan` mengandalkan ada orang yang membuka halamannya, dan gangguan 14 jam itu bermula pukul 01:25.

**Tidak bisa lewat WhatsApp, dan itu bukan detail kecil** -- hampir semua yang layak dialarmkan di sistem ini adalah "WhatsApp tidak jalan". Bentuknya **webhook HTTP generik**, bukan SMTP: nol dependensi baru (`fetch` sudah bawaan Node, dan menambah klien SMTP berarti satu paket lagi yang harus dirawat di server RS), dan satu URL yang sama bisa diarahkan ke bot Telegram, webhook Slack/Discord, atau endpoint milik IT rumah sakit. Field `text` diletakkan di depan payload dengan nama itu supaya ketiganya memakainya apa adanya tanpa adaptor.

Empat hal yang menempel padanya:

- **`alert.webhook_url` default KOSONG = tidak ada peringatan yang dikirim.** Konsisten dengan `autoreply.enabled`: fitur yang menghubungi dunia luar dinyalakan sadar-sadar, bukan menyala karena kebetulan terpasang.
- **Jeda per JENIS peringatan** (`alert.min_interval_minutes`, default 15), disimpan di memori bukan database -- satu proses worker, dan peringatan yang hilang saat restart justru YANG BENAR karena restart itu sendiri kejadian baru. Tanpa jeda, satu gangguan semalaman jadi ratusan pesan dan penerimanya berhenti membacanya, persis alasan level log dipisah `debug`/`warn` di `wa-client.ts`. `kind: 'test'` dikecualikan: staf yang menekan tombol uji berulang sambil membetulkan URL harus melihat hasilnya.
- **`sendAlert()` TIDAK PERNAH melempar**, dan punya batas waktu keras 10 detik. Peringatan yang gagal tidak boleh menjatuhkan proses yang sedang berusaha melaporkan masalahnya sendiri -- itu menukar satu gangguan dengan dua.
- **Isinya cuma keadaan sistem** -- tidak pernah nomor pasien, nama, atau isi pesan. Webhook mengirim ke pihak ketiga di luar kendali RS, jadi aturan §9.7 berlaku lebih ketat lagi.

Dipasang di tiga titik, semuanya keadaan "tidak ada pesan yang bisa terkirim": watchdog sesi tersangkut, pemeriksaan kesehatan gagal, dan **pemeriksaan keamanan startup gagal** -- yang terakhir paling senyap dari semuanya, karena PM2 terus menyalakan ulang sementara dashboard tetap tampil normal (proses web hidup sendiri).

**Tombol "Kirim peringatan uji" di `/pengaturan` menguji nilai yang SUDAH TERSIMPAN, bukan yang sedang diketik** -- menguji isi kotak yang belum disimpan akan melaporkan "berhasil" atas URL yang tidak akan dipakai worker saat gangguan sungguhan datang. Webhook yang tidak pernah dicoba sama saja dengan tidak ada: URL salah ketik, bot yang belum diundang ke grup, atau token kedaluwarsa semuanya diam sampai saat paling buruk untuk menemukannya.

**Kunci baru wajib didaftarkan ke `EDITABLE_KEYS`** di `api/settings/route.ts` -- itu daftar-izin, jadi kunci yang tidak terdaftar tersimpan diam-diam tanpa efek.

### Akun dashboard: dua jalur, satu pagar

`/pengguna` (admin-only) dan `/profil` (semua peran) menggantikan keadaan lama di mana pengelolaan akun HANYA ada di CLI. Yang menempel di sini:

- **Pagar hidup di `core/userPolicy.ts` + `lib/userAdmin.ts`, dipakai BERSAMA oleh halaman dan `scripts/manage-users.ts`.** Begitu dashboard jadi jalur kedua ke `app_user`, pagar yang tinggal di salah satu sisi adalah pagar yang cepat atau lambat dilewati -- yang menambah tombol di halaman tidak punya alasan membuka skrip CLI untuk mencari larangan apa yang pernah ditulis di sana. `userPolicy.ts` sengaja fungsi murni: keadaan yang paling perlu diuji ("satu-satunya admin aktif yang tersisa") kalau dibuat di database berarti menonaktifkan admin sungguhan lebih dulu, dan uji yang gagal di tengah meninggalkan sistem tanpa admin.
- **CLI TIDAK dihapus setelah halamannya jadi**, dan itu bukan kelalaian: ia justru untuk keadaan saat halamannya tidak bisa dipakai -- admin terakhir terkunci, sandi admin hilang, atau `wakhanza-web` tidak mau hidup.
- **Menurunkan peran admin terakhir dijaga sama ketatnya dengan menonaktifkannya**, dan ini yang paling gampang lolos: sesudahnya tabel tetap menampilkan satu baris "aktif", jadi tidak ada yang terlihat hilang.
- **Menonaktifkan/menurunkan/menghapus DIRI SENDIRI ditolak.** Tidak mengunci siapa pun (admin lain masih ada), tapi pelakunya tetap bisa memakai dashboard sampai sesinya habis lalu tiba-tiba tidak bisa masuk lagi tanpa ada yang menjelaskan kenapa.
- **HAPUS ada berdampingan dengan nonaktifkan, bukan menggantikannya**, dan pagarnya sama persis (admin aktif terakhir, diri sendiri) karena keduanya berujung pada orang yang sama tidak bisa masuk lagi. Yang BERBEDA cuma satu: `bolehNonaktifkan` meloloskan akun yang sudah nonaktif sebagai "bukan perubahan", sementara menghapusnya tetap menghilangkan barisnya selamanya -- jadi tidak ada jalan pintas yang setara di `bolehHapus`. Empat hal yang menempel:
  - **Baris audit dan penghapusannya satu transaksi** (`db.transaction`, `logAudit(..., { transaction })`). Begitu barisnya hilang, `audit_log` adalah SATU-SATUNYA tempat yang masih menyebut akun itu pernah ada; hapus-berhasil-catat-gagal meninggalkan akun yang lenyap tanpa jejak siapa menghapusnya, dan tidak ada lagi sumber untuk merekonstruksinya. Rollback bukan perintah DELETE, jadi append-only `audit_log` tetap utuh.
  - **Riwayat audit orangnya TIDAK ikut terhapus dan memang tidak bisa** -- `actor` menyimpan username sebagai teks, bukan foreign key (`app_user` tidak diacu FK dari mana pun). Efek sampingnya justru kebalikannya: usernamenya jadi bisa dipakai lagi, dan sejak itu riwayat lama terbaca seolah milik orang baru. Yang menutup celahnya bukan pagar melainkan **detail baris `user_delete` yang memuat username + peran** -- itulah batas yang memisahkan dua pemakai nama yang sama. Memblokir pemakaian ulang username akan membakar nama seperti `loket1` selamanya, jadi sengaja tidak dilakukan.
  - **Tombol Nonaktifkan turun jadi `secondary`, Hapus yang memegang `destructive`.** Dua tombol merah berdampingan membuat yang benar-benar tidak bisa ditarik kembali berhenti menonjol; yang reversibel tidak boleh terlihat sama bahayanya.
  - **`ConfirmDialog` dapat prop `pendingLabel`.** Sebelumnya teks "Menghapus..." dihardcode, sehingga dialog Nonaktifkan menampilkannya juga saat diproses -- orang yang membacanya wajar mengira ia salah tekan.
- **Perbedaan nonaktif vs hapus ditulis di ATAS tabel, bukan cuma di dialog konfirmasi.** Yang menentukan pilihan adalah "apakah akun ini mungkin dipakai lagi", dan itu sudah diketahui sebelum tombolnya ditekan; dialog yang baru menjelaskannya datang setelah orangnya memilih.
- **Ganti sandi SENDIRI wajib menyertakan sandi lama; admin menyetel sandi orang lain TIDAK.** Bedanya bukan gaya: tanpa sandi lama, satu sesi yang terlanjur terbuka di komputer loket cukup untuk mengunci pemilik akunnya keluar dari akunnya sendiri. Admin memang tidak mengetahui sandi orang lain, jadi di sana yang menjaga adalah `requireRole` dan `audit_log`.
- **Username tidak bisa diubah**, dan alasannya ditulis di layar alih-alih kotaknya sekadar ditiadakan: ia dipakai sebagai `actor` di `audit_log`, jadi menggantinya memutus seluruh jejak lama dari pemiliknya. Kotak yang hilang tanpa penjelasan terbaca sebagai fitur yang belum dibuat, lalu ditanyakan berulang kali.
- **Profil dibaca dari DATABASE, bukan dari sesi.** Sesi JWT isinya beku sejak login; membacanya dari sana membuat halaman ini berbohong tepat sesudah penggunanya mengganti namanya sendiri.
- **Pesan sukses modal dinaikkan ke halaman.** Ditemukan saat pengujian, bukan diperkirakan: "Ubah" dan "Tambah" masih terlihat hasilnya di tabel, tapi SETEL SANDI tidak mengubah apa pun yang tampak -- modal yang menutup diam-diam terbaca sama persis seperti modal yang gagal tanpa pesan.

### `npm run users`, dan kenapa JWT membatasi artinya "dinonaktifkan"

`seed:admin` MENOLAK bila username sudah ada, dan tidak ada halaman pengelolaan pengguna. Sampai `scripts/manage-users.ts` ada, tidak ada satu pun jalan yang didukung untuk mengganti kata sandi, menonaktifkan akun petugas yang sudah pindah, atau membuka akun terkunci -- selain menyunting `app_user` lewat SQL mentah, yang berarti menghitung hash bcrypt sendiri di luar aplikasi dan tidak meninggalkan jejak `audit_log`. Semua tindakannya tercatat dengan pelaku `cli:<akun OS>` (dibedakan sengaja dari username staf), dan **kata sandinya tidak pernah ikut dicatat**.

**Pagar yang tidak boleh dilepas**: menonaktifkan admin aktif TERAKHIR ditolak. Halaman pengaturan, template, broadcast, dan audit semuanya admin-only, jadi tanpa admin aktif satu-satunya jalan kembali adalah menyunting database langsung.

**`is_active=0` menghentikan LOGIN BERIKUTNYA, bukan sesi yang sedang berjalan.** Sesinya JWT, bukan session di database (TECH_STACK.md, sengaja -- "sesedikit mungkin komponen"), jadi tidak ada tempat untuk mencabutnya di sisi server. Petugas yang harus diputus saat itu juga perlu `AUTH_SECRET` diganti di `.env` + `wakhanza-web` dimulai ulang, dan itu membatalkan sesi SEMUA orang sekaligus. Batas ini nyata dan harus diketahui sebelum dibutuhkan, bukan ditemukan saat sedang buru-buru.

### Halaman Ringkasan (`/ringkasan`) -- halaman pendaratan

Sesudah login mendarat di `/ringkasan`, bukan `/koneksi` seperti sebelumnya: halaman Koneksi menjawab "bagaimana menyambungkan WhatsApp", pertanyaan yang muncul sekali saat pemasangan; yang ditanyakan petugas tiap hari adalah "apakah pesannya terkirim?". Redirect 403 di `/audit`, `/broadcast`, `/broadcast-terjadwal` dan `redirectTo` di `login/actions.ts` ikut diarahkan ke sini.

**`InboundStatus` -- satu-satunya panel yang mengukur arah MASUK.** Semua angka lain di halaman ini (terkirim, menunggu, perlu ditinjau, grafik volume) mengukur apa yang KITA KIRIM. Saat WhatsApp memindahkan pengalamatan ke `@lid` dan setiap pesan pasien dibuang di baris kedua listener, seluruh halaman ini tetap hijau berjam-jam. Nol pesan masuk seharian di nomor yang dipakai pasien adalah tanda rusak, bukan hari sepi -- tapi hanya kalau ada yang menampilkannya. Diletakkan tepat di bawah `SystemStatus` karena keduanya menjawab pertanyaan yang sama dari dua arah.

Empat hal yang menempel padanya:

- **Dihitung dari `auto_reply_log`, bukan `outbox`.** Pertanyaan pasien yang tidak dibalas justru TIDAK meninggalkan jejak di `outbox` sama sekali -- menghitung dari sana akan buta persis pada kasus yang perlu dilihat.
- **Bukan `StatCard` seperti empat kotak di atasnya.** Angka telanjang "0" di deretan kotak terbaca sebagai kabar baik (nol gagal, nol perlu ditinjau). Di sini nol adalah kabar buruk, jadi ia perlu kalimat.
- **Keputusannya di `core/inboundHealth.ts`, fungsi murni.** Bukan kerapian: keadaan yang paling perlu dibuktikan adalah "belum pernah menerima apa pun", dan `auto_reply_log` sengaja tanpa grant `UPDATE` sehingga baris nyata tak bisa disembunyikan sementara untuk mensimulasikannya lewat database. Unit test satu-satunya jalan. `null` (belum pernah) dihitung **sunyi**, bukan aman.
- **Saat `autoreply.enabled` mati, panelnya menolak menilai** (`tidak-terpantau`). Pencatatan pesan masuk ikut mati di situ, jadi nol tidak berarti apa-apa; melaporkannya sebagai kecurigaan akan jadi peringatan palsu permanen di setiap RS yang belum menyalakan balasan otomatis -- dan peringatan permanen sama saja dengan tidak ada peringatan.

**Sekalian diperbaiki: KPI "Perlu ditinjau" menghitung sendiri `failed_permanent + expired`** alih-alih memakai `NEEDS_REVIEW` yang dipakai tabel tepat di bawahnya. Sesudah `failed` masuk daftar itu, angkanya bisa mengatakan nol sementara daftar di bawahnya tidak kosong. Sekarang dijumlahkan dari daftar yang sama.

**Satu definisi hari dipakai seluruh halaman: `outbox.created_at`** (kapan pesan masuk antrean), bukan `sent_at`. Pesan yang muncul pukul 22:00, tertahan jam tenang, lalu terkirim pukul 07:00 keesokan hari tetap dihitung pada hari kejadiannya -- kalau tidak, satu pesan bisa tampil di dua hari berbeda tergantung angka mana yang sedang dilihat.

**`migrations/009` menambah `ix_created (created_at, status, trigger_code)`, dan urutan kolomnya sempat salah.** Percobaan pertama `(status, created_at)` -- alasannya "kueri menyaring status DAN tanggal" -- terbukti keliru lewat EXPLAIN terhadap database sungguhan: rincian per jenis pesan tidak menyaring status sama sekali, jadi kolom pertamanya tidak terpakai dan kuerinya jatuh ke `type: ALL`. `created_at` di depan karena itu satu-satunya kolom yang disaring SEMUA kueri ringkasan; dua kolom sisanya membuat ketiganya jadi covering index. Halaman ini dibuka tiap login, jadi tanpa indeks yang benar setiap login memicu pemindaian penuh `outbox` -- tabel yang paling cepat tumbuh di skema ini.

**Palet grafik divalidasi lewat skrip, bukan dikira-kira.** Hijau-merah adalah pasangan terburuk untuk buta warna deutan, jadi `--chart-sent`/`--chart-failed` TIDAK memakai `--primary`/`--destructive` apa adanya: `--primary` (hue 158) GAGAL pemeriksaan pita kecerahan dan hanya mencapai CVD ΔE 7,1 di mode gelap. Nilai yang dipakai sekarang dicari lewat penelusuran terhadap validator palet dan lolos SEMUA pemeriksaan di kedua mode terhadap permukaan `--card` yang sebenarnya (terang `#30a68b` vs `#dc2828` di `#ffffff` -> CVD ΔE 12,3 · normal ΔE 32,1; gelap `#2c967d` vs `#e05252` di `#141c2e` -> CVD ΔE 9,0 · normal ΔE 27,2; ambang CVD >= 8, normal >= 15, kontras >= 3:1). **Mengubah salah satu nilai itu berarti menjalankan ulang validasinya**, dan nilai mode gelap bukan pembalikan otomatis dari nilai terang -- ia dipilih ulang untuk permukaan gelap.

`VolumeChart` dibangun dari elemen HTML biasa, bukan SVG: dengan begitu tetap Server Component tanpa satu baris pun JavaScript klien, sementara tooltip per batang cukup ditangani `group-hover` CSS. Ketentuan bentuk yang menempel padanya: batang dibatasi 24px dan tidak pernah memenuhi slotnya, ujung data membulat 4px sementara pangkalnya siku di garis dasar, pemisah antar segmen adalah **celah 2px sewarna permukaan** (`gap-[2px]`) dan bukan garis tepi, hari nol tetap menyisakan jejak tipis (hari mati harus terlihat sebagai batang kosong, bukan menghilang), warna batang hanya di batang (angka dan legenda memakai token teks), dan `<details>` "Lihat sebagai tabel" adalah jalur baca yang tidak bergantung warna maupun hover. Rincian per jenis pesan sengaja berupa **tabel/meter, bukan grafik** -- di atas ~7 kelas yang semuanya bermakna, warna berhenti membedakan apa pun.

## Keputusan yang dulu terbuka, sudah diputuskan saat implementasi

- **`core/phone.ts`**: diimplementasikan **ketat** -- persis 7 langkah ARCHITECTURE §5.1, tanpa heuristik tambahan. Diverifikasi terhadap seluruh 8.117 baris `sik.pasien` nyata: 59,5% langsung valid (melampaui baseline 45% di PRD), sisanya masuk `patient_contact` dengan alasan penolakan untuk dikoreksi manual lewat dashboard.

### `npm run scan:contacts` -- kenapa pemindaian awal perlu ada terpisah

`worker/contactResolver.ts` menulis satu baris `patient_contact` hanya SAAT sebuah pemicu sudah melewati pasien itu. Konsekuensinya luput cukup lama: di hari pertama produksi halaman `/nomor-bermasalah` kosong, lalu terisi seorang demi seorang **sesudah** tiap pasien gagal dikirimi. Nomor yang tidak terpakai baru ketahuan setelah pesannya telanjur hilang -- padahal daftarnya bisa diketahui seluruhnya di muka. `scripts/scan-contacts.ts` membaca `sik.pasien` sekali jalan (SELECT saja, keyset pagination lewat PK + jeda antar batch supaya tidak berebut koneksi dengan SIMRS) dan mengisi semuanya. **Baris `source='manual'` tidak pernah ditimpa** -- koreksi petugas mengalahkan normalisasi otomatis (F2.1-F2.3), dan skrip ini tidak boleh membatalkan pekerjaan orang. Aman dijalankan berulang; punya `--dry-run`.

Hasil nyata di database ini: 8.118 pasien, 4.834 (59,5%) terpakai -- **angka yang sama persis dengan verifikasi `core/phone.ts` dulu**, jadi sekalian membuktikan skripnya memakai normalisasi yang sama, bukan salinan yang menyimpang.

**Sebarannya timpang, dan itu mengubah bentuk halamannya.** Dari 3.284 nomor bermasalah, 3.166 beralasan `empty` -- pasien yang di Khanza memang tidak punya nomor sama sekali. Itu bukan salah ketik yang bisa dibetulkan sambil menatap layar; nomornya harus diminta saat pasien datang lagi. Yang benar-benar bisa dikerjakan petugas dari mejanya cuma 118 (`too_short` 55, `not_mobile` 52, `unparseable` 11). Karena chip saringan dulu diurutkan mengikuti urutan kunci enum, `Kosong` tampil lebih dulu dan mengubur 118 baris itu. Sekarang chip-nya **diurutkan yang bisa dikerjakan lebih dulu, membawa jumlah masing-masing**, ditambah keterangan "menampilkan 100 dari N" (halamannya berbatas 100 baris dan dulu tidak mengatakannya) dan satu kalimat khusus pada saringan `Kosong` yang menjelaskan kenapa tidak ada yang bisa dikoreksi di situ.

- **`BILLING_READY` — kirim ke pasien atau penanggung jawab?** (PRD §10 #3) Ternyata pertanyaan ini tidak berdampak teknis: `reg_periksa.p_jawab` cuma berisi NAMA, bukan nomor kontak terpisah. Satu-satunya nomor yang tersedia tetap `pasien.no_tlp`, apa pun jawabannya (lihat komentar di `khanza/billing.ts`).

## Yang masih perlu keputusan rumah sakit (bukan teknis)

- **Daftar layanan/poli sensitif** (F4.3) dan **kode pemeriksaan sensitif**: default kosong (`[]`), diisi lewat halaman Pengaturan dashboard (`/pengaturan`, admin-only) begitu RS memutuskan.
- **Jam kirim pengingat H-1** (PRD §10 #4): default 18:00 WIB (`schedule.book_remind_hour` di `app_setting`), dapat diubah dari dashboard tanpa restart.
- **Volume harian sesungguhnya** (PRD §9 #1): database dev berisi riwayat historis tapi bukan cerminan beban nyata -- baru terjawab saat Fase 5 (uji coba `dryrun` terhadap salinan data RS sungguhan).
- **Dasar hukum BROADCAST**: fitur ini mengirim pesan ke pasien berdasarkan riwayat kunjungan lampau, bukan kejadian yang sedang berlangsung seperti ketujuh pemicu reaktif -- secara kebijakan ini lebih dekat ke pemberitahuan/ajakan daripada notifikasi transaksional. Kode TIDAK membedakan keduanya secara hukum (memakai mekanisme privasi/opt-out yang sama), jadi RS yang harus memutuskan pemakaian macam apa yang sesuai basis persetujuan pasien yang ada, sebelum dipakai ke pasien sungguhan dalam jumlah besar.
- **Siapa saja yang boleh ada di dalam grup apotek** (NOTIFIKASI FARMASI): ini satu-satunya fitur yang mengirim data pasien ke penerima yang **keanggotaannya diatur di luar sistem ini**. Broadcast dan ketujuh pemicu menuju satu nomor pasien yang bersangkutan sendiri; sebuah grup bisa ditambahi orang oleh admin grup mana pun, kapan saja, tanpa terlihat di dashboard. Kode sudah membatasi diri sejauh yang bisa dilakukan kode: nama obat/jumlah/aturan pakai/diagnosis tidak pernah diambil dari `sik`, poli sensitif otomatis diganti pesan tanpa identitas, dan isi pesannya bisa dipersempit sampai tinggal `{no_resep}` saja. Yang TIDAK bisa diputuskan kode: apakah grup yang dipakai memang khusus apotek (bukan grup umum RS), siapa yang meninjau anggotanya secara berkala, dan apakah basis persetujuan pasien di RS mencakup identitasnya muncul di WhatsApp pribadi tiap anggota grup. `farmasi.enabled` default MATI justru supaya ini diputuskan lebih dulu. Salah satu grup di mesin ini beranggota **722 orang** -- angka yang layak dilihat sebelum memilih grup.

- **Pengingat kontrol non-BPJS: yang harus diputuskan BUKAN privasinya, melainkan MANA dari dua pemicu yang dipakai** (`KONTROL_ULANG`, migrations/032). Isinya tidak menambah satu pun kelas data baru -- tanggal, dokter, nomor surat, dan keenam kolom klinis di `skdp_bpjs` tidak pernah dibaca. Yang benar-benar perlu keputusan RS adalah akibat dari setelan Khanza `JADIKANBOOKINGSURATKONTROL`, yang di mesin ini bernilai `yes`: setiap surat kontrol otomatis jadi booking, sehingga **BOOK_REMIND sudah mengingatkan pasien yang sama**. Menyalakan keduanya berarti pasien menerima dua pesan untuk satu kunjungan -- dan yang menerima keluhannya adalah loket, bukan sistem ini. Pilih satu: BOOK_REMIND (berlaku untuk semua booking, kalimatnya umum) atau KONTROL_ULANG (hanya pasien bersurat kontrol, kalimatnya menyebut nomor suratnya). Kode sengaja TIDAK memagarinya, karena di instalasi yang setelan Khanza-nya `no` justru pemicu inilah satu-satunya yang memberi tahu pasien; yang ada peringatan di `/template`, terbentang dan kuning tepat saat keduanya aktif. Perlu diketahui juga bahwa **menu Surat Kontrol praktis sudah ditinggalkan di RS ini** -- 253 surat pada Des 2023-Feb 2024 lalu berhenti, nol di database produksi -- jadi menyalakannya sekarang kemungkinan besar tidak menghasilkan apa pun, dan pertanyaan di atas baru menjadi nyata bila poliklinik mulai memakai menu itu lagi.

- **Apakah persediaan dan daftar harga apotek boleh dijawab otomatis, dan kepada siapa** (BALASAN STOK OBAT, `farmasi.stok_mode`): ini bukan pertanyaan privasi pasien -- yang dibaca katalog barang, bukan resep siapa pun -- melainkan pertanyaan **dagang dan kebijakan layanan**. Mode `semua` membuat siapa pun yang mengirim WhatsApp ke nomor RS bisa menanyakan harga obat apa saja, dan itu pilihan yang wajar bagi apotek yang memang mengumumkan harganya (pasien tidak perlu datang sia-sia). Yang perlu diputuskan sadar-sadar: apakah harga yang tersimpan di Khanza memang harga yang siap diumumkan (bukan tarif internal yang belum diperbarui), dan siapa yang memastikan katalognya tetap mutakhir -- jawaban otomatis yang menyebut harga lama lebih buruk daripada tidak menjawab, karena orang datang membawa uang yang salah. Angka persediaan sengaja hanya muncul pada mode `petugas`. Bawaannya `mati` justru supaya keputusan ini diambil lebih dulu.

- **Siapa yang boleh meminta REKAP kekurangan gudang** (`farmasi.darurat_tanya`, migrations/022): pertanyaannya beda jenis dari yang di atas, dan lebih sempit. Rekap darurat bukan daftar harga -- ia daftar apa saja yang sedang tidak bisa dilayani apotek, dan pengetahuan itu punya nilai lain sama sekali (pemasok yang tahu, pesaing yang tahu). Karena itu kode TIDAK menyediakan mode `semua` sama sekali: penanya wajib terdaftar `boleh_tanya`, dan itu batas yang tidak bisa dilonggarkan lewat pengaturan mana pun. Yang tetap harus diputuskan RS: **siapa saja yang ada di dalam grup yang dicentang itu**, karena satu centang membuat setiap anggotanya bisa memanggil rekap kapan saja -- dan keanggotaan grup diatur di luar sistem ini, sama seperti peringatan tentang grup apotek di bawah. Perlu diketahui juga bahwa `farmasi.darurat_tanya` **bawaannya menyala**: RS yang sudah menyalakan `farmasi.darurat_enabled` untuk rekap TERJADWAL ikut mendapat arah masuknya, dan kalau itu tidak diinginkan sakelarnya harus dimatikan sendiri di `/farmasi`.

- **Apakah harga beli dari pemasok boleh beredar di WhatsApp, dan siapa yang membacanya** (PENGADAAN, `farmasi.pengadaan_harga`, migrations/028): ini pertanyaan yang paling BERBEDA jenisnya di daftar ini, karena tidak ada satu pun pasien yang terlibat -- `pembelian`/`detailbeli` memang tidak punya kolom yang menautkannya dengan seorang pasien, dan variabel pasien tidak tersedia untuk ditambahkan ke templatenya. Yang beredar adalah informasi **dagang**: berapa yang dibayar rumah sakit ke tiap pemasok, per barang. Pengetahuan itu punya nilai bagi pihak yang seharusnya tidak memilikinya -- pemasok lain yang tahu harga pesaingnya, atau pemasok yang sama yang tahu RS tidak membandingkan harga. Kode membatasi diri sejauh yang bisa: sakelar harga bisa dimatikan dan saat mati kolomnya tidak dibaca sama sekali, sementara `terima_pengadaan` sengaja dipisah dari ketiga centang lain supaya grup shift apotek bisa menerima notifikasi resep TANPA ikut menerima nota pembelian. Yang TIDAK bisa diputuskan kode, dan sama seperti peringatan grup apotek di bawah: siapa saja yang ada di dalam grup tujuan, dan siapa yang meninjau anggotanya secara berkala. Perlu diketahui bahwa `farmasi.pengadaan_harga` **bawaannya menyala** -- nota tanpa harga bukan nota, dan yang menahan seluruhnya adalah `farmasi.pengadaan_enabled` yang mati; kalau RS ingin notanya beredar tanpa harga, sakelarnya harus dimatikan sendiri di `/farmasi`.

- **Apakah rencana pembelian boleh beredar sebelum barangnya ada** (SURAT PEMESANAN, `farmasi.pemesanan_enabled`, migrations/030): pertanyaan dagang yang sama dengan PENGADAAN di atas berlaku utuh -- harga per barang, per pemasok, tanpa satu pun pasien terlibat -- **plus satu lapis yang tidak dipunyai pengadaan**: yang beredar di sini adalah rencana, bukan catatan. Nota pembelian menceritakan transaksi yang sudah terjadi; surat pemesanan menceritakan apa yang **akan** dibeli, dari siapa, berapa banyak, dan pada harga berapa -- pengetahuan yang jauh lebih berharga bagi pemasok pesaing justru karena tawarannya masih bisa diubah. Ditambah lagi statusnya bisa dibalik staf kapan saja, jadi sebuah pesanan yang sudah diberitakan bisa saja tidak pernah jadi. Kode membatasi diri sejauh yang bisa: sakelar harga bisa dimatikan (dan saat mati kolomnya tidak dibaca sama sekali), dan `terima_pemesanan` sengaja dipisah dari `terima_pengadaan` supaya memantau apa yang sedang dipesan tidak memaksa ikut menerima setiap nota penerimaan. Yang TIDAK bisa diputuskan kode: siapa saja yang ada di dalam grup tujuan, dan apakah bagian pengadaan memang ingin rencana belanjanya terbaca di WhatsApp. Perlu diketahui juga bahwa di mesin ini menunya praktis belum dipakai -- **satu pesanan dalam lebih dari dua tahun** -- jadi menyalakannya sekarang kemungkinan besar tidak menghasilkan apa pun, dan pertanyaannya baru menjadi nyata bila bagian pengadaan mulai memakai menu itu.

- **Siapa yang boleh tahu berapa nilai barang yang disumbangkan, dan dari siapa** (HIBAH, `farmasi.hibah_enabled`, migrations/031): pertanyaan dagang pada PENGADAAN dan SURAT PEMESANAN **tidak** berlaku utuh di sini -- tidak ada pemasok yang tawarannya bisa dirugikan, dan angkanya bukan hasil negosiasi RS. Yang menggantikannya pertanyaan yang berbeda jenisnya: **sebuah hibah punya PEMBERI, dan pemberi itu pihak luar yang namanya ikut beredar.** "DINKES PROPINSI" tidak menimbulkan pertanyaan; seorang perorangan, sebuah perusahaan, atau sebuah lembaga yang memberi dengan diam-diam bisa saja tidak mengharapkan namanya muncul di WhatsApp sekian anggota grup -- dan tidak ada satu pun kolom di Khanza yang menyatakan pemberi mana yang ingin disebut. Lapis kedua: **nilai yang DIAKUI adalah angka akuntansi** (yang dijurnal sebagai PENDAPATAN HIBAH), dan pada barang pemberian angka itu adalah penilaian RS sendiri -- bukan fakta transaksi seperti harga beli. Beredarnya di luar bagian yang menetapkannya mengundang pertanyaan yang tidak bisa dijawab di grup WhatsApp. Kode membatasi diri sejauh yang bisa: sakelar nilai per barang bisa dimatikan (dan saat mati kolomnya tidak dibaca sama sekali), kedua total bisa dihapus dari templatenya, dan `terima_hibah` sengaja dipisah dari `terima_pengadaan` supaya bagian yang mencocokkan pembelian tidak otomatis ikut membaca daftar pemberi. Yang TIDAK bisa diputuskan kode: siapa saja yang ada di dalam grup tujuan, dan apakah para pemberi hibah RS ini bersedia namanya disebut di sana. Perlu diketahui juga bahwa **menu Hibah Obat & BHP di RS ini belum pernah dipakai sama sekali** (nol baris), jadi menyalakannya sekarang tidak menghasilkan apa pun -- pertanyaan di atas baru menjadi nyata saat bagian gudang mulai mencatat hibah lewat menu itu.

- **Pertanyaan yang sama, kini berlaku untuk KETUJUH PEMICU PASIEN** (`template_target`, migrations/018): sejak tujuan tambahan bisa dipasang per pemicu, notifikasi antrian/hasil lab/obat/tagihan bisa ikut mengalir ke sebuah grup WhatsApp. Yang membuatnya lebih berat daripada kasus farmasi, dan karena itu perlu diputuskan terpisah: isinya adalah **pesan yang sama dengan yang diterima pasien**, termasuk namanya dan nama polinya -- bukan versi ringkas yang sengaja dipersempit seperti template farmasi. Kode membatasi diri sejauh yang bisa: poli sensitif otomatis diganti template generik, dan `tujuan_mode` default `pasien` sehingga tidak satu pun pemicu mengalir ke grup sampai ada yang memasangnya sendiri. Dua hal yang TIDAK bisa diputuskan kode: apakah basis persetujuan pasien mencakup identitas kunjungannya terbaca seluruh anggota sebuah grup, dan -- khusus untuk mode `tujuan` -- apakah benar pasien TIDAK perlu diberi tahu untuk pemicu itu, karena sejak saat itu ia tidak menerima apa pun dari pemicu tersebut. Perlu diingat juga bahwa **permintaan berhenti dari pasien tidak menghentikan salinan ke grup**; kalau itu tidak sesuai kebijakan RS, jangan pakai mode yang melibatkan tujuan tambahan.

- **DUA keputusan terpisah untuk BPJS** (`/bpjs`, migrations/024), dan menggabungkannya adalah kekeliruan yang paling gampang terjadi karena keduanya di satu halaman. (1) **Pembatalan Mobile JKN** memuat nama pasien, no. RM, dan poli tujuannya, dan penerimanya sebuah grup yang keanggotaannya diatur di luar sistem ini — pertanyaannya sama persis dengan grup apotek di atas, dan kode sudah membatasi diri sejauh yang bisa (poli sensitif otomatis diganti pesan tanpa identitas, dan isi pesannya bisa dipersempit sampai tinggal jadwalnya saja). (2) **Pengingat surat kontrol** menuju PASIEN, jadi pertanyaannya bukan tentang grup melainkan tentang **isi janji medis**: kode tidak pernah membaca satu pun kolom klinis dari `bridging_surat_kontrol_bpjs` (tabel itu menyimpan `status_prb` berisi diagnosis kronis apa adanya, plus HBA1C/GDP/eGFR/tekanan darah), tapi yang TIDAK bisa diputuskan kode adalah apakah RS memang ingin mengingatkan seluruh pasien kontrol tanpa seorang pun meninjau daftarnya tiap hari — polanya "atur sekali, kirim berulang otomatis", sama seperti peringatan pada BROADCAST TERJADWAL. Perlu diketahui juga: **`bpjs.kontrol_ke_pasien` bisa dimatikan** sehingga pengingatnya hanya masuk ke loket, dan itu bentuk pemakaian yang wajar selama RS masih menimbang keputusan (2) tanpa menunda keputusan (1).

- **TIGA keputusan terpisah untuk ADMINISTRASI** (`/administrasi`, migrations/026), dan ini kanal dengan pertanyaan kebijakan paling tajam di proyek ini -- yang beredar bukan pesan melainkan **dokumen resmi rumah sakit**, yang begitu diterima bisa diteruskan ke siapa pun tanpa sepengetahuan RS.

  (1) **Apakah surat keterangan sakit yang dikirim lewat WhatsApp diterima sebagai sah** oleh tempat kerja pasien, dan siapa yang bertanggung jawab bila berkas itu sampai ke nomor yang keliru. Nomor tujuan berasal dari `pasien.no_tlp` di Khanza, yang di rumah sakit ini **sekitar 40% di antaranya belum terpakai** -- salah kirim bukan kemungkinan teoretis. Kode sudah membatasi diri sejauh yang bisa: nomor diperiksa sebelum berkasnya dirender, poli sensitif DITOLAK sepenuhnya (bukan sekadar diganti pesan generik), dan tiap kiriman tercatat di `audit_log`. Yang tidak bisa diputuskan kode: apakah lembar bertanda tangan basah tetap wajib, dan apakah catatan kaki asal-usulnya cukup sebagai penanda keaslian.

  (2) **Apakah diagnosa ikut dicetak** (`administrasi.sertakan_diagnosa`, default MATI). Khanza punya dua bentuk suratnya dan RS ini memakai varian yang mencetak kode ICD + nama penyakit. Penerimanya pasien sendiri, yang memang berhak atas diagnosanya -- jadi ini bukan pelanggaran §5.2, melainkan keputusan yang dampaknya baru muncul saat berkasnya diteruskan. Selama mati, kolomnya tidak dibaca sama sekali dari Khanza.

  (3) **Apakah surat SEHAT boleh diterbitkan dari halaman ini sama sekali** -- dan ini yang paling gampang terlewat karena kedua surat tampak setara di layar. Surat sakit sudah ada catatannya di Khanza (dokter memutuskan, lalu tersimpan); surat sehat TIDAK -- Khanza mencetaknya langsung dari layar registrasi, jadi tidak ada satu baris pun di database yang menyatakan seorang dokter menyimpulkan "sehat". Mengirim dari tab itu berarti **menerbitkan** surat keterangan sehat atas sebuah kunjungan, bukan mengantarkan ulang surat yang sudah ada. Kode mewajibkan staf menekan kirim satu per satu dan menampilkan peringatan ini di halamannya, tapi yang harus diputuskan RS: siapa yang berwenang menyatakan seorang pasien sehat, dan apakah wewenang itu boleh dijalankan lewat tombol di dashboard.

  (4) **Apakah sidik jari dokter boleh ikut ke dalam QR pengesahan.** Khanza mengisi baris "ID" di QR-nya dengan `sha1(sidikjari.sidikjari)` -- SHA1 atas cetakan sidik jari dokter -- dan baru memakai kode dokter bila pegawainya belum mendaftarkan sidik jari. Di sini tabel itu kosong, jadi keduanya kebetulan sama dan **kode ini memakai kode dokter tanpa pernah membaca tabel `sidikjari`**. Begitu RS mulai memakai absensi sidik jari, keduanya berpisah: QR Khanza memuat turunan biometrik pegawai, QR wakhanza tidak. Yang harus diputuskan RS bukan mana yang benar melainkan apakah nilai itu boleh berada di dalam benda yang **diteruskan tanpa batas lewat WhatsApp** -- surat Khanza berpindah sebagai kertas yang diserahkan ke satu pihak, surat ini tidak. Kalau RS memutuskan keduanya harus sama persis, itu perubahan kode yang sadar-sadar, bukan penyelarasan yang boleh dilakukan diam-diam.

  (5) **Apakah surat boleh berangkat TANPA seorang pun melihatnya** (`administrasi.auto_enabled`, migrations/027) -- keputusan yang berdiri sendiri di atas ketiga di atasnya, dan yang paling gampang dianggap sekadar "versi praktis" dari keputusan (1). Bukan itu: sepanjang pengiriman manual, ada satu orang yang membuka pratinjau, melihat nama dan alamat yang tercetak, lalu menekan kirim -- dan orang itulah yang selama ini menjadi pemeriksa terakhir bahwa berkas ini memang untuk pasien ini. Menyalakan kirim otomatis menghapus langkah itu, dan yang menggantikannya cuma pemeriksaan yang bisa dilakukan mesin: nomor bisa dinormalkan, poli sensitif bisa dikenali, daftar tolak bisa dicocokkan. Yang TIDAK bisa: apakah nomor di Khanza benar-benar milik pasien yang bersangkutan. Di rumah sakit ini sekitar **40% nomor pasien belum terpakai**, dan yang salah ketik tetap sah menurut normalisasi -- ia terkirim ke pemilik nomor itu, lengkap dengan nama, umur, dan alamat pasien di dalam berkasnya. Kode sudah membatasi diri sejauh yang bisa (lantai aktivasi supaya arsip tidak ikut terbongkar, kuota per siklus, poli sensitif ditolak sepenuhnya, tunduk jam tenang dan daftar tolak), tapi tidak satu pun dari itu menjawab pertanyaan sebenarnya: **siapa yang bertanggung jawab bila surat sampai ke nomor yang keliru saat tidak ada seorang pun yang menekan kirim.** Jangan nyalakan sebelum RS menjawabnya, terpisah dari keputusan (1).

- **Apakah penjamin pasien boleh disebut di dalam pesan** (`{cara_bayar}`): variabelnya tersedia untuk ketujuh pemicu pasien, tapi **tidak satu pun template bawaan memakainya** — ia baru muncul kalau ada yang mengetiknya sendiri di `/template`, jadi keadaan awalnya nol perubahan. Ke pasiennya sendiri ini nyaris tidak menambah apa-apa: ia sudah tahu ia peserta BPJS atau bayar umum. Yang perlu diputuskan sadar-sadar adalah kombinasinya dengan `template_target` di atas — begitu sebuah pemicu punya tujuan grup, `{cara_bayar}` ikut terbaca seluruh anggota grup, dan sebagian nilai `penjab` mengatakan hal yang jauh lebih pribadi daripada "BPJS" atau "UMUM": di katalog mesin ini ada **"DINAS SOSIAL"** dan **"JASA RAHARJA"**, yang masing-masing menyiratkan status kesejahteraan dan keterlibatan kecelakaan. Kode tidak bisa membedakan mana nilai `penjab` yang layak diumumkan dan mana yang tidak — daftarnya milik RS, dan bisa bertambah kapan saja tanpa terlihat di dashboard. Kalau sebuah pemicu memakai tujuan grup, tinjau dulu isi tabel `penjab` sebelum menaruh `{cara_bayar}` di templatenya.

- **Siapa yang bertanggung jawab atas isi BALASAN OTOMATIS** -- pertanyaan yang berbeda jenisnya dari dua di bawah. Broadcast (manual maupun terjadwal) tetap "RS mengirim ke pasien"; balasan otomatis menjadikan sistemnya **menjawab pasien**, dan pasien wajar menganggap jawaban dari nomor resmi RS sebagai jawaban RS. Kode sudah membatasi diri sejauh yang bisa dilakukan kode: hanya mencocokkan kata kunci (tidak memahami keluhan), isi jawabannya seluruhnya ditulis staf atau dibaca apa adanya dari `sik.jadwal`, dan pesan yang tidak cocok DIAM secara default supaya tetap dibaca petugas. Yang TIDAK bisa diputuskan kode: siapa yang meninjau bahwa isi tiap aturan benar secara klinis dan tetap benar saat jadwal/layanan berubah, dan apa yang terjadi bila pasien bertindak berdasarkan jawaban otomatis yang ternyata usang. `autoreply.enabled` default MATI justru supaya keputusan ini diambil lebih dulu, bukan ditemukan belakangan. Jangan nyalakan sebelum RS menunjuk pemiliknya.

- **Dasar hukum BROADCAST TERJADWAL -- lebih ketat dari BROADCAST manual**: pertanyaan di atas berlaku PLUS satu lapis lagi -- broadcast biasa masih ada staf yang meninjau segmen dan mengklik kirim tiap kali; broadcast terjadwal (khususnya harian/mingguan/bulanan) mengirim berulang kali TANPA ada manusia yang meninjau ulang tiap kali jalan. Kode menyediakan pagar teknis (`stop_after_date`, jeda/aktifkan sekali klik, segmen kelewat besar dilewati bukan dipotong) tapi TIDAK memutuskan apakah pola "atur sekali, kirim berulang otomatis ke siapa pun yang saat itu masuk kriteria" sesuai basis persetujuan pasien yang berlaku di RS -- ini keputusan kebijakan, bukan sesuatu yang bisa diselesaikan lewat pagar teknis tambahan. Jangan aktifkan jadwal berulang ke pasien sungguhan dalam jumlah besar sebelum RS memutuskan ini, terpisah dari keputusan BROADCAST manual di atas.
